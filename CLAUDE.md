# NLightning — agent guide (CLAUDE.md / AGENTS.md)

## Project goal

NLightning works as a fully functioning, spec-compliant BOLT Lightning node: interoperates with LND/CLN/Eclair/LDK, and can open, operate, route through and close channels safely with real funds. The BOLT specs are authoritative; every protocol piece is validated with official test vectors.

NLightning is a C# (.NET 10) Lightning Network node and library set. It is split into Domain, Application and several Infrastructure projects, plus a Daemon (`NLightning.Daemon`) and a CLI client (`NLightning.Client`) that talks to the daemon over IPC. Both usage texts call the binary `nltg` (`src/NLightning.Daemon/Utilities/DaemonUtils.cs`, `src/NLightning.Client/Utils/ClientUtils.cs`); the assemblies keep their `NLightning.*` names. What works today: BOLT 8 transport, BOLT 1 init/ping/error, BOLT 2 v1 channel **opening** (open → accept → funding_created/signed → channel_ready; idle and pushed channels stay Active against LND, BOLT2 plan Proof N0/N1), BOLT 3 funding/commitment/HTLC transactions, HTLC signatures and key derivation (every Appendix C/F vector byte-exact), BOLT 2 **HTLC normal operation on the wire** (N6: the commitment engine `src/NLightning.Domain/Channels/Commitments/` driven by the update_add/fulfill/fail/fail_malformed_htlc, commitment_signed, revoke_and_ack and update_fee handlers and by `IChannelOperations`/`CommitScheduler`, one save per transition before sending), BOLT 2 **channel_reestablish** (N7: `ReestablishPlanner`, retransmission, data-loss detection, error re-send; proven against LND in `Docker/ReestablishFlowTests`), BOLT 9 feature bits (unimplemented features are refused unless `Features:AllowExperimentalFeatures=true`), BOLT 7 gossip parse-and-drop plus empty replies to gossip queries, and a direct signed `channel_update` exchange with the channel peer once a channel is open (ABCD W1-E; LND shows our policy), BOLT 11 invoices (encode validates, `r` route hints for private channels) with an `InvoiceService` and invoice/payment/forward-circuit tables, and `createinvoice`/`listinvoices`/`payinvoice`/`listpayments` over IPC. BOLT 4 onion core (M1+M2: packet, Sphinx construct/peel, hop payloads, validator, replay cache), legacy error onions (M3) and M4 in `src/NLightning.Application/Payments/`: the `HtlcSwitch` (forwarding, final-hop receive, upstream propagation, replay after restart) and `PaymentService` (send directly or through a route hint). The ABCD multi-hop e2e (LND → NLightning → NLightning → LND, `test/NLightning.Integration.Tests/Docker/Abcd/`) is green. BOLT 2 **cooperative close** (N10, legacy `shutdown`/`closing_signed` with and without `fee_range`, `closechannel` over IPC; `src/NLightning.Application/Channels/Close/`), BOLT 2 **channel safety** (N9: `Channels/Safety/` HTLC deadline monitor and fail-the-channel broadcast of our latest commitment; `Channels/Fees/` update_fee scheduler for channels we fund and `max_dust_htlc_exposure_msat`). **Not implemented:** `option_simple_close` (N11), BOLT 5 on-chain handling (sweeps, HTLC resolution, detecting the peer's commitment, penalty; plan `docs/agents/BOLT5_ONCHAIN_PLAN.md`), MPP, attribution_data, route-blinding payloads, a persistent onion replay set, and BOLT 7 announcements/graph.

Deeper docs: `docs/agents/REPO_MAP.md` (per-area map), `docs/agents/BOLT_COVERAGE.md` (status matrix), `docs/agents/ONION_ROUTING_PLAN.md` (BOLT 4 plan), `docs/agents/BOLT2_NORMAL_OPERATION_PLAN.md` (BOLT 2 HTLC / reestablish / close plan, milestones N0-N11), `docs/agents/BOLT5_ONCHAIN_PLAN.md` (BOLT 5 plan, milestones O0-O8), `docs/agents/LNBOLT_REVIEW.md` (legacy onion code review), `docs/agents/ABCD_ROADMAP.md` (waves to the multi-hop LND e2e goal). Some `src/*/` and `test/` folders also have their own `CLAUDE.md`; read those when you work there.

## Layers & dependency rules

```
NLightning.Daemon (composition root, DI, IPC server, hosted service)
  direct refs: Application, Infrastructure, Infrastructure.Bitcoin, Infrastructure.Serialization,
               Infrastructure.Repositories, Infrastructure.Persistence.{Postgres,Sqlite,SqlServer},
               Client, Daemon.Plugins, Daemon.Contracts
  Client -> Transport.Ipc -> Daemon.Contracts          (Transport.Ipc also -> Domain; Daemon gets it only via Client)

Application -> Infrastructure.Bitcoin -> Infrastructure -> Domain     (Application also -> Infrastructure, Domain directly)
Infrastructure.Serialization -> Infrastructure, Domain
Infrastructure.Repositories  -> Infrastructure.Persistence -> Domain
Infrastructure.Persistence.{Postgres,Sqlite,SqlServer} -> Infrastructure.Persistence
NLightning.Domain   (no NuGet, no project refs)
Application -> Bolt11 -> Infrastructure + Infrastructure.Bitcoin
```
Simplified: see each `*.csproj` for the exact `ProjectReference` list.

- **Domain** references nothing. It holds most abstractions (`ITlvConverterFactory`, `IUnitOfWork`, `ILightningSigner`, `IChannelManager`, `IMessageFactory`, ...). Exceptions: `IEcdh` and `ICryptoProvider` live in `src/NLightning.Infrastructure/Crypto/Interfaces/`, `ITcpService` in `src/NLightning.Infrastructure/Transport/Interfaces/`, and `IBlockchainMonitor` in `src/NLightning.Infrastructure.Bitcoin/Wallet/Interfaces/`. Keep Domain BCL-only and free of NBitcoin.
- **Infrastructure** → Domain. **Infrastructure.Bitcoin** → Infrastructure (all secp256k1/NBitcoin code lives here). **Infrastructure.Serialization** → Domain + Infrastructure. **Persistence** → Domain. **Repositories** → Domain + Persistence.
- **Application** → Domain + Infrastructure + Infrastructure.Bitcoin + Bolt11 (invoices, since ABCD W1-B). This breaks clean architecture: handlers use `IBlockchainMonitor`, tx builders and `ITcpService` directly. Don't make it worse; add new abstractions to Domain.
- Every project targets net10.0, plus net11.0 when built with SDK 11 or newer (`src/Directory.Build.props` and `test/Directory.Build.props`, which gate on the SDK version read from `MSBuildBinPath`; `-p:NltgTargetNet11=false` or `-f net10.0` for net10.0 only; the Blazor projects stay net10.0). LangVersion is 14. `global.json`: SDK 10.0.100+, rollForward latestMajor, prereleases allowed until .NET 11 GA. See `docs/agents/NET11_PLAN.md`.
- Each layer exposes an `Add…` extension in its `DependencyInjection.cs`: `AddApplicationServices`, `AddInfrastructureServices`, `AddSerializationInfrastructureServices`, `AddPersistenceInfrastructureServices`, `AddRepositoriesInfrastructureServices`, and the exception **`AddBitcoinInfrastructure()`** (no `Services` suffix). The Daemon composes them in `src/NLightning.Daemon/Extensions/NodeServiceExtensions.cs`: `AddNltgNodeServices(configuration, secureKeyManager)` is the whole node graph (layers, fee-service HttpClient, options, client and IPC command handlers), and `ConfigureNltgServices` adds only the hosted service and the config-path IPC pieces (`NamedPipeIpcService`, `CookieFileAuthenticator`). `IEcdh` and `ILightningSigner` (`LocalLightningSigner`, from the host's `ISecureKeyManager`) are registered in `src/NLightning.Infrastructure.Bitcoin/DependencyInjection.cs`; `IChannelOpenValidator`, `IChannelFactory`, `ICommitmentTransactionModelFactory` and `IFundingTransactionModelFactory` (Domain, which has no DI) in `AddApplicationServices`. `ITlvConverterFactory` is `TryAddSingleton`ed by both `AddInfrastructureServices` and `AddSerializationInfrastructureServices`. The Docker tests build their node through `test/NLightning.Integration.Tests/Docker/Utils/NLightningTestNode.cs`, which calls `AddNltgNodeServices` too (NL-156), so there is nothing to mirror by hand: register new services in the layer's `DependencyInjection.cs`. (`PostgresTests.cs` and `SqlServerTests.cs` in that folder are container-backed migrate + round-trip tests; the SQLite equivalent is `test/NLightning.Integration.Tests/Persistence/SqlitePersistenceTests.cs`, which runs in CI.)

## Recipes

### Add a BOLT wire message end to end
1. `src/NLightning.Domain/Protocol/Constants/MessageTypes.cs`: add the enum value.
2. `src/NLightning.Domain/Protocol/Payloads/XPayload.cs` (implements `IChannelMessagePayload` if channel-scoped) and `Messages/XMessage.cs` (`sealed : BaseChannelMessage`, `public new XPayload Payload => (XPayload)base.Payload`, and build `Extension = new TlvStream()` only if it has TLVs).
3. Payload serializer in `src/NLightning.Infrastructure.Serialization/Payloads/`. Register it in `Factories/PayloadSerializerFactory.cs` in **both** dictionaries (Type→serializer and MessageTypes→Type).
4. Message-type serializer in `Messages/Types/`. Register it in `Factories/MessageTypeSerializerFactory.cs` in **both** `RegisterSerializers` and `RegisterTypeDictionary`. If you miss the MessageTypes map, the message is treated as unknown: dropped if its type is odd, and the peer is killed if it is even.
5. `Create*` method on `src/NLightning.Domain/Protocol/Interfaces/IMessageFactory.cs` and `src/NLightning.Application/Protocol/Factories/MessageFactory.cs`.
6. Routing. For a channel message, add `IChannelMessageHandler<XMessage>` in `src/NLightning.Application/Channels/Handlers/` (auto-registered Scoped by reflection) **and** a `case` in `ChannelManager.HandleChannelMessageAsync` (`src/NLightning.Application/Channels/Managers/ChannelManager.cs`). Without the case, the message reaches `default` → channel-scoped `ChannelWarningException` ("not supported yet"): the message is ignored, the peer gets a `warning` for that channel and stays connected (today only the v2/interactive-tx messages end there). If the channel is unknown to us (not in memory, not a temporary channel of that peer, not in the DB), the peer gets an `error` for that channel_id instead (BOLT 1). Non-channel messages go through `src/NLightning.Infrastructure/Node/Services/PeerService.cs` `HandleMessage`: besides channel/error/warning it handles gossip (256-259 dropped, queries 261/263 answered by `GossipQueryResponder`, 265 ignored) and `stfu` (warning + disconnect); anything else is dropped.
7. Round-trip test in `test/NLightning.Infrastructure.Serialization.Tests/Messages/`.

### Add a TLV
1. Add a `static readonly BigSize` in `src/NLightning.Domain/Protocol/Constants/TlvConstants.cs`. Numbers are per-message and **collide** (0 and 1 are each reused). For new namespaces such as onion hop payloads, use a separate constants class.
2. `src/NLightning.Domain/Protocol/Tlv/XTlv.cs : BaseTlv`, calling `base(TlvConstants.X)`.
3. `src/NLightning.Infrastructure/Protocol/Tlv/Converters/XTlvConverter.cs : ITlvConverter<XTlv>` (validate Type/Length and throw `InvalidCastException`; mark the explicit non-generic members `[ExcludeFromCodeCoverage]`). Register it in `src/NLightning.Infrastructure/Protocol/Factories/TlvConverterFactory.cs`.
4. `TlvStreamSerializer` looks the converter up by the TLV's runtime type (`ITlvConverterFactory.GetConverter(Type)`), so registration is enough; an unregistered subtype throws "No converter found", a plain `BaseTlv` is written verbatim. `TlvStreamSerializerTests` requires a sample for every registered converter, so add one there.
5. Add a nullable property and ctor arg on the message. Read it in the message-type serializer with `TryGetTlv(TlvConstants.X, …)` plus the converter.
6. Tests go in `test/NLightning.Infrastructure.Tests/Protocol/Tlv/Converters/`.

### Add a channel message handler
Implement `IChannelMessageHandler<TMessage>.HandleAsync(msg, currentState, negotiatedFeatures, peerPubKey)`, which returns `Task<IReadOnlyList<IChannelMessage>>`: the messages to send back to the same peer, in wire order (empty for none). `ChannelManager` runs it under the channel's lock (`IChannelLockProvider`, one `SemaphoreSlim` per channel id, not reentrant) and raises every returned message through `OnResponseMessageReady` before releasing it; `PeerManager` puts them into that peer's `PeerOutbox`, the single ordered send path. To send elsewhere or outside a reply, raise an event that goes through `ChannelManager.OnResponseMessageReady` while holding the channel's lock. Throw `ChannelFailedException` to fail the channel (`ChannelManager` persists `ChannelState.Failed` + the error under the lock, then the error is sent and the connection kept; later messages and every reconnect get the stored error again, NL-200), `ChannelErrorException` (send `error` for the channel and disconnect) or `ChannelWarningException` (send a `warning`; set `CloseConnection = true` for BOLT's "send a warning and close the connection" option). Pass the channel id when you have it; `ChannelManager` attaches the message's (temporary) channel id to any that lack one, because an all-zero channel_id `error` makes the peer fail every channel (BOLT 1). Only the `PeerMessage` text goes on the wire. For temporary-channel-id messages `currentState` is `None`; look temp state up via `IChannelMemoryRepository.TryGetTemporaryChannelState`. Persist through a scoped `IUnitOfWork` and call `SaveChangesAsync`. Never inject `IUnitOfWork` into a singleton; open a scope instead. Then add the `ChannelManager` case (step 6 above).

### Add an EF migration (all 3 providers)
Edit the entity (`src/NLightning.Infrastructure.Persistence/Entities/…`, `internal` parameterless ctor), its `EntityConfiguration/…/Configure<Name>Entity`, and the DbSet/`OnModelCreating` in `Contexts/NLightningDbContext.cs`. Then:
Prerequisite: `dotnet-ef` is not installed by the repo (no `.config/dotnet-tools.json`); run `dotnet tool install --global dotnet-ef --version 10.0.12` (matches the EF packages; the migration scripts pass `--framework net10.0`, override with `EF_FRAMEWORK`). `dotnet ef` loads the provider assemblies from the shared `src/NLightning.Infrastructure.Persistence/bin/Debug`, so build the three `NLightning.Infrastructure.Persistence.{Postgres,Sqlite,SqlServer}` projects in Debug first or it generates against stale models (NL-233).
```bash
cd src/NLightning.Infrastructure.Persistence
./scripts/start_postgres.sh && ./scripts/start_sql.sh      # Docker: postgres :15432, mssql :1433
./scripts/add_migration.sh MyCamelCaseName                  # builds + runs dotnet ef for Postgres, Sqlite, SqlServer
```
`add_migration.sh` runs `dotnet ef database update` before and after each `migrations add`, so the new migration is also **applied** to the Postgres/SqlServer containers and to `src/NLightning.Infrastructure.Persistence/nltg.db` (created by the script; don't commit it). `start_sql.sh` pulls mssql with `--platform linux/amd64`, which runs under emulation on Apple Silicon.
Commit the migration, Designer and Snapshot files for all three `NLightning.Infrastructure.Persistence.{Postgres,Sqlite,SqlServer}` projects together. Never copy migration files between providers: SqlServer uses varbinary sizes and Postgres uses snake_case. The design-time factory picks the provider from the first env var it finds, checking `NLIGHTNING_POSTGRES`, then `_SQLITE`, then `_SQLSERVER`. Remove a migration with `./scripts/remove_migration.sh` and revert the model changes by hand. Because the migration was already applied, EF will likely refuse to remove it until you roll each database back (`dotnet ef database update <PreviousMigration>` per provider) or recreate them with `./scripts/destroy_{postgres,sql,sqlite}.sh` then `start_*.sh` (not verified end to end). The `destroy_*.sh` scripts are also the cleanup step.

## Coding conventions (`.editorconfig`, enforced by `dotnet format` in CI)
- File-scoped namespace equal to the folder path. `System`/`Microsoft`/`NBitcoin` usings go **above** the namespace. `NLightning.*` usings go **after** it as relative names (`using Domain.Money;`).
- Private fields are `_camelCase`, private static fields are `s_camelCase`, private `const` fields are `PascalCase` (no prefix), locals and parameters are `camelCase`, and local functions are `PascalCase`. All naming rules are severity **error** in `dotnet format`. No `this.`. Prefer `var`. Unused usings, members and parameters, and double blank lines, are **errors** in format (not in build).
- LF endings. `*.cs` files have no final newline.
- Amounts are always `LightningMoney`. Implicit `ulong/long → LightningMoney` is **msat**, so use `LightningMoney.Satoshis(...)`. Byte-backed value objects (`ChannelId`, `TxId`, `CompactPubKey`, `Hash`) convert implicitly to and from `byte[]`.
- Integers on the wire are big-endian. Existing code uses `src/NLightning.Infrastructure/Converters/EndianBitConverter.cs`. Prefer `BinaryPrimitives` for new code, because the LE trim/pad helpers are suspect.
- Tests use xUnit v3 + Moq, named `Given_X_When_Y_Then_Z` with Arrange/Act/Assert comments. Pass `TestContext.Current.CancellationToken`. Moq can't mock Span parameters, so use the Fake* + virtual byte[] pattern in `test/NLightning.Tests.Utils/Mocks`.
- `InternalsVisibleTo` is declared in `src/*/AssemblyInfo.cs` where one exists: only Application, Bolt11, Daemon, Domain, Infrastructure, Infrastructure.Bitcoin and Infrastructure.Persistence have it. `NLightning.Domain.Tests` and `NLightning.Daemon.Tests` have **no** internals access (Application lists `NLightning.Application.Tests`) (Daemon lists a stale `NLightning.Bolts.Tests`). When a test needs internals, add an entry, or create `AssemblyInfo.cs` if the project lacks one.

## Non-obvious gotchas
- `UpdateAddHtlcPayload.OnionRoutingPacket` is a mandatory raw `ReadOnlyMemory<byte>` of exactly `OnionConstants.PacketLength` (1366) bytes (constructor and serializer enforce it; a short read throws). Parse it with `OnionPacket`. The update_add_htlc extension is read strictly (unknown even types rejected) and the blinded path uses `TlvConstants.BlindedPath`.
- Deserializers use `stream.Position/Length` to find trailing TLVs, so they need a seekable stream bounded to one message.
- `TlvStream` (`src/NLightning.Domain/Protocol/Models/TLVStream.cs`; note the file-name casing) is a `SortedDictionary`, so it silently re-sorts records. Every message extension is read with `DeserializeStrictAsync(stream, knownTypes)` (NL-001): add every TLV a message can carry to its serializer's known-type set, because an unlisted **even** type is rejected (the peer gets a `warning` and is disconnected); unlisted odd types are ignored. A malformed message answers with a connection `warning` and closes (NL-207). BigSize decoding is canonical.
- `TlvStreamSerializer.DeserializeAsync` enforces strictly increasing types and length <= remaining bytes but cannot reject unknown even types (no known-type set); use `DeserializeStrictAsync(stream, knownTypes)` where the namespace is known (new messages). Hop payloads use `IHopPayloadSerializer` instead, because `invalid_onion_payload` needs the offending type and offset, which the strict reader does not report.
- Some Domain TLVs (`FeeRangeTlv`, `RemoteAddressTlv`, `FundingOutputContributionTlv`) don't hold real wire bytes in `Value`. Always go through the converter.
- `ChannelModel.UpdateState` only allows strictly increasing `ChannelState` values, so number new states with that in mind (`Failed = 35` sits between Closing and Closed, `OnchainResolving = 37` between Failed and Closed). The HTLC state lives in the engine snapshot `ChannelModel.Commitments` (`ChannelCommitments`); balances, next ids and commitment numbers are read from it. The legacy `LocalOfferedHtlcs`/`RemoteOfferedHtlcs` collections are no longer persisted and are empty after a reload (NL-241). Change the snapshot only through the engine: per transition `IChannelStateDbRepository.ApplyAsync` + one `SaveChangesAsync`, then `ChannelModel.UpdateCommitments(next, extras)`, then send. Engine events (`CommitmentsResult.Events`) are replayed at startup with `ChannelDomainEvents.DerivePending`, so every consumer must be idempotent. `LocalBalance`/`RemoteBalance` are **gross** (they include the owner's pending offered HTLCs; NL-062).
- Normal-operation wiring (N6, `src/NLightning.Application/CLAUDE.md` has the details): receive handlers go through the scoped `ChannelStateTransitionService`; the send side is the singleton `ChannelOperationsService : IChannelOperations`, which publishes under the channel lock through `IChannelMessagePublisher` and schedules `CommitScheduler` after releasing it. Handlers queue domain events in the scoped `ChannelDomainEventQueue`, drained into `IHtlcSwitch` after the lock is released. Every send-side update and signature requires the channel's link (`IPeerLivenessProbe`, decorated by `ReestablishGatedLivenessProbe` and `LinkUpReplayingPeerLivenessProbe`): pinned to the connection the channel turned Open on, then re-marked by `MarkLinkUp` after each channel_reestablish, which also replays the channel's pending events into the switch. Normal-operation messages of a channel not yet reestablished on the current connection are dropped by `ChannelManager.Publish` (the reestablish retransmits them). `AddApplicationServices` registers `HtlcSwitch` (`AddHtlcSwitchServices`, replacing the `LocalOnlyHtlcSwitch` default) and then `PaymentService` (`AddPaymentSendServices`); keep that order. `IChannelOperations.OfferHtlcAsync` saves the `HtlcOrigin` in the add's save, and `FulfillHtlcAsync(..., stageWithFulfill, ct)` stages extra writes (the invoice settle) in the fulfill's save. HTLC messages and operations are refused unless `NodeOptions.HtlcsEnabled` (`Node:EnableHtlcs`; unset means on for regtest only).
- Fee estimates: `IFeeService` is one shared singleton (`Infrastructure.Bitcoin/Services/AddFeeServices`, registered by `AddNltgNodeServices`; the Docker test node passes a fixed-rate handler); the instance the daemon starts is the one every consumer reads, and it never reports 0 (`FeeEstimation:FallbackFeeRatePerKw`, default 2500). `FeeEstimation:Source` is `Http` (value in `RateUnit`, default sat/vB), `Bitcoind` (`estimatesmartfee`) or `Fixed`; every rate goes through `FeeRateConverter` (sat/vB x 250, floored at BOLT 3's 253 sat/kw; the old `RateMultiplier` is ignored with a warning, NL-288). As fundee we accept any `open_channel` feerate from 253 sat/kw (NL-289).
- Wallet addresses: `GetUnusedAddressAsync` hands out spent addresses again (it infers use from UTXO rows; concurrent closes reserve their shutdown address, NL-280 partial); a new batch starts one past the highest index, under a process-wide lock (NL-283 fixed); `BlockchainMonitorService` keeps watching an address after its first deposit (NL-281).
- `ISha256` is registered as `ThreadLocalSha256` (NL-247, W3-D): one hash state per thread, so the shared singleton is safe for concurrent callers.
- `test/NLightning.Tests.Utils/Mocks/FakeServiceProvider` returns null for unregistered types like the real provider (NL-249, W3-D); set `Strict = true` to get the old `KeyNotFoundException`.
- `FeatureSet.GetBytes()` is little-endian; use `GetWireBytes()` for anything that goes on the wire (e.g. channel_type, NL-112). Negotiated features: Compulsory if either side requires, Optional if both support (NL-111). Unimplemented features are listed in `FeatureOptions.ExperimentalFeatures` and refused unless `Features:AllowExperimentalFeatures=true`; remove a feature from that set when you implement it.
- Channel parameters are per side (NL-194): `ChannelModel.ChannelParams.Local` is what we announced and `Remote` what the peer announced (see `ChannelParams` XML docs for which side each value binds; our commitment's to_local uses `Remote.ToSelfDelay`). open_channel/accept_channel are built from `ChannelParams.Local` (`IMessageFactory.CreateOpenChannel1Message/CreateAcceptChannel1Message` take a `ChannelParty`); accept_channel echoes the opener's channel_type (NL-218). Channels opened before the split carry `ChannelParams.HasInferredParams = true` (partly guessed limits, set by a migration): never fail such a channel over those limits.
- `ChannelDbRepository.UpdateAsync` syncs child rows (config, key sets, local aliases) by primary key (NL-192); don't go back to `DbSet.Update(graph)`. It never writes HTLCs, and once a snapshot exists (or is staged) it leaves the snapshot-owned scalars alone: HTLC, commitment-slot and fee-update rows are written only by `ChannelStateDbRepository` (N5). A channel with legacy HTLC rows (states 0-3) is refused with `LegacyHtlcStateException` by `GetByIdAsync` and skipped (logged) by multi-channel loads (NL-025). SQLite connections run `PRAGMA synchronous=FULL`. Balances are stored in msat (`Channels.LocalBalanceMsat/RemoteBalanceMsat`, `long`, NL-191) and the real SCID in `Channels.ShortChannelId` (NL-225, null until funding confirms); `test/NLightning.Integration.Tests/Persistence/ChannelRoundTripTests.cs` reloads every `ChannelModel` field, so extend it when you add one.
- Ordering (NL-033, NL-193, BOLT2 N0-T3): each peer has one inbound loop (its channel messages are handled one at a time, in arrival order; the transport read loop only queues them) and one `PeerOutbox` (replies, `OnResponseMessageReady` messages, channel warnings and the final error/warning of a disconnect, sent FIFO, one at a time). Every channel mutation (peer message, startup registration, funding confirmation, stale/backfill block handling) holds `IChannelLockProvider`'s lock for that channel id; never hold two, never re-acquire, and only enqueue (never await a send) while holding one. Startup (`PeerManager.StartAsync`) awaits the registration of every non-Closed/Stale channel of every peer (memory + signer) before the first connection, then connects; a peer with such channels that can't be reached is retried in the background with exponential backoff (5 s doubling to 10 min; `Node:ReconnectInitialDelay`/`Node:ReconnectMaxDelay`) until it connects either way or the manager stops (NL-201); `PeerManager` reads the delays from `IOptions<NodeOptions>` when given. The same backoff loop starts when a peer with active channels (per `IChannelMemoryRepository`) drops at runtime, unless we disconnected it on purpose (`DisconnectPeer`, `StopAsync`) or a newer connection replaced it. A new connection from a connected peer replaces the old one (LND/CLN behavior); within `SimultaneousConnectWindow` (5 s) of an opposite-direction connection, both ends keep the one initiated by the lower pubkey (LND tie-break). A closed connection's inbound loop drops what is still queued, and the next connection's loop starts only after it has finished (StopAsync waits for them too); replies raised by the old loop never go out on the new connection.
- `NLightning.sln` config mappings are maintained by hand. When you add a project or configuration, run `python3 scripts/check-sln-configs.py` (a CI step); it also fails when a `*.Tests` project lacks `IsTestProject` or `xunit.runner.visualstudio`.
- `MessagePackSerializer.DefaultOptions = NLightningMessagePackOptions.Options` must be set on both IPC ends. Any IPC wire change also needs a new `ClientCommand` value (never renumber existing ones) and an `IIpcCommandHandler` registered in `NodeServiceExtensions`. Client and daemon must come from the same build (NL-210).
- Key files are v2 (random salt/nonce, full UTF-8 password); a v1 file is upgraded in place with a `<file>.v1.bak`, and older builds can't read v2 (NL-158, NL-211).
