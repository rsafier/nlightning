# NLightning — agent guide (CLAUDE.md / AGENTS.md)

## Project goal

NLightning works as a fully functioning, spec-compliant BOLT Lightning node: interoperates with LND/CLN/Eclair/LDK, and can open, operate, route through and close channels safely with real funds. The BOLT specs are authoritative; every protocol piece is validated with official test vectors.

NLightning is a C# (.NET 10) Lightning Network node and library set. It is split into Domain, Application and several Infrastructure projects, plus a Daemon (`NLightning.Daemon`) and a CLI client (`NLightning.Client`) that talks to the daemon over IPC. Both usage texts call the binary `nltg` (`src/NLightning.Daemon/Utilities/DaemonUtils.cs`, `src/NLightning.Client/Utils/ClientUtils.cs`); the assemblies keep their `NLightning.*` names. What works today: BOLT 8 transport, BOLT 1 init/ping/error, BOLT 2 v1 channel **opening** (open → accept → funding_created/signed → channel_ready; idle and pushed channels stay Active against LND, BOLT2 plan Proof N0/N1), BOLT 3 funding/commitment/HTLC transactions, HTLC signatures and key derivation (every Appendix C/F vector byte-exact), BOLT 2 **HTLC normal operation on the wire** (N6: the commitment engine `src/NLightning.Domain/Channels/Commitments/` driven by the update_add/fulfill/fail/fail_malformed_htlc, commitment_signed, revoke_and_ack and update_fee handlers and by `IChannelOperations`/`CommitScheduler`, one save per transition before sending), BOLT 2 **channel_reestablish** (N7: `ReestablishPlanner`, retransmission, data-loss detection, error re-send; proven against LND in `Docker/ReestablishFlowTests`), BOLT 9 feature bits (unimplemented features are refused unless `Features:AllowExperimentalFeatures=true`), BOLT 7 gossip (see the G-A/G-B/G-C sentences below), a direct signed `channel_update` exchange with the channel peer once a channel is open (ABCD W1-E; LND shows our policy), BOLT 11 invoices (encode validates, `r` route hints for private channels, none once an announced channel can receive) with an `InvoiceService` and invoice/payment/forward-circuit tables, and `createinvoice`/`listinvoices`/`payinvoice`/`listpayments` over IPC. BOLT 4 onion core (M1+M2: packet, Sphinx construct/peel, hop payloads, validator, replay set), legacy error onions (M3) and M4 in `src/NLightning.Application/Payments/`: the `HtlcSwitch` (forwarding, final-hop receive, upstream propagation, replay after restart) and `PaymentService` (send directly, through route hints or over the gossip graph). The ABCD multi-hop e2e (LND → NLightning → NLightning → LND, `test/NLightning.Integration.Tests/Docker/Abcd/`) is green. BOLT 2 **cooperative close** (N10, legacy `shutdown`/`closing_signed` with and without `fee_range`, `closechannel` over IPC; `src/NLightning.Application/Channels/Close/`), BOLT 2 **channel safety** (N9: `Channels/Safety/` HTLC deadline monitor and fail-the-channel broadcast of our latest commitment; `Channels/Fees/` update_fee scheduler for channels we fund and `max_dust_htlc_exposure_msat`). BOLT 5 on-chain resolution (ABCD wave 5, plan `docs/agents/BOLT5_ONCHAIN_PLAN.md`): `forceclosechannel`/`pendingsweeps` IPC, every funding spend classified by `Application/Onchain/OnchainChannelWatcher` and its outputs resolved by `OnchainResolutionExecutor` through the `IOutputResolver`s `LocalCommitResolver` (to_local, HTLC-timeout/success and second-level sweeps), `RemoteCommitResolver` (to_remote, HTLC claims on the peer's current/next/future commitment) and `RevokedCommitResolver` (penalties); Docker proofs O2-O5 in `Docker/Onchain/`. ## Issue tracking

- GitHub issues are disabled on this fork. The single issue ledger is **`docs/agents/ISSUES.md`** (IDs `NL-###`). Check it before starting work and cite the ID in commit messages.
- When you fix something, update its entry (`Status: fixed (<SHA>)`) and the summary counts **in the same commit**. When you find something new, add it with the next free `NL-###`. Never renumber and never delete entries; mark them `wontfix` or `duplicate of NL-###` instead.

## Layers & dependency rules

```
NLightning.Daemon (composition root, DI, IPC server, hosted service)
  direct refs: Application, Infrastructure, Infrastructure.Bitcoin, Infrastructure.Serialization,
               Infrastructure.Repositories, Infrastructure.Persistence.{Postgres,Sqlite,SqlServer},
               Client, Daemon.Contracts   (the plugin stub Daemon.Plugins is deleted: no runtime plugin loading, NL-151)
  Client -> Transport.Ipc -> Daemon.Contracts          (Transport.Ipc also -> Domain; Daemon gets it only via Client)

Application -> Infrastructure.Bitcoin -> Infrastructure -> Domain     (Application also -> Infrastructure, Domain directly)
Infrastructure.Serialization -> Infrastructure, Domain
Infrastructure.Repositories  -> Infrastructure.Persistence -> Domain
Infrastructure.Persistence.{Postgres,Sqlite,SqlServer} -> Infrastructure.Persistence
NLightning.Domain   (no NuGet, no project refs)
Application -> Bolt11 -> Infrastructure + Infrastructure.Bitcoin
```
Simplified: see each `*.csproj` for the exact `ProjectReference` list.

- **Domain** references nothing. It holds most abstractions (`ITlvConverterFactory`, `IUnitOfWork`, `ILightningSigner`, `IChannelManager`, `IMessageFactory`, ...). Exceptions: `IEcdh` and `ICryptoProvider` live in `src/NLightning.Infrastructure/Crypto/Interfaces/`, `ITcpService` in `src/NLightning.Infrastructure/Transport/Interfaces/`, and `IBlockchainMonitor` in `src/NLightning.Infrastructure.Bitcoin/Wallet/Interfaces/`. ### Add a BOLT wire message end to end
1. `src/NLightning.Domain/Protocol/Constants/MessageTypes.cs`: add the enum value.
2. `src/NLightning.Domain/Protocol/Payloads/XPayload.cs` (implements `IChannelMessagePayload` if channel-scoped) and `Messages/XMessage.cs` (`sealed : BaseChannelMessage`, `public new XPayload Payload => (XPayload)base.Payload`, and build `Extension = new TlvStream()` only if it has TLVs).

4. Message-type serializer in `Messages/Types/`. Register it in `Factories/MessageTypeSerializerFactory.cs` in **both** `RegisterSerializers` and `RegisterTypeDictionary`. If you miss the MessageTypes map, the message is treated as unknown: dropped if its type is odd, and the peer is killed if it is even.
5. `Create*` method on `src/NLightning.Domain/Protocol/Interfaces/IMessageFactory.cs` and `src/NLightning.Application/Protocol/Factories/MessageFactory.cs`.
6. Routing. For a channel message, add `IChannelMessageHandler<XMessage>` in `src/NLightning.Application/Channels/Handlers/` and put it on the explicit Scoped registration list in `DependencyInjection.cs` (`AddChannelMessageHandlers`, NL-055; the guard test `ChannelMessageHandlerRegistrationTests` fails until it is listed) **and** a `case` in `ChannelManager.HandleChannelMessageAsync` (`src/NLightning.Application/Channels/Managers/ChannelManager.cs`). Without the case, the message reaches `default` → channel-scoped `ChannelWarningException` ("not supported yet"): the message is ignored, the peer gets a `warning` for that channel and stays connected (today only `open_channel2`/`accept_channel2` end there; the interactive-tx messages 66-74 go to the `Tx*MessageHandler`s and `IInteractiveTxDriver` since wave qit). If the channel is unknown to us (not in memory, not a temporary channel of that peer, not in the DB), the peer gets an `error` for that channel_id instead (BOLT 1). Non-channel messages go through `src/NLightning.Infrastructure/Node/Services/PeerService.cs` `HandleMessage`: besides channel/error/warning it handles gossip (256/257/258 go to the optional `IGossipIngress` (the graph, when `Gossip:Enabled`), 258 also to `ChannelUpdateService` through `OnChannelUpdateReceived`; 259 goes the channel path (`AnnouncementSignaturesMessageHandler`, NL-342), 261-265 go to the optional `IGossipSyncService` (`Application/Gossip/Sync/GossipSyncManager`: queries answered from the graph by `QueryResponder`, replies to our own queries checked, the peer's `gossip_timestamp_filter` kept for the relay; without a sync service queries get empty replies)) `onion_message` (513) goes to the optional `IOnionMessageService.HandleIncoming` (queued, never processed on the read loop); `stfu` (2) is a channel message since wave qit and goes the channel path to `StfuMessageHandler` → `IQuiescenceService` (NL-019); anything else is dropped.

### Add a channel message handler
Implement `IChannelMessageHandler<TMessage>.HandleAsync(msg, currentState, negotiatedFeatures, peerPubKey)`, which returns `Task<IReadOnlyList<IChannelMessage>>`: the messages to send back to the same peer, in wire order (empty for none). `ChannelManager` runs it under the channel's lock (`IChannelLockProvider`, one `SemaphoreSlim` per channel id, not reentrant) and raises every returned message through `OnResponseMessageReady` before releasing it; `PeerManager` puts them into that peer's `PeerOutbox`, the single ordered send path. To send elsewhere or outside a reply, raise an event that goes through `ChannelManager.OnResponseMessageReady` while holding the channel's lock. Throw `ChannelFailedException` to fail the channel (`ChannelManager` persists `ChannelState.Failed` + the error under the lock, then the error is sent and the connection kept; later messages and every reconnect get the stored error again, NL-200), `ChannelErrorException` (send `error` for the channel and disconnect) or `ChannelWarningException` (send a `warning`; set `CloseConnection = true` for BOLT's "send a warning and close the connection" option). Pass the channel id when you have it; `ChannelManager` attaches the message's (temporary) channel id to any that lack one, because an all-zero channel_id `error` makes the peer fail every channel (BOLT 1). Only the `PeerMessage` text goes on the wire. For temporary-channel-id messages `currentState` is `None`; look temp state up via `IChannelMemoryRepository.TryGetTemporaryChannelState`. Persist through a scoped `IUnitOfWork` and call `SaveChangesAsync`. Never inject `IUnitOfWork` into a singleton; open a scope instead. Then add the `ChannelManager` case (step 6 above).

### Add an EF migration (all 3 providers)

Prerequisite: `dotnet-ef` is not installed by the repo (no `.config/dotnet-tools.json`); run `dotnet tool install --global dotnet-ef --version 10.0.12` (matches the EF packages; the migration scripts pass `--framework net10.0`, override with `EF_FRAMEWORK`). ## Coding conventions (`.editorconfig`, enforced by `dotnet format` in CI)
- File-scoped namespace equal to the folder path. `System`/`Microsoft`/`NBitcoin` usings go **above** the namespace. `NLightning.*` usings go **after** it as relative names (`using Domain.Money;`).
- Private fields are `_camelCase`, private static fields are `s_camelCase`, private `const` fields are `PascalCase` (no prefix), locals and parameters are `camelCase`, and local functions are `PascalCase`. All naming rules are severity **error** in `dotnet format`. No `this.`. Prefer `var`. Unused usings, members and parameters, and double blank lines, are **errors** in format (not in build).
- LF endings. `*.cs` files have no final newline.
- Amounts are always `LightningMoney`. Implicit `ulong/long → LightningMoney` is **msat**, so use `LightningMoney.Satoshis(...)`. Byte-backed value objects (`ChannelId`, `TxId`, `CompactPubKey`, `Hash`) convert implicitly to and from `byte[]`.
- Integers on the wire are big-endian. Existing code uses `src/NLightning.Infrastructure/Converters/EndianBitConverter.cs`. Prefer `BinaryPrimitives` for new code, because the LE trim/pad helpers are suspect.
- Tests use xUnit v3 + Moq, named `Given_X_When_Y_Then_Z` with Arrange/Act/Assert comments. Pass `TestContext.Current.CancellationToken`. Moq can't mock Span parameters, so use the Fake* + virtual byte[] pattern in `test/NLightning.Tests.Utils/Mocks`.
- `InternalsVisibleTo` is declared in `src/*/AssemblyInfo.cs` where one exists: only Application, Bolt11, Client, Daemon, Domain, Infrastructure, Infrastructure.Bitcoin and Infrastructure.Persistence have it. Domain lists `NLightning.Domain.Tests` and Daemon and Client list `NLightning.Daemon.Tests` since batch4 (NL-179, which also dropped Daemon's stale `NLightning.Bolts.Tests`); Application lists `NLightning.Application.Tests`. When a test needs internals, add an entry, or create `AssemblyInfo.cs` if the project lacks one.

## Non-obvious gotchas
- Byte-backed value objects (`TxId`, `ShortChannelId`, `ChannelId`, `Hash`, `ChainHash`, `Witness`, `BitcoinScript`, `Secret`, `PrivKey`, `CompactSignature`, ...) are `readonly struct`s with `implicit operator X(byte[])`, so in `cond ? x : null` (and switch expressions) the `null` arm binds through that operator: the conditional's natural type is `X`, not `X?`, whatever the target, and the null arm throws (`ArgumentNullException` from the ctor) at runtime. Write `(X?)null`, an if/else, or give the other arm a nullable type; `CompactPubKey` is immune because its implicit operator takes `ReadOnlySpan<byte>`, which a `null` literal cannot bind to. With `Nullable` enabled (every project) each instance is a CS8625 build warning, so never wave one of those away on these expressions (NL-369, also hit as NL-260 and NL-390).
- `UpdateAddHtlcPayload.OnionRoutingPacket` is a mandatory raw `ReadOnlyMemory<byte>` of exactly `OnionConstants.PacketLength` (1366) bytes (constructor and serializer enforce it; a short read throws). Parse it with `OnionPacket`. The update_add_htlc extension is read strictly (unknown even types rejected) and the blinded path uses `TlvConstants.BlindedPath`.
- Deserializers use `stream.Position/Length` to find trailing TLVs, so they need a seekable stream bounded to one message.
- `TlvStream` (`src/NLightning.Domain/Protocol/Models/TLVStream.cs`; note the file-name casing) is a `SortedDictionary`, so it silently re-sorts records. Every message extension is read with `DeserializeStrictAsync(stream, knownTypes)` (NL-001): add every TLV a message can carry to its serializer's known-type set, because an unlisted **even** type is rejected (the peer gets a `warning` and is disconnected); unlisted odd types are ignored. A malformed message answers with a connection `warning` and closes (NL-207). BigSize decoding is canonical.
- `TlvStreamSerializer.DeserializeAsync` enforces strictly increasing types and length <= remaining bytes but cannot reject unknown even types (no known-type set); use `DeserializeStrictAsync(stream, knownTypes)` where the namespace is known (new messages). Hop payloads use `IHopPayloadSerializer` instead, because `invalid_onion_payload` needs the offending type and offset, which the strict reader does not report.
- Some Domain TLVs (`FeeRangeTlv`) don't hold real wire bytes in `Value`. Always go through the converter. `FundingOutputContributionTlv` holds its wire bytes since wave sp1: it is an s64 in satoshis (`long Satoshis`, negative = splice-out; NL-476), and `tx_init_rbf`'s feerate and locktime are no longer swapped (NL-475). `RemoteAddressTlv.Value` holds the wire bytes since gossip wave G-A: it wraps one `Domain/Gossip/Addresses/AddressDescriptor` decoded by the strict `AddressDescriptorCodec` (NL-008); a malformed one is logged and dropped without failing init, and a valid one is kept only as `IPeerService.ObservedAddress` (our address as the peer sees it; NL-344 fixed).
- The signer loads channels itself (NL-067 first half, gossip wave G-A): `LocalLightningSigner` takes an `IChannelSigningInfoSource` and, on the first call for a channel it does not know, reads its signing data from the DB (`ChannelSigningInfoDbRepository`: keys, SCID, commitment number, data loss, S1 broadcast mark, announce flag; Closed/Stale channels are not loaded) and registers it. `RegisterChannel` with other keys or another funding outpoint throws `SignerException` before any guard moves. `ChannelManager` registers a channel by hand only when no `IChannelSigningInfoSource` is registered (source-less signers in in-process harnesses, re-registered at the funding confirmation for the real SCID; NL-343 fixed). `SignChannelAnnouncement` refuses channels without `AnnounceChannel`. `SignWalletTransaction` (NL-067 second half, wave O7) signs only wallet inputs held by an `IFeeInputSelector` reservation (pass the reservation id to bind it), checks the derived key against the UTXO's address and needs the other spent outputs for a P2TR input; reserve, sign, save the `BroadcastTransactions` row, then publish, and call `ConfirmAsync` again until the chain monitor has seen the spend. `SignLocalHtlcTransaction` signs input 0 of a combined anchors HTLC transaction (fee inputs after it).
- `ChannelModel.UpdateState` only allows strictly increasing `ChannelState` values, so number new states with that in mind (`Failed = 35` sits between Closing and Closed, `OnchainResolving = 37` between Failed and Closed). The HTLC state lives in the engine snapshot `ChannelModel.Commitments` (`ChannelCommitments`); balances, next ids and commitment numbers are read from it. The legacy `LocalOfferedHtlcs`/`RemoteOfferedHtlcs` collections are no longer persisted and are empty after a reload (NL-241). Change the snapshot only through the engine: per transition `IChannelStateDbRepository.ApplyAsync` + one `SaveChangesAsync`, then `ChannelModel.UpdateCommitments(next, extras)`, then send. Engine events (`CommitmentsResult.Events`) are replayed at startup with `ChannelDomainEvents.DerivePending`, so every consumer must be idempotent. `LocalBalance`/`RemoteBalance` are **gross** (they include the owner's pending offered HTLCs; NL-062).
- Splicing (wave sp1; `OptionSplice` Optional by default since D13; `src/NLightning.Domain/CLAUDE.md` and `src/NLightning.Application/CLAUDE.md` have the details): a channel can hold several fundings (`ChannelCommitments.PendingFundings`, table `ChannelFundings`); `ChannelModel.FundingOutput` and `LocalFundingPubKey`/`RemoteFundingPubKey` are the **current** funding (a splice rotates our funding key, `m/0'/i'`), so never read `LocalKeySet.FundingCompactPubKey` for the funding (NL-478 fixed the backup and announcement readers in wave sp2 and NL-495 `ChannelModel.GetSigningInfo` in wave spr, which also reports `ChannelModel.LocalFundingKeyIndex`). With a pending splice every `commitment_signed` goes out as `start_batch` + one per active funding (`ChannelStateTransitionService.SignPendingAsync`; `SignIfPendingAsync` then signs nothing and schedules `ICommitScheduler`) and inbound batches reach `IChannelManager.HandleCommitmentSignedBatchAsync`, grouped by `PeerManager` only when `option_splice` was negotiated. The splice's lock moves the funding columns and SCID (`IChannelFundingDbRepository.ApplyLockAsync`) and retires the old SCID in `IRetiredScidMap` for 72 blocks (never for an alias-only channel); hosts must await `IRetiredScidMap.LoadAsync(monitor.LastProcessedBlockHeight)` before `PeerManager.StartAsync` (the daemon and `NLightningTestNode` do, NL-487). Hosts also await `IBlockchainMonitor.LoadWalletAsync` (UTXO set, fee input reservations, last processed height) before `PeerManager.StartAsync`: a splice the peer resumes right after a restart signs our reserved wallet inputs before the chain monitor starts (NL-600). The revocation log is written per funding (NL-479); `RemoteCommit.SignedOnFundings` is persisted with the state machine's remote slots since migration `AddSpliceHardening` (NL-494). After a restart, pending splices with the peer's signatures are restored into the engine by `ChannelStateDbRepository.LoadAsync` and the `channel_reestablish` handler calls `SpliceService.EnsureLoadedAsync` to resume an unfinished splice negotiation from its rows (NL-484). Splice RBF (wave spr): every pending attempt is an RBF sibling in `FundingSet` (`AddRbfSibling`, at most `Splice:MaxRbfAttempts`), batches carry one `commitment_signed` per active funding, and a lock discards every sibling; any quiescence initiator may bump (`ISpliceService.BumpAsync`, the `tx_init_rbf` sender is the interactive-tx initiator), and a splice RBF always sends `funding_output_contribution`, 0 included (CLN fails the RBF without it, NL-503); the bumped attempt stays Pending and is rebroadcast until the lock. A peer that connects to us from a loopback address is saved as `PeerModel.IsInboundOnly` without an address (NL-497): its channels are registered at startup and it is never dialed at the loopback address (a dialable row saved before is kept and used), and channel backups and restores leave its row out.
- Normal-operation wiring (N6, `src/NLightning.Application/CLAUDE.md` has the details): receive handlers go through the scoped `ChannelStateTransitionService`; the send side is the singleton `ChannelOperationsService : IChannelOperations`, which publishes under the channel lock through `IChannelMessagePublisher` and schedules `CommitScheduler` after releasing it. Handlers queue domain events in the scoped `ChannelDomainEventQueue`, drained into `IHtlcSwitch` after the lock is released. Every send-side update and signature requires the channel's link (`IPeerLivenessProbe`, decorated by `ReestablishGatedLivenessProbe` and `LinkUpReplayingPeerLivenessProbe`): pinned to the connection the channel turned Open on, then re-marked by `MarkLinkUp` after each channel_reestablish, which also replays the channel's pending events into the switch. Normal-operation messages of a channel not yet reestablished on the current connection are dropped by `ChannelManager.Publish` (the reestablish retransmits them). `AddApplicationServices` registers `HtlcSwitch` (`AddHtlcSwitchServices`, replacing the `LocalOnlyHtlcSwitch` default) and then `PaymentService` (`AddPaymentSendServices`); keep that order. `IChannelOperations.OfferHtlcAsync` saves the `HtlcOrigin` in the add's save, and `FulfillHtlcAsync(..., stageWithFulfill, ct)` stages extra writes (the invoice settle) in the fulfill's save. HTLC messages and operations are refused unless `NodeOptions.HtlcsEnabled` (`Node:EnableHtlcs`; unset means on, on every network including mainnet since BOLT 5 O6-T4 (gossip wave G-D); `false` turns them off).
- Fee estimates: `IFeeService` is one shared singleton (`Infrastructure.Bitcoin/Services/AddFeeServices`, registered by `AddNltgNodeServices`; the Docker test node passes a fixed-rate handler); the instance the daemon starts is the one every consumer reads, and it never reports 0 (`FeeEstimation:FallbackFeeRatePerKw`, default 2500). `FeeEstimation:Source` is `Http` (value in `RateUnit`, default sat/vB), `Bitcoind` (`estimatesmartfee`) or `Fixed`; every rate goes through `FeeRateConverter` (sat/vB x 250, floored at BOLT 3's 253 sat/kw; the old `RateMultiplier` is ignored with a warning, NL-288). The last good estimate (rate, HTTP buckets, fetch time, source and a hash of the source settings) is saved to `FeeEstimation:CacheFile` (`<configPath>/fee_estimation_cache.bin`; empty = off, the library default; never for `Fixed`) by a background writer after each fetch (temp file + rename, 0600) and read when the service is built: at the start an estimate younger than `CacheExpiration` is used without waiting for a fetch, one younger than `CacheMaxAge` (default 1 h) replaces the fallback while the first fetch fails, and a stale, corrupt or other-source file is logged and ignored (NL-706). As fundee we accept any `open_channel` feerate from 253 sat/kw (NL-289); as funder we never offer a commitment feerate from the estimate below `Node:MinCommitmentFeeRatePerKw` (default 275, >= 253: `open_channel`, `open_channel2` and `update_fee`; an LDK peer refused 253, NL-564).
- Anchors reserve (wave O7b, NL-379): every channel funding goes through `IAnchorReserveService` (`AnchorReserveService.LockFundingUtxosAsync`, the 2-argument `LockUtxosToSpendOnChannel` is only the fallback when no service is registered), which keeps min(`Node:Anchors:ReservePerChannel` x anchors channels, `MaxReserve`) of confirmed P2WPKH/P2TR outputs (3 confirmations) free, counts admitted in-flight opens, adds the funding fee and skips outputs our pending `BroadcastTransactions` spend (NL-385); fee inputs (`IFeeInputSelector`) may spend the reserve. A fundee refuses an anchors channel it cannot back, so tests and Docker nodes that accept anchors opens must fund their wallet first; `walletbalance` shows the reserve.
- Onion messages (wave M6): forwards, replies and sends go through `IPeerOnionMessageOutbox` (`PeerManager`) into the peer's `PeerOutbox` onion class, capped by `OnionMessages:MaxOutboxPerPeer` (64) and never awaited; a full outbox drops (`dropped{reason=outbox_full}`), and we never connect to forward or reply (plan D6). The onion class never goes ahead of channel messages, warnings, errors or a disconnect, and takes one slot per 8 gossip sends. Invalid `OnionMessages` options keep the service off (logged) instead of failing peer connections. A malformed 513 is ignored (no warning, no close) and counted as `dropped{reason=malformed}` by `MessageService` on the shared onion message counter set (NL-444, NL-464 fixed). A null `byte[]` (or a bare `null` in a conditional with a `ReadOnlyMemory<byte>` arm) converts to an empty, non-null `ReadOnlyMemory<byte>?`, which encodes an empty `path_id`: assign the nullable only when the array is not null (NL-443).
- Quiescence and interactive-tx (wave qit, `src/NLightning.Application/CLAUDE.md` has the details): `stfu` has exactly one handler (`Channels/Handlers/StfuMessageHandler`, a registration test pins it) that delegates to the singleton `IQuiescenceService`; quiescence is memory-only and bound to the connection it started on. While a channel is quiescing or quiescent `IChannelOperations` refuses every update with `ChannelQuiescentException` (callers treat it like a link that is down; the switch's replay re-sends a refused fulfill after the end), `CommitScheduler` keeps signing the drain, and a peer's `update_*` after its `stfu` gets warning + close. The owed `stfu` is released after a transition's replies through `IStfuReleaseScheduler`, never inline in a handler (it must follow the `revoke_and_ack`). A timed-out quiescence keeps blocking updates until the disconnection. A probe we start (`RequestAsync(Probe)`) is ended with our `tx_abort` through `IInteractiveTxDriver.AbortQuiescence`. The interactive-tx driver runs one negotiation per channel under the channel lock, persists the `InteractiveTxSessions` row before our `commitment_signed` (persist, then memory, then send), never sends `tx_abort` after our `tx_signatures` (IT-ABT-01) and keeps the wallet reservation until an input is spent; `InteractiveTxSessions` has no FK to `Channels`, so whoever deletes or forgets a channel must call `DeleteByChannelIdAsync` (nothing does yet, NL-470).
