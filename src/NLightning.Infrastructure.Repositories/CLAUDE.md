# NLightning.Infrastructure.Repositories

This project implements the Domain repository ports: `IUnitOfWork`, the `I*DbRepository` interfaces backed by EF Core, and the two `I*MemoryRepository` singletons. It maps EF entities to Domain models and back by hand. The EF model, entities and migrations are in `../NLightning.Infrastructure.Persistence` (see persistence notes there).

## Layout
- `UnitOfWork.cs`: the scoped `IUnitOfWork` (interface: `src/NLightning.Domain/Persistence/Interfaces/IUnitOfWork.cs`). It creates each Db repo lazily over one `NLightningDbContext`, and has `GetPeersForStartupAsync` (every saved peer with its channels, plus an `IsInboundOnly` peer without an address for every non-Closed/Stale channel whose peer has no `Peers` row, so such a channel is registered at startup and never dialed, NL-497), `AddUtxo`/`TrySpendUtxo` (DB now, memory after a successful save) and `SaveChanges(Async)`.
- `Database/BaseDbRepository.cs`: generic `Get` / `GetByIdAsync(object id)` / `Insert` / `Update` / `Delete*`. Reads use AsNoTracking by default. `Update` is tracking-aware.
- `Database/Helpers/PrimaryKeyHelper.cs`: builds the PK predicate. Pass composite keys as a **ValueTuple, in key order**.
- `Database/Bitcoin/`: BlockchainState, Utxo, WalletAddresses (`GetUnusedAddressAsync` never returns an address that is `IsReserved`, holds a UTXO or lies below the highest reserved or funded address of its type and chain, NL-280: spending deletes the UTXO row, so the monotonic rule keeps legacy spent addresses from coming back), WatchedTransaction (the RevocationWatch stub was deleted, NL-095), and `FeeInputReservationDbRepository` (`IUnitOfWork.FeeInputReservationDbRepository`, port `Domain/Bitcoin/Interfaces/IFeeInputReservationDbRepository`, migration `AddFeeInputReservations`, BOLT 5 plan O7-T1): staged `Add(reservation, createdAt)` (one input row per outpoint: an outpoint already reserved fails the save on the key), `DeleteAsync(id)` (staged, with its input rows), `GetByIdAsync`, `GetAllAsync` (oldest first) and `GetReservedOutpointsAsync` (startup load); used by `Infrastructure.Bitcoin/Wallet/FeeInputSelector`.
- `Memory/UtxoMemoryRepository` (NL-379, NL-385): the six-argument `LockUtxosToSpendOnChannel(amount, channelId, reserveToKeep, excludedOutpoints, fundingFeeRatePerKw, height)` selects P2WPKH/P2TR outputs not in `excludedOutpoints` (outputs our pending broadcasts spend) for the amount plus the funding transaction's worst-case fee (`FundingFeeEstimator`, re-selected until the input count it was estimated for suffices), and throws `AnchorReserveException` when the outputs left that back the reserve (`UtxoModel.BacksAnchorReserve`: mined, known P2WPKH/P2TR address, three-block rule) plus the funding's least change (after the fee with a P2TR change output; none below 330 sat) would not cover `reserveToKeep`, all under `_reservationLock`; `GetAvailableConfirmedBalance` is the balance of the unlocked, unreserved, non-excluded outputs that back the reserve.
- `Database/Channel/`: Channel (channel row, config, key sets, aliases; attaches the commitment snapshot on reload), ChannelConfig (maps `ChannelParams`: `Local*`/`Remote*` columns per `ChannelParty` field; a default party's null amounts are written as 0), ChannelKeySet, ChannelState, RemoteShachain. `ChannelStateDbRepository` (`IUnitOfWork.ChannelStateDbRepository`, BOLT2 N5-T2) persists the engine: `InitializeAsync(snapshot)` stages everything, `ApplyAsync(next, transition, extras)` stages what `ChannelTransition` says changed (upserted and settled HTLCs are upserted by PK, settled ones stay as an archive with their final state until `PruneSettledHtlcsAsync`; dropped HTLCs are deleted; fee updates and commitment slots are synced when flagged; the channel scalars, `SentCommitDiff` (cleared when there is no unacked remote commitment), `LastSentOrder` and the shachain from `ChannelStateExtras` are written every time), `LoadAsync(channelId, CommitmentParams)` restores via `ChannelCommitments.Restore` and refuses legacy HTLC rows (NL-025). Nothing saves: the caller does one `SaveChangesAsync` per transition. `CommitmentStateEncoding` holds the blob formats. The legacy `HtlcDbRepository`/`IHtlcDbRepository` were removed. `RemoteShachainDbRepository` (`IUnitOfWork.RemoteShachainDbRepository`, NL-136) stores the peer's shachain as up to 49 `(ChannelId, Bucket)` rows: `SaveAsync(channelId, ISecretStorageService.Export())` upserts by bucket and removes absent buckets (staged, commit with the uow; calling it several times before `SaveChangesAsync` is safe because it merges `DbSet.Local`), `GetByChannelIdAsync` returns `ShachainEntry`s for `ISecretStorageService.Load`. It is not part of the `ChannelDbRepository` graph (no navigation on `ChannelEntity`); rows cascade on channel delete.
- `ChannelStateDbRepository` maps a removal's `attribution_data`/`fulfillment_payload` (`HtlcRemoval.AttributionData`/`FulfillmentPayload`, NL-326) to `Htlcs.AttributionData`/`FulfillmentPayload` (empty = null), and stamps `Htlcs.AddedAt` once, when it inserts a row, from the `TimeProvider` it is built with (`UnitOfWork` passes its optional `TimeProvider`, default `TimeProvider.System`); `GetHtlcAddedAtAsync` reads it through the change tracker (null for rows from before `AddAttributionData`). `PaymentDbRepository` writes `PaymentHop.HoldTime` as `PaymentHops.HoldTimeMs` on `AddAsync` and, since the route is otherwise fixed, `UpdateAsync` updates only the hop rows' hold times.
- `ChannelStateDbRepository` also holds the `HtlcOrigin` of HTLCs we offer (ONION M4-T7): `SetHtlcOriginAsync(channelId, key, origin)` after `ApplyAsync` staged the add, in the same unit of work (the row may be only staged; `FindAsync` sees it), `GetHtlcOriginAsync`, and `FindHtlcsByOriginAsync(origin)` (startup replay: which channel HTLCs carry this payment hash / this forwarded incoming HTLC; archived final rows included until pruned). `ApplyAsync` never overwrites the origin or the onion shared secret. `WriteScalars` stores `next.Params.MaxDustHtlcExposureMsat` on the channel row (NL-242).
- `Database/Payment/` (ABCD W1-C): `InvoiceDbRepository`, `PaymentDbRepository`, `ForwardCircuitDbRepository` implement the Domain ports `IInvoiceDbRepository`/`IPaymentDbRepository`/`IForwardCircuitDbRepository` (`IUnitOfWork.InvoiceDbRepository`/`PaymentDbRepository`/`ForwardCircuitDbRepository`). Writes are staged; single-key reads (`GetByPaymentHashAsync`, `GetByIncomingAsync`, `GetByOutgoingAsync`) go through the change tracker and see what this unit of work staged, list/replay reads (`ListAsync` newest first then by hash, `GetInFlightAsync`/`GetUnresolvedAsync` oldest first) read what is saved. `AddAsync` throws `InvalidOperationException` for an existing key, except `PaymentDbRepository.AddAsync` over a `Failed` payment, which replaces the row and syncs its `PaymentHops` by hop index (never delete + re-add under one key); `UpdateAsync` of an unknown key throws. Payment routes (`PaymentModel.Route`, `PaymentHop` with each hop's Sphinx shared secret) are written only by `AddAsync`.
- `ChannelDbRepository` column ownership: `UpdateAsync` never writes `RemoteNextPerCommitmentPoint`, `SentCommitDiff`, `LastSentOrder`, `MaxDustHtlcExposureMsat`, `RevocationLogFromNumber` (set by the migration only), and, once the channel has a snapshot (held by `ChannelModel.Commitments`, staged in this unit of work by `InitializeAsync`/`ApplyAsync`, or stored), not the balances, next HTLC ids, commitment and revocation numbers either (a stale model, including one that predates its first snapshot, must not roll a saved transition back). `AddAsync` also stages the snapshot when the model has one. Reads map channels one at a time (one query per channel for the state; no concurrent use of the context).
- Legacy HTLC rows (NL-025) throw `LegacyHtlcStateException` (an `InvalidOperationException`) from `ChannelStateDbRepository.LoadAsync` and `ChannelDbRepository.GetByIdAsync`; the multi-channel reads (`GetAllAsync`, `GetReadyChannelsAsync`, `GetByPeerIdAsync`, so `UnitOfWork.GetPeersForStartupAsync`) log that channel and leave it out, so one legacy channel never blocks the others.
- Reload params: `ChannelDbRepository` restores a snapshot with `CommitmentParams.FromChannel(model, stored MaxDustHtlcExposureMsat)`, so it keeps the dust policy it was saved with (NL-242) and `HasInferredLimits` of a channel migrated by `SplitChannelParams` (the removed `ChannelModel.ToCommitmentParams()` dropped both; create first snapshots with `FromChannel` too). `ChannelStateDbRepository.LoadAsync` uses the params it is given as they are. Follow-up for the wiring (W2-B): nothing calls `PruneSettledHtlcsAsync` yet, so settled HTLC rows accumulate and every channel load reads them all (NL-243); use `IChannelDbRepository.ExistsAsync` (one `ANY` query, never throws for legacy rows) instead of `GetByIdAsync` as an existence check. Startup replay (W2-B/W2-C): `FindHtlcsByOriginAsync(Local(hash))` also returns the archived HTLCs of earlier failed attempts, since a retry replaces a `Failed` payment under the same hash; count only a non-final row, or the one matching the payment's `OutgoingChannelId`/`OutgoingHtlcId`, before deciding an `InFlight` payment has an HTLC.
- `Database/Payment/OfferDbRepository` (`IUnitOfWork.OfferDbRepository`, port `Domain/Offers/Interfaces/IOfferDbRepository`, migration `AddBolt12Offers`, NL-447): staged `AddAsync` (an existing id throws) and `UpdateAsync` (status and disable time only), `GetByIdAsync` and `GetByOfferBytesAsync` (by primary key: the id is SHA256 of the bytes, which must then match exactly; through the change tracker), `ListAsync(activeOnly, skip, take)` newest first, and the saved-row counts `GetInvoiceCountsAsync(offerId, now)` (settled, and unpaid, BOLT 12 invoices of the offer) and `CountUnpaidInvoicesAsync(now)` (unpaid BOLT 12 invoices of every offer). Unpaid = `Accepted` (an HTLC set is held, expired or not) plus `Open` and unexpired. Both are counted in SQL: `CreatedAt + ExpirySeconds` does not translate over the ticks converter, so the open rows are counted once per distinct `ExpirySeconds` with the bound `CreatedAt > now - ExpirySeconds` (exact in ticks). `InvoiceDbRepository.PruneExpiredBolt12InvoicesAsync(now, max)` stages the deletion of at most `max` `Open` BOLT 12 invoices expired at `now` (same per-expiry bound), oldest expiry first, skipping rows this unit of work already moved out of `Open`; BOLT 11 rows are never pruned (entry point for the BOLT 12 expiry sweep, plan §3.7 step 6). `InvoiceDbRepository` maps `InvoiceModel.Bolt12` (`Bolt12InvoiceDetails`) to the `Invoices` BOLT 12 columns on `AddAsync` only and refuses to load a `Kind` 1 row without its offer, bytes or payer id; `PaymentDbRepository` maps `PaymentModel.Bolt12` (`Bolt12PaymentDetails`, present when `OfferBolt12` is set) on `AddAsync`, including a replacement of a failed payment. The `IUnitOfWork.OfferDbRepository` default member throws `NotSupportedException` for test doubles that store no offers (`CrashingUnitOfWork` and `ThreeNodeHarness.HookedUnitOfWork` forward it; the prune is also a throwing default member of `IInvoiceDbRepository`, forwarded by `HookedInvoiceRepository` and implemented by the Application tests' `InMemoryInvoiceDbRepository`).
- `Database/Onchain/` (BOLT 5 plan O0): `WatchedOutpointDbRepository` (`IUnitOfWork.WatchedOutpointDbRepository`: `Add`, `GetAsync`, `GetActiveAsync` = every watch except those of a Closed/Stale channel, `MarkSpentAsync` (no-op without a row), `ClearSpendsAboveAsync(height)` for reorgs, `AddFundingOutpointIfMissingAsync(channelId, fundingTxId)` (reads the channel row's funding index; used by the monitor when a watched funding tx is first seen, so the fundee's funding output is watched too) and `AddMissingFundingOutpointsAsync` (startup backfill for channels past funding_created that are not Closed/Stale)), `BroadcastTransactionDbRepository` (`Add`, `GetByTransactionIdAsync`, `GetByChannelIdAsync` oldest first, `GetPendingAsync` oldest first, `MarkConfirmedAsync`, `MarkAbandonedAsync` (pending only; the on-chain watcher gives our commitment up when the peer's won the funding output, the chain monitor a funding or wallet send refused for good, NL-294), `GetAbandonedAsync` (oldest first, read by `pendingsweeps`; a default interface member returning none for test doubles), `UnconfirmAboveAsync(height)`; `CommitmentNumber` of a `LocalCommitment` row round-trips, ABCD W5) and `BlockHeaderDbRepository` (`AddOrReplaceAsync`, `GetAllAsync` lowest first, `DeleteAboveAsync`, `DeleteBelowAsync`). Their writes go through tracked entities (never `ExecuteUpdate`), so a rollback is atomic with the rest of the unit of work. The Domain ports are in `src/NLightning.Domain/Onchain/Interfaces/`. `WatchedTransactionDbRepository` gained the reorg helpers `ResetPendingFirstSeenAboveAsync`/`GetCompletedFirstSeenAboveAsync`, and its `Update` no longer overwrites `CreatedAt`.
- BOLT 5 plan O1: `Database/Channel/RevokedCommitmentDbRepository` (`IUnitOfWork.RevokedCommitmentDbRepository`, port `Domain/Onchain/Interfaces/IRevokedCommitmentDbRepository`: `GetAsync(channelId, number)`, `GetByChannelIdAsync` by number, `GetLogStartAsync` (`Channels.RevocationLogFromNumber ?? 0`), `DeleteByChannelIdAsync`). Rows are staged only by `ChannelStateDbRepository.ApplyAsync` when `ChannelTransition.RevokedRemoteCommit` is set and has HTLCs (internal `StageAsync`, idempotent for a replayed transition), so the log row, the RAA's scalars and its shachain entry commit in one save. `Database/Onchain/OnchainResolutionDbRepository` (`IUnitOfWork.OnchainResolutionDbRepository`: `UpsertCloseAsync`/`GetCloseAsync`/`GetClosesAsync`/`DeleteCloseAsync` for `ChannelCloseModel`, `UpsertOutputAsync`/`GetOutputAsync`/`GetOutputsByChannelIdAsync`/`GetUnresolvedOutputsAsync` (not Irrevocable, not Ignored) for `OutputResolutionModel`; key reads go through the change tracker, list reads read what is saved).
- `Database/Gossip/GraphDbRepository` (`IUnitOfWork.GraphDbRepository`, port `Domain/Gossip/Interfaces/IGraphDbRepository`, migration `AddGossipGraph`, BOLT 7 plan G2-T3): nodes, channels, per-direction policies and bans as the Domain records in `Domain/Gossip/Persistence/` (`GraphNodeRecord`, `GraphChannelRecord`, `GraphPolicyRecord`, `GraphBannedNodeRecord`; raw signed payloads kept byte-exact). Upserts replace every column (a channel upsert keeps its policies; `GraphChannelRecord.FundingTxId`, nullable, since migration `AddGraphFundingTxId`, NL-352), `MarkChannelSpentAsync`, `ClearSpentAboveAsync` (reorg), `GetChannelsSpentAtOrBelowAsync` (pruner), `DeleteChannelAsync` (with its policies), `DeleteExpiredBansAsync`; writes go through tracked entities (staged), key reads through the change tracker (a row this unit of work deleted reads as absent; an upsert revives it), list reads read what is saved. A policy needs its channel (FK, the save fails otherwise). Bulk members (BOLT 7 plan G5-T3, default interface methods on the port that loop over the single-row ones, so test doubles need nothing): `UpsertChannelsAsync`/`UpsertPoliciesAsync`/`UpsertNodesAsync` and `DeleteChannelsAsync`/`DeleteNodesAsync` stage exactly what the single-row calls stage (tracked rows first, a row this unit of work deleted revived, then one tracking query per `KeysPerQuery` = 500 keys: EF 10 sends each key as its own parameter, SQL Server allows 2,100), and `StreamChannelsAsync`/`StreamPoliciesAsync`/`StreamNodesAsync` stream the tables without tracking (the store's startup load). Tests: `Integration.Tests/Persistence/GraphDbRepositoryBulkTests` (SQLite: bulk equals single-row, replace, staged/deleted rows of the same unit of work, cascade, streams) and the bulk section of `GossipGraphSchemaRoundTrip` (also run by the Docker Postgres/SQL Server tests; Postgres green).
- `Database/Channel/InteractiveTxSessionDbRepository` (`IUnitOfWork.InteractiveTxSessionDbRepository`, port `Domain/Protocol/InteractiveTx/Interfaces/IInteractiveTxSessionDbRepository`, migration `AddInteractiveTxSessions`, splicing plan IT3-T2): staged `Add` (a duplicate key fails the save), `UpdateAsync` (every column but the key and `CreatedAt`; `KeyNotFoundException` for an unknown or deleted row), `GetByIdAsync` and `DeleteAsync` through the change tracker (they see what this unit of work staged), `GetByChannelIdAsync` and `GetUnresolvedAsync` (`ResolvedAt` null and not `Aborted`) oldest first by `CreatedAt` then `SessionId`, over saved rows (ordered in memory: EF SQLite cannot order `DateTimeOffset`). `InteractiveTxSessionEncoding` holds the blob formats (version byte 1, big-endian integers, u32-length byte strings, presence bytes, msat amounts); a decoder throws `InvalidOperationException` for an unknown version or enum value, a truncated blob or trailing bytes, and `Map` does the same for an unknown `Purpose`/`State`. The contribution's reservation id is its own column (`LocalReservationId`), not part of the blob. The table has no FK to `Channels` (a dual-funded open may save its negotiation before its channel row), so rows outlive a forgotten or deleted channel: whoever forgets or deletes a channel calls `DeleteByChannelIdAsync` (saved and staged rows of the channel, returns the count) in the same save, and the startup/reestablish driver (lane IT-D) must skip or resolve a session from `GetUnresolvedAsync` whose channel is unknown instead of resuming it or keeping its `LocalReservationId`. `WriteBytes` throws `ArgumentException` for a null byte string (a `default` value object such as `default(Witness)`), so `Add`/`UpdateAsync` stage nothing. `CrashingUnitOfWork` forwards the property; `ThreeNodeHarness.HookedUnitOfWork` (Application.Tests) does not yet (it gets the interface's throwing default).
- `Database/Channel/ChannelSigningInfoDbRepository` (`IUnitOfWork.ChannelSigningInfoDbRepository`, port `Domain/Channels/Interfaces/IChannelSigningInfoDbRepository`, NL-067): the signer's `ChannelSigningInfo` straight from the channel row, both key sets (key index, funding keys, the peer's htlc basepoint) and the lowest `CommitmentNumber` of the channel's `LocalCommitment` broadcast rows, plus `RemoteNodeId`, the real `ShortChannelId`, `LocalCommitmentNumber`, `DataLossDetected` and `AnnounceChannel` (from the config row); every state except Closed and Stale (those return null, so the signer keeps refusing them after a restart), never refused for legacy HTLC rows; `FundingSatoshis` is filled in **msat** as `ChannelModel.GetSigningInfo` does. `Database/Channel/ChannelSigningInfoSource` is the singleton `IChannelSigningInfoSource` (registered by `AddRepositoriesInfrastructureServices`) the signer loads unregistered channels through: one scope per lookup, the async read waited on the thread pool.
- Splicing (migration `AddSpliceFundings`, lane SP1-C): `Database/Channel/ChannelFundingDbRepository` (`IUnitOfWork.ChannelFundingDbRepository`, port `Domain/Channels/Interfaces/IChannelFundingDbRepository`): staged funding rows (tracked, `GetEntitiesAsync` merges the change tracker's added rows and skips deleted ones, ordered by `Sequence`), `ApplyLockAsync` (the lock's save: retired fundings staged and their commitment slots removed, the channel row's current funding columns moved, the new current staged last), the pending fundings' commitment slots through `ChannelStateDbRepository`'s internal `UpsertCommitmentAsync`/`SyncRemoteNextAsync`/`FindCommitmentAsync` (now keyed by funding txid; the current funding's slots are refused), `StageRevokedCommitmentAsync` (`RevokedCommitmentDbRepository.StageAsync(channelId, revoked, fundingTxId)`), and the dual-funding columns. Wave sp2 (lane SP2-C, NL-479, SP-I2): `ChannelStateDbRepository.ApplyAsync` logs a revoked number once per funding it was signed on (`ChannelTransition.RevokedRemoteCommitFundings`, each with `ChannelCommitments.SpecFor(revoked.Spec, funding)`, the current funding's row as before) and, while `ChannelCommitments.PendingFundings` is not empty, writes every pending funding's slots the transition changed (local with `LocalCommit.SignaturesFor`, remote current when it was signed on that funding (keeping the stored sent signatures while the number is unchanged), remote next with `RemoteNextCommit.SignaturesFor` or removed), for fundings that have a `ChannelFundings` row; `RevokedCommitmentModel.FundingTxId` is filled on every read and `GetByFundingAsync(channelId, fundingTxId)` lists one funding's log (staged rows included) for the on-chain side. Tests: `Integration.Tests/Persistence/RevokedCommitmentPerFundingTests`. `ChannelStateDbRepository` reads and writes only the slots of `Channels.FundingTxId` (read from the tracked channel row, so a lock staged earlier in the same unit of work moves the state machine too); `RevokedCommitmentDbRepository.GetAsync(channelId, fundingTxId, n)` reads the row of the funding a breach spends (pass the spent outpoint's txid); `GetAsync(channelId, n)` prefers the current funding's row, else the funding created first (`ChannelFundings.Sequence`), and `GetByChannelIdAsync` lists a number once per funding. `ChannelDbRepository`: `AddAsync`/`UpdateAsync` stage the Current/Initial funding row once the funding outpoint is known (funding keys from the key sets, as the migration's data step) and keep it in step (outpoint, capacity, keys, SCID) while it is still the Current funding, whatever pending or discarded splices sit beside it; once a splice was locked (a Current non-initial row or any Replaced row) `UpdateAsync` leaves the current funding columns and SCID alone (a stale model never undoes a lock), and it never writes the dual-funding columns; reloads take the current funding's keys from its row only once it is a splice (our key rotates per splice); the initial funding's keys stay the key sets' (a FundingOutput whose keys differ from the key sets once broke restarts in the lane). `ChannelSigningInfoDbRepository` fills `LocalFundingKeyIndex` and the funding keys from the current funding row when it is a splice (else the key sets and 0), `Fundings` with the others and `PersistedSpliceCommitments` from the pending fundings' local slots that carry the peer's signatures (SP-I1 across restarts). `Database/Channel/ChannelPolicyDbRepository` (`IUnitOfWork.ChannelPolicyDbRepository`, table `ChannelPolicies`): `GetAsync` through the change tracker, `GetAllAsync` saved rows, staged `UpsertAsync` (replaces every value; a default `UpdatedAt` is stamped from the unit of work's `TimeProvider`) and `DeleteAsync`. `CrashingUnitOfWork` and `ThreeNodeHarness.HookedUnitOfWork` (since the wave sp1 integration, d778d100) forward both properties.
- `Database/Node/PeerDbRepository.cs`; `Database/Node/PeerStorageDbRepository.cs` (`IUnitOfWork.PeerStorageDbRepository`, port `Domain/Node/PeerStorage/IPeerStorageDbRepository`, table `PeerStorageBlobs`, wave rf1): `GetAsync`, `GetAllAsync`, staged `UpsertAsync` (one row per peer, through the change tracker) and `DeleteAsync`
- `Memory/ChannelMemoryRepository.cs`: live channels and temp channels (keyed by `(peerPubKey, tempChannelId)`). Raises `OnChannelUpgraded` / `OnChannelUpdated`. A temp channel expires after `TemporaryChannelTimeout` (default 10 min, optional `TimeProvider` in the ctor): the lookups no longer find it and every `AddTemporaryChannel` drops the expired ones; `RemoveTemporaryChannels(peer)` forgets a peer's opens, called by `PeerManager` when its connection ends (NL-392).
- `Memory/UtxoMemoryRepository.cs`: the UTXO set, balances (confirmed means `BlockHeight + 3 <= currentBlockHeight`, hard-coded), and Branch-and-Bound coin selection with a greedy fallback. Fee reservations (O7-T1) are kept by outpoint apart from the `UtxoModel`s (so a reorg's remove and re-add keeps them): `TryReserveForFee` (all or nothing; refuses an unknown, channel-locked or reserved outpoint), `ReleaseFeeReservation`, `TryGetFeeReservation`, `GetUnreservedUtxos`, `LoadFeeReservations`; one lock serializes them with `LockUtxosToSpendOnChannel`, which skips reserved outputs; `GetLockedBalance` counts reserved outputs too.
- `DependencyInjection.cs`: `AddRepositoriesInfrastructureServices()` registers `IUnitOfWork` (scoped) and the memory repos (singleton). Individual Db repos are **not** registered in DI (resolve them through `IUnitOfWork`), except the three payment repositories (`IInvoiceDbRepository`, `IPaymentDbRepository`, `IForwardCircuitDbRepository`), registered Scoped as the scope's `IUnitOfWork` properties so they share its DbContext and its save (the payment core resolves `IInvoiceDbRepository` from a scope).

## Dependency rules
- It references only `NLightning.Domain` and `NLightning.Infrastructure.Persistence` (see the csproj). Do NOT add references to Application, Infrastructure, Infrastructure.Bitcoin, Serialization or Daemon. Get hashing (and, if ever needed, serialization) through Domain abstractions (`ISha256`, `IMessageSerializer`); UnitOfWork receives `ISha256` by injection.
- Entity constructors are `internal`. InternalsVisibleTo lives in `src/NLightning.Infrastructure.Persistence/AssemblyInfo.cs`.
- Never expose EF entities outside this project. Return Domain models only.

## Adding a Db repository (common task)
1. If the table is new, add the entity, the `Configure<Name>Entity` config, the DbSet in `NLightningDbContext`, and migrations for all 3 providers. That all happens in the Persistence project (`scripts/add_migration.sh`).
2. Add `I<Name>DbRepository` in `src/NLightning.Domain/<Area>/Interfaces/`.
3. Add `Database/<Area>/<Name>DbRepository.cs : BaseDbRepository<<Name>Entity>, I<Name>DbRepository`, with static `MapDomainToEntity` / `MapEntityToDomain`. Make a mapper `internal static` if other repos reuse it, as `ChannelDbRepository` does with the config and key set mappers.
4. Add a lazy property to `IUnitOfWork` and `UnitOfWork`.
5. Callers resolve `IUnitOfWork` from a scope (`IServiceScopeFactory.CreateScope()`) and must call `SaveChangesAsync()`. Nothing is written without it.
6. Update the `IUnitOfWork` mocks (and `test/NLightning.Tests.Utils/Mocks/CrashingUnitOfWork.cs`) if the interface changed: `test/NLightning.Application.Tests` (`Channels/Handlers/FundingCreatedMessageHandlerTests.cs`, `Node/Managers/PeerManagerTests.cs`) and `test/NLightning.Infrastructure.Bitcoin.Tests/Wallet/BlockchainMonitorServiceTests.cs`. `CrashingUnitOfWork` and `ThreeNodeHarness.HookedUnitOfWork` (`test/NLightning.Application.Tests/Channels/Harness/`) forward every `IUnitOfWork` property, including `RevokedCommitmentDbRepository`, `OnchainResolutionDbRepository` (BOLT 5 plan O1) and `PeerStorageDbRepository` (wave rf1), so add a new property there too.

## Conventions
- Most files: System.*/Microsoft.* usings, then the file-scoped namespace, then relative `using Domain.X;` / `using Persistence.X;` below it. Follow the majority style in new files.
- Channel/HTLC enums (`State`, `Version`, `Direction`) are stored as `byte` on entities; `UtxoEntity.AddressType` is the enum type itself. Money types vary: `FundingAmountSatoshis` and `UtxoEntity.AmountSats` are `long`, `HtlcEntity.AmountMsat` is `ulong`, `ChannelEntity.Local/RemoteBalanceMsat` are `long` msat (NL-191). `ChannelModel.ShortChannelId` maps to a nullable column: a default (unconfirmed) scid has no bytes and is written as null. Check the entity before mapping.
- Writes build a fresh detached entity from the Domain model, then call Insert or Update. There are no explicit transactions.

## Known bugs / gotchas (verify before relying on these paths)
- `State`/`Direction` are raw `byte` on entities: compare with `== (byte)HtlcState.X`, never `.Equals(HtlcState.X)` (a boxed enum never equals a byte). This was the NL-125 HTLC-reload bug, now fixed.
- On reload, `CommitmentNumber` must be built as (opener, accepter) payment basepoints, ordered by `IsInitiator` (BOLT 3 obscuring factor; NL-127 fixed).
- `ChannelEntity.LocalCommitmentNumber`/`RemoteCommitmentNumber` are persisted on their own (migration `PersistCommitmentNumbers`, which filled existing rows from the revocation numbers). Never rebuild them from `LocalRevocationNumber`/`RemoteRevocationNumber`: mid-dance the local commitment number runs one ahead of the revocations, and the signer's revocation guard reads it after a restart (NL-188).
- `ChannelModel.ChangeAddress` is persisted through the convention FK (`ChangeAddressIndex` + shadow `ChangeAddressIsChange`/`ChangeAddressAddressType`), which `ChannelDbRepository.SetChangeAddressForeignKey` sets via the change tracker; reads `Include(c => c.ChangeAddress)`. The referenced `WalletAddresses` row must already exist (FK). If NL-134 makes the FK explicit, that helper keeps working because it reads the FK metadata.
- `UnitOfWork.AddUtxo`/`TrySpendUtxo` only stage the DB change; `IUtxoMemoryRepository` is updated after `SaveChanges(Async)` succeeds (NL-133). Until then the utxo is not visible in memory (balances, coin selection). `TrySpendUtxo` also finds utxos added earlier in the same unit of work, and `UtxoDbRepository.Spend` cancels a still-pending insert instead of deleting.
- `ChannelMemoryRepository.TryGetChannel` returns the shared mutable model. Call `UpdateChannel` afterwards so that `OnChannelUpdated` fires.
- Do not inject `IUnitOfWork` into singletons. `UnitOfWork.Dispose` disposes the DbContext.

## Onion routing (BOLT 4) hooks
- The onion packet persists raw in `HtlcEntity.OnionRoutingPacket`; the per-HTLC shared secret in `HtlcEntity.OnionSharedSecret` (`IChannelStateDbRepository.SetOnionSharedSecretAsync`/`GetOnionSharedSecretAsync`).
- Forward circuits, invoices, payments (with per-hop shared secrets) and HTLC origins are persisted (`Database/Payment/`, `ChannelStateDbRepository` origin methods). The onion replay set is `Database/Payment/OnionReplayDbRepository` (`IUnitOfWork.OnionReplayDbRepository`, NL-078: `GetByHmacAsync`, staged `Add`, `DeleteExpiredAsync(height)` runs at once with `ExecuteDeleteAsync`, `CountAsync`), used by Infrastructure's `PersistentOnionReplayStore`. Still missing: failure reasons and a lookup from scid/alias to ChannelId (likely via `IChannelMemoryRepository`).
- In-flight HTLCs round-trip through `ChannelStateDbRepository`; HTLC signatures live on the commitment rows.
- `ChannelStateDbRepository` stores `RemoteCommit.SignedOnFundings` of the state machine's remote slots (current and unacked, never a pending funding's slots) in `Commitments.SignedOnFundings` (NL-494, migration `AddSpliceHardening`; `CommitmentStateEncoding.EncodeSignedOnFundings`: per funding the txid and the engine's local/remote balance deltas, 48 bytes, big-endian). `LoadAsync` reads every `ChannelFundings` row of the channel (any status) and restores the list through `RemoteCommit.WithSignedOnFundings` plus the stored deltas (`RestoreSignedOnFundings`); a stored txid without a funding row leaves the list null (the engine then falls back to the pending fundings, as before). `ChannelDbRepository` sets `ChannelModel.LocalFundingKeyIndex` from the current funding's row on every reload (NL-495). `PeerDbRepository` maps `PeerModel.IsInboundOnly` (NL-497).
