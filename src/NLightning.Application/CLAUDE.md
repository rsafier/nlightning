# NLightning.Application — agent guide

Orchestration layer. It sits between the peer/transport layer (Infrastructure) and the domain plus crypto (Domain, Infrastructure.Bitcoin), and holds:
- PeerManager: the peer table, connect/accept, routing channel messages.
- ChannelManager: dispatches channel messages and reacts to blockchain events.
- The BOLT 2 v1 channel-open handlers and the BOLT 2 normal-operation receive handlers (update_add/fulfill/fail/fail_malformed_htlc, commitment_signed, revoke_and_ack, update_fee; BOLT2 plan N6-T1).
- MessageFactory: builds outbound protocol messages (Infrastructure's `PeerCommunicationService` still constructs error/warning messages directly).
- The send side (BOLT2 plan N6-T2): `IChannelOperations` (`ChannelOperationsService`), the commit scheduler and the `LocalOnlyHtlcSwitch`, which fails every incoming HTLC back once it is locked in (no invoices or forwarding yet).

Not implemented yet: channel_reestablish (N7), final-hop receive and forwarding (ABCD W2), shutdown/close (N10).

The payment core (ABCD W1-B) lives in `Payments/`: incoming onion processing, final hop, forwarding policy, route and onion building for our payments, and invoices. The send path (`Payments/Send/PaymentService`, ABCD W2-C) uses it and offers our HTLCs through `IChannelOperations`; the forwarding/final-hop switch that calls the rest is W2-B. See "Payments" below.

## Layout
- `DependencyInjection.cs`: `AddApplicationServices()`. Registers the Domain services that have no DI of their own (IChannelOpenValidator, IChannelFactory, ICommitmentTransactionModelFactory, IFundingTransactionModelFactory; they need the host's IFeeService and AddBitcoinInfrastructure's ILightningSigner) and IChannelLockProvider, `ChannelManager` (built by a factory lambda, then exposed as both `IChannelManager` and `IChannelMessagePublisher`: one instance), IMessageFactory and IPeerManager as singletons, plus `AddCommitmentEngineServices()`, `AddChannelStateTransitionServices()` and `AddChannelOperationsServices()` (all in `Channels/Services/CommitmentEngineServiceCollectionExtensions.cs`), `Gossip.AddGossipServices()` and `Payments.AddPaymentsServices()`. A reflection scan registers every `IChannelMessageHandler<>` as Scoped. `FundingConfirmedMessageHandler` is registered as a concrete Scoped type. It is called from `src/NLightning.Daemon/Extensions/NodeServiceExtensions.cs`.
- `Channels/Handlers/Interfaces/IChannelMessageHandler.cs`: `Task<IReadOnlyList<IChannelMessage>> HandleAsync(msg, ChannelState currentState, FeatureOptions negotiatedFeatures, CompactPubKey peerPubKey)`. The returned messages are sent back to the same peer in list order (e.g. revoke_and_ack before commitment_signed); return `[]` for none.
- `Channels/Services/ChannelLockProvider.cs`: `IChannelLockProvider` (Domain) singleton, one non-reentrant `SemaphoreSlim` per channel id, dropped when unused. `AcquireAsync` / blocking `Acquire` return an `IDisposable`.
- `Channels/Handlers/`:
  - `OpenChannel1MessageHandler`: we are the non-initiator. Receives open_channel, replies accept_channel with **our** values (`ChannelParams.Local`, never the opener's; NL-194) and the opener's `channel_type` echoed byte for byte (BOLT 2, NL-218).
  - `AcceptChannel1MessageHandler`: we are the initiator. Receives accept_channel, fails it if `channel_type` differs from the one we sent (`ChannelParams.ToChannelType()`) or a reserve is below the other side's dust limit, stores the peer's values with `ChannelModel.UpdateRemoteParams` (our own, incl. `to_self_delay`, never change), builds the funding tx, replies funding_created. The channel is not persisted until funding_signed (BOLT 2: a funder that has not broadcast SHOULD NOT remember the channel).
  - `FundingCreatedMessageHandler`: non-initiator. Replies funding_signed, persists the channel and watches the funding tx.
  - `FundingSignedMessageHandler`: initiator. Signs, publishes and watches the funding tx. Sends no reply.
  - `ChannelReadyMessageHandler`: on the **first** channel_ready (the remote key set still at the first index) it builds the channel's first commitment snapshot (`ChannelStateTransitionService.CreateInitialCommitments`: balances, feerate, both commitment numbers, the peer's signature of our commitment 0, the peer's current point from the key set and the next point from the message) before the key set's point is overwritten (NL-232), and saves it with `IChannelStateDbRepository.InitializeAsync` in the same save as the channel; the model gets it only after the save. If the snapshot can't be built it logs and the channel works without HTLCs. Channels that received channel_ready before this existed have lost the peer's commitment-0 point and never get a snapshot (logged at startup; their HTLC messages get a warning).
  - Normal operation (N6-T1), all through the scoped `Services/ChannelStateTransitionService`: `UpdateAddHtlcMessageHandler`, `UpdateFulfillHtlcMessageHandler`, `UpdateFailHtlcMessageHandler`, `UpdateFailMalformedHtlcMessageHandler` (a failure_code without BADONION: warning + close, checked first), `UpdateFeeMessageHandler` (feerate bounds `MinAcceptableFeeratePerKw` 253 / `MaxAcceptableFeeratePerKw` 250,000), `CommitmentSignedMessageHandler` (replies revoke_and_ack, then our commitment_signed when changes are pending for the peer) and `RevokeAndAckMessageHandler` (inserts the secret into a fresh copy of the peer's shachain loaded from `IRemoteShachainDbRepository`, saves it with the transition as `ChannelStateExtras.RemoteShachain`, then signs if changes are pending). Each: guard (`GetUpdatableChannel`), engine call, `CommitAsync` (`ApplyAsync` + one `SaveChangesAsync`, then `ChannelModel.UpdateCommitments` + memory update, then the transition's events are queued), then the replies. Engine violations (`CommitmentViolationException`) become `ChannelWarningException { CloseConnection = true }` (BOLT 2's warning-and-close option; the engine state is unchanged and reestablish recovers), except `MustFailChannel` ones (bad revocation secret, B2-RAA-R01) which become `ChannelFailedException`.
  - `FundingConfirmedMessageHandler`: not an IChannelMessageHandler. It is triggered by a funding confirmation and emits channel_ready through its `OnMessageReady` event.
- `Channels/Services/CommitmentSigningService.cs` (BOLT2 plan N3-T5): a concrete service (no interface) with `SignRemoteCommitment(channel, CommitmentTxSpec, remoteNumber, remotePoint)` and `VerifyLocalCommitment(channel, CommitmentTxSpec, localNumber, sig, htlcSigs)` (throws `SignerException`), both returning `CommitmentTxSignatures(txid, sig, htlcSigs)`. It runs factory (spec-driven overload) -> `BuildWithOutputMap` -> `HtlcTransactionModelFactory` -> `IHtlcTransactionBuilder.Build` -> `ILightningSigner` (`SignChannelTransaction` + `SignRemoteHtlcTransactions`, or `ValidateSignature` + `ValidateLocalHtlcSignatures`), so HTLC signatures are always in commitment output order. Vectors: `test/NLightning.Integration.Tests/BOLT3/CommitmentSigningServiceVectorTests` (Appendix C/F: as node B the signatures equal `remote_signature`/`remote_htlc_signature`; as node A the vector signatures verify).
- Engine ports (NL-230), same folder: `EngineCommitmentSignerPort : ICommitmentSigner` and `EngineCommitmentVerifierPort : ICommitmentVerifier` (the Domain engine ports in `Channels/Commitments/Interfaces`) look the channel up in `IChannelMemoryRepository` by id (static data only), adapt the engine's `CommitmentSpec` with `CommitmentTxSpec.FromCommitmentSpec`, and call `CommitmentSigningService`; they reject a spec of the wrong holder (`ArgumentException`) and an unknown channel (`InvalidOperationException`). The verifier maps `SignerException` to `false` (the engine then raises B2-CS-R01) and logs it; other exceptions propagate. `EngineRevocationVerifierPort : IRevocationVerifier` delegates to `IPerCommitmentSecretVerifier.Verify`. All four are singletons registered by `CommitmentEngineServiceCollectionExtensions.AddCommitmentEngineServices()` (called from `AddApplicationServices`). Proof: `test/NLightning.Application.Tests/Channels/Services/EngineCommitmentPortsTwoNodeTests` drives two engines with real `LocalLightningSigner`s built from the production DI (`RealSigningCommitmentPair`) through add/CS/RAA/fulfill/fail/update_fee, with and without anchors, and checks that the txid each side signed equals the txid the other verified; tampered commitment/HTLC signatures fail B2-CS-R01 and a wrong secret B2-RAA-R01. The same harness records each node's domain events (`RealSigningNode.Events`, N4-T4) and checks lock-in once on revoke_and_ack and fail/settle only when irrevocable. The N6-T1 receive handlers drive the engine through `ChannelStateTransitionService`. `ChannelManager` hands the `IHtlcSwitch` (Domain, `Channels/Interfaces`; `LocalOnlyHtlcSwitch` by default) the events of each persisted transition, and replays `ChannelDomainEvents.DerivePending` at startup.
- `Channels/Services/ChannelStateTransitionService.cs` (scoped, N6-T1): `GetUpdatableChannel(id, state, name)` is the state guard (HTLCs disabled by `NodeOptions.HtlcsEnabled` → the old "not supported yet" warning; channel not in memory or without a snapshot → warning; `Failed` → `error` again; not `Open` → warning + close, B2-NO-02); `CommitAsync(channel, result, extras)` persists one transition (D3/I1/I2); `CreateRevokeAndAck` calls `ILightningSigner.AdvanceLocalCommitment` then `RevealPerCommitmentSecret` (only after the save, I3); `SignIfPendingAsync` signs the peer's next commitment when `ChannelCommitments.CanSendCommit` (never after data loss) and saves it with `ChannelStateExtras.SentCommitDiff` (our pending updates rebuilt from the snapshot — adds by id, removals by id, fee — then the commitment_signed, in `SentCommitDiffCodec` format: u16 big-endian length + serialized message each) and `LastSent`; `ToWireMessage` maps engine outbound messages to wire messages; `LoadRemoteShachainAsync` gives a fresh store loaded from the database. `ChannelDomainEventQueue` (scoped) collects the events of the persisted transitions. `SecretStorageServiceFactory` (`ISecretStorageServiceFactory`, `TryAddSingleton`) makes `SecretStorageService` instances. All registered by `AddChannelStateTransitionServices()` (in `CommitmentEngineServiceCollectionExtensions`, called from `AddApplicationServices`).
- Send side (N6-T2), `Channels/Interfaces/` and `Channels/Services/`:
  - `ChannelOperationsService : IChannelOperations` (singleton): Offer/Fulfill/Fail/FailMalformed/UpdateFee each take the channel's lock, check the preconditions (`NodeOptions.HtlcsEnabled`, `Open`, not `Failed`, no data loss, a snapshot, and for **every** operation the channel's link is up: `IPeerLivenessProbe.IsAliveAsync(channelId, peer)`), run the engine (its sender rules throw `CommitmentRefusedException`), persist with `ChannelStateTransitionService.CommitAsync` (one save), publish the wire message through `IChannelMessagePublisher` under the lock, then `ICommitScheduler.Schedule` after the lock. Nothing is persisted or sent on a refusal; an unknown channel throws `KeyNotFoundException`. A removal or fee update for a peer that is away (or on a connection the channel was not opened/reestablished on) is refused like an offer: `PeerManager` drops messages for a peer that is not connected and nothing retransmits before N7, so a persisted-but-unsent update would later be covered by a `commitment_signed` the peer can't verify. The HTLC stays locked in and the switch acts again on the replay (startup; N7 must replay after the reestablish). Left for N7: an update enqueued just as its connection closes is lost with that connection (the link is then down for good, so nothing signs over it; N7's reestablish must forget/retransmit it). `RecordOnionSecretAsync` stores the incoming HTLC's Sphinx secret (`IChannelStateDbRepository.SetOnionSharedSecretAsync`, one save). The `HtlcOrigin` of an offer is validated but **not stored** (the circuit/payment tables are W1-C/W2-B). "channel_reestablish processed" is approximated by the pinned link (N7 must call `MarkLinkUp`).
  - `CommitScheduler : ICommitScheduler` (singleton, `CommitSchedulerOptions.Debounce`, default 10 ms): one waiting round per channel, run on the thread pool without the caller's execution context (so its message goes to the peer's current connection); `SignNowAsync` asks `IPeerLivenessProbe` (ping-before-commit) before the lock and again under it (a reconnection meanwhile must not get a commitment_signed before channel_reestablish), then under the lock `ChannelStateTransitionService.SignIfPendingAsync` (never while `RemoteNextCommit` exists, D7; persisted with the diff) and publishes. `WhenIdleAsync` for tests. A failed signature is logged; the changes stay pending. The receive handlers still sign on their own after commitment_signed/revoke_and_ack.
  - `IPeerLivenessProbe` → `ConnectedPeerLivenessProbe` (singleton): channel-scoped. `MarkLinkUp(channelId, peer)` pins the peer's current connection (the `PeerModel` instance `IPeerManager.GetPeer` returns; one per connection); `IsAliveAsync(channelId, peer)` is true only while `GetPeer` still returns that same instance, so after a reconnection the channel is down until marked again. `ChannelManager` marks a channel when it turns `Open` (channel_ready handled, or our funding confirmation); a channel loaded at startup is **never** marked (no channel_reestablish until N7, which must call `MarkLinkUp` after the reestablish and replay the pending events). Without a peer manager (in-process tests) a marked channel is up. The peer manager is resolved lazily. A real ping needs a last-message timestamp from `IPeerService` (not there yet).
  - `IChannelMessagePublisher`: implemented by `ChannelManager.Publish` (raises `OnResponseMessageReady`); call it under the channel's lock.
  - `Channels/Switch/LocalOnlyHtlcSwitch : IHtlcSwitch` (`TryAddSingleton`; replace it with `services.Replace(...)`): on `IncomingHtlcLockedIn` it skips an HTLC that is no longer in `RcvdAddAckRevocation` (idempotent replay), fails a blinded HTLC with `invalid_onion_blinding` (malformed), peels with `ISphinxService.PeelAsLocalNode(packet, payment_hash)` (BADONION → `update_fail_malformed_htlc` with the exception's sha256_of_onion; `invalid_onion_payload` with a secret → encrypted), records the shared secret, then fails with `incorrect_or_unknown_payment_details(htlc_msat, IBlockchainMonitor.LastProcessedBlockHeight)` when final and the height is known, or `temporary_node_failure` when it would forward or no block was processed yet (height 0 would mislead the payer); no BOLT 4 final-node checks yet (`final_incorrect_cltv_expiry`/`final_incorrect_htlc_amount`, W2-B), encrypted by `IFailureOnionService.CreateErrorPacket`. No replay-cache entry. Outgoing fulfilled/failed are logged; `OutgoingHtlcSettled` prunes the archived row (`PruneSettledHtlcsAsync`, one save, NL-243). A `CommitmentRefusedException`/`KeyNotFoundException` is logged, not thrown.
- `Channels/Managers/ChannelManager.cs`: the `switch (message.Type)` in `DispatchChannelMessageAsync`. `HandleChannelMessageAsync` creates the message scope **before** taking the lock; after the lock is released it drains the scope's `ChannelDomainEventQueue` into the registered `IHtlcSwitch` (a failing switch is logged, the events are re-derivable), also when the handler threw after a persisted transition. A `ChannelFailedException` from a handler is persisted first (under the lock): `ChannelState.Failed` and the serialized `error` (`ChannelModel.MarkErrorSent`) through `ChannelDbRepository.UpdateAsync` + save, then rethrown (PeerManager sends the error and disconnects). funding_created runs under its temporary id's lock **and** the real channel id's lock (computed with `IChannelIdFactory`, temporary first; NL-235): the only place two locks are held. `RegisterExistingChannelAsync` also keeps `Failed` channels in memory, and for a channel with a snapshot runs `ChannelCommitments.RevertUncommitted` and persists it when it changed something (before any reestablish); for an `Open` channel it then derives the pending events (`ChannelDomainEvents.DerivePending` over the snapshot and the unpruned settled rows from `IChannelStateDbRepository.LoadAsync`; a failure is logged and skipped) and hands them to the switch **after** releasing the lock (I8). At startup no channel's link is up, so a replayed fail is refused (logged by the switch) and the HTLC stays locked in until the replay after N7's reestablish. `HandleChannelMessageAsync` (a channel that was not `Open` before the message and is after it) and the funding confirmation (after `FundingConfirmedMessageHandler`) call `IPeerLivenessProbe.MarkLinkUp` under the lock. Also handles blockchain events: `HandleNewBlockDetected` (ForgetStaleChannels, ConfirmUnconfirmedChannels) and `HandleFundingConfirmationAsync`.
- `Node/Managers/PeerManager.cs`: `ConcurrentDictionary<CompactPubKey, PeerSession>`; a session is one connection: the `PeerModel`, a bounded inbound queue (1024, the transport read loop waits when full) drained by one loop, a close token, and the connection's `PeerOutbox`. A connection becomes a session only after `IPeerService.WaitForInitAsync` (both inits exchanged; its preferred address and features come from that init): `ConnectToPeerAsync` returns only then and throws `ConnectionException` (after disposing the peer service) if the connection closes first, and an inbound connection is handled on its own task (`HandleNewPeerConnectedAsync`) and dropped with an info log in that case. So neither end ever keeps a connection the other cannot use (NL-240). `StopAsync` sets `_stopping` under the session lock and cancels the pending init waits (`WaitForInitAsync` gets a stopping token; the connection is disconnected and disposed); `TryInstallSession` refuses under the same lock once stopping (`InstallResult.Stopping`), so every installed session is in the disconnect pass, and `StopAsync` also waits (5 s timeout) for the inbound setups still running (`_inboundSetups`, registered before any of the setup runs), so no peer is saved to the database after it returns. Sessions subscribe to the peer service right after that (before any DB work; `PeerService` replays channel messages and a disconnection that happened before), and only then are installed. Closing a session cancels its loop (queued messages are dropped, the one being handled finishes); the next session of the same peer starts its loop only after the previous loop ended, and `StopAsync` waits for all loops. Replies raised while a loop handles a message go to that loop's session (an `AsyncLocal`), so they are dropped rather than sent on a newer connection. A new connection replaces the current one, except within `SimultaneousConnectWindow` (5 s) of an opposite-direction connection, where the connection initiated by the lower pubkey is kept (LND's `shouldDropLocalConnection`). A runtime drop of a peer with active channels in `IChannelMemoryRepository` starts the backoff reconnect loop unless the disconnect was ours (`DisconnectPeer`, `StopAsync`, replacement). It subscribes to `IChannelManager.OnResponseMessageReady` in its constructor and only enqueues there (never throws). Maps exceptions (through the outbox, so they follow the replies queued before them), always scoped to the message's channel id (never an all-zero `error`, BOLT 1): ChannelErrorException sends `error` for the channel and disconnects, ChannelWarningException sends a `warning` and stays connected (or disconnects after it when `CloseConnection` is set), any other exception (our bug) sends a channel `warning` and disconnects.
- `PeerManager.StartAsync` (NL-201): awaits `IChannelManager.RegisterExistingChannelAsync` (takes the channel lock; memory + signer) for every non-Closed/Stale channel of every stored peer before connecting to any of them; a failing channel is logged and skipped. A peer with such channels that can't be reached gets a background reconnect loop (`NodeOptions.ReconnectInitialDelay`, default 5 s, doubling up to `NodeOptions.ReconnectMaxDelay`, default 10 min; config `Node:ReconnectInitialDelay`/`Node:ReconnectMaxDelay`; `PeerManager` takes an optional `IOptions<NodeOptions>` and falls back to those defaults without it) that ends when the peer is connected (either direction) or `StopAsync` cancels it (StopAsync waits for the loops before disconnecting peers).
- `Gossip/` (ABCD W1-E, NL-099 subset: direct `channel_update` exchange on our unannounced channels): `Interfaces/IChannelUpdateService`, `Services/ChannelUpdateService` (singleton), `Events/ChannelUpdateReadyEventArgs`, and `GossipServiceCollectionExtensions.AddGossipServices()` (TryAdd, so idempotent; called from `AddApplicationServices`). `PeerManager` takes it as an optional last constructor parameter: without it nothing is sent or stored. The service subscribes to `IChannelMemoryRepository.OnChannelUpdated`; the first time a channel is seen `Open` with a short channel id it runs `SendChannelUpdateAsync` on another task, which takes the channel's lock first (the event is raised under the lock by the handler that opened the channel, before it queues its own channel_ready, so our update always follows channel_ready in the outbox), builds and signs the update (`must_be_one|dont_forward`, `direction` = 1 when our node id is the greater, the real scid or, for an `option_scid_alias` channel (`ChannelParams.UseScidAlias` > No), the peer's alias `RemoteAlias` (BOLT 2 forbids routing into it by the real scid), fee/CLTV delta from `NodeOptions.Routing`, `htlc_minimum_msat` = max(peer's htlc_minimum, `Routing.HtlcMinimumMsat`), `htlc_maximum_msat` = min(capacity, peer's max_htlc_value_in_flight, `Routing.HtlcMaximumMsat`), timestamp = UNIX time but always above the previous one; no update at all, with a warning log, when the minimum is above that maximum or an alias channel has no `RemoteAlias` yet: `CreateChannelUpdate` throws `InvalidOperationException` there) and raises `OnChannelUpdateReady`, which `PeerManager` turns into `PeerOutbox.TryEnqueueGossip`. `HandleRemoteChannelUpdate(peer, message)` keeps the peer's update only if it is for our chain, names a channel with that peer (real scid, our `LocalAliases` or its `RemoteAlias`), has the peer's direction, verifies with the peer's node id (`ILightningSigner.VerifyNodeMessage`), is newer, is at most `ChannelUpdateService.MaxFutureTimestamp` (14 days) ahead of our clock and has `htlc_maximum_msat` <= capacity; `TryGetRemoteChannelUpdate`/`TryGetLocalChannelUpdate` read them (for route hints and BOLT 4 UPDATE failures). Resend: every session `PeerManager` installs (after init; also after a reconnect or a restart) runs `SendChannelUpdatesToPeerAsync(peer)` on another task: for each `Open` channel with that peer (under its channel lock) the last update again if its policy is still current (same timestamp, as LND does on reconnect), else a new one. LND ignores a same-policy "keep-alive" update younger than 24 h, so only a policy change (e.g. new `Routing` options after a restart) shows up there. The peer's update is kept in memory only (forgotten on restart until it sends a new one). Note LND never puts an unannounced node in `addinvoice --private` hints (it requires `IsPublicNode`), so that needs `node_announcement` (NL-099). Docker proof: `Docker/ChannelUpdateExchangeTests` (LND `GetChanInfo` shows our policy; we stored LND's).
- `Node/Services/PeerOutbox.cs`: the only send path for a peer's channel messages: a FIFO (`System.Threading.Channels`) drained by one loop that awaits each `IPeerService` send. `TryEnqueue`, `TryEnqueueGossip` (our `channel_update`, sent with `IPeerService.SendGossipMessageAsync`), `TryEnqueueWarning`, and `TryEnqueueDisconnect` (terminal: sent after everything queued before it, later items are refused). Nothing else calls `IPeerService.SendMessageAsync` for channel messages: the Daemon's `OpenChannelClientHandler` calls `IChannelManager.StartOpeningChannelAsync`, which stores the temporary channel and raises open_channel through `OnResponseMessageReady` under the temporary channel's lock.
- `Protocol/Factories/MessageFactory.cs`: implements Domain `IMessageFactory`. Thin payload+TLV builders with no validation.

## Adding an inbound channel message handler (the common task)
1. The message, payload and serializer must already exist. Check `src/NLightning.Domain/Protocol/Messages`, `src/NLightning.Infrastructure.Serialization/{Messages,Payloads,Tlv,Factories}` and `src/NLightning.Domain/Protocol/Constants/MessageTypes.cs`.
2. Create `Channels/Handlers/<Msg>MessageHandler.cs : IChannelMessageHandler<<Msg>Message>`. DI registers it automatically; don't add it by hand.
3. Add a `case MessageTypes.<X>:` to `ChannelManager.DispatchChannelMessageAsync`. It should call `ThrowIfUnknownChannelAsync` for a real channel id, then `GetChannelMessageHandler<T>(scope).HandleAsync(Cast<T>(message), ...)`. **If you skip this, the message falls into `default`, which throws a channel-scoped ChannelWarningException ("not supported yet"): the message is ignored, the peer gets a `warning` and stays connected.** That is the interim behavior for channel_reestablish (BOLT2 plan N7) and shutdown/closing_signed (N10); we never fail the channel for a missing handler, since LND would force-close it. A message for a channel we don't know at all (memory, temporary channels of the peer, DB) gets an `error` for that unknown channel_id (BOLT 1 SHOULD; `ThrowIfUnknownChannelAsync`).
4. At the top of the handler, check the state and throw ChannelErrorException or ChannelWarningException (`NLightning.Domain.Exceptions`) with `(message, channelId?, peerMessage?)`. The peer receives `PeerMessage` when it is non-empty; otherwise the internal `message` is sent (`src/NLightning.Infrastructure/Node/Services/PeerCommunicationService.cs`), so always pass a `peerMessage` if the internal text shouldn't leak.
5. Persist through a scoped `IUnitOfWork` (`ChannelDbRepository` then `SaveChangesAsync`) and update `IChannelMemoryRepository`.
6. Build outbound messages only through `IMessageFactory`. Return the replies to the requester as a list, in wire order. To send to a peer other than the requester (e.g. when forwarding), raise an event that ChannelManager converts into `OnResponseMessageReady` (see `FundingConfirmedMessageHandler`), synchronously while the channel's lock is held, so wire order equals persist order. `ChannelManager` already holds the lock of the message's channel id around your handler: don't acquire it again (it is not reentrant), and never take a second channel's lock from inside a handler.
7. Add tests in `test/NLightning.Application.Tests/Channels/Handlers/` (xunit.v3 + Moq). Existing handler tests are named `HandleAsync_Condition_Outcome`; PeerManager tests use `Given_X_When_Y_Then_Z`.

## Conventions
- Use a file-scoped namespace. Put System and Microsoft usings above it, and relative `using Domain.X;` usings after it.
- Store injected dependencies in `_camelCase` readonly fields. Guard hot-path logs with `if (_logger.IsEnabled(...))`.
- Lifetimes: managers are singletons. They create an `IServiceScope` per message or event. Handlers and `IUnitOfWork` are Scoped. Never inject IUnitOfWork into a singleton. `IChannelMemoryRepository` and `IUtxoMemoryRepository` are singletons.
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate. `.editorconfig` treats IDE0005/0051/0060/0044 and the naming rules as errors.

## Dependency rules
- The intended direction is Domain only. In practice the csproj also references `NLightning.Infrastructure` and `NLightning.Infrastructure.Bitcoin`, because of IBlockchainMonitor and IBitcoinWalletService (`Infrastructure.Bitcoin/Wallet/Interfaces`), the funding/commitment tx builders (`Infrastructure.Bitcoin/Builders/Interfaces`), and ITcpService, NewPeerConnectedEventArgs and PeerAddress (`Infrastructure/Transport`, `Infrastructure/Protocol/Models`). Don't add more.
- `NLightning.Bolt11` is referenced (since ABCD W1-B) for invoice encode/decode. Keep its NBitcoin types (`uint256`, `PubKey`) inside `Payments/Invoices` and `Payments/Routing/PaymentTarget.cs` (`PaymentTarget.ToWireBytes`/`FromWireBytes` convert a Bolt11 `uint256` to wire bytes through its hex, which is the LND/wire order).
- MUST NOT reference: Infrastructure.Serialization, Infrastructure.Persistence(.*), Infrastructure.Repositories, Daemon, Client, Transport.Ipc. Depend on Domain interfaces instead, such as `IUnitOfWork`, `IMessageSerializer` and `IHopPayloadSerializer`.
- New abstractions belong in Domain as interfaces (as `ISphinxService`/`IOnionReplayCache` already do). Their implementations go in Infrastructure(.Bitcoin).

## Gotchas
- Opening messages carry the **temporary** channel id. `currentState` only looks up real channels, so it is `None` for them, and the handlers must call `TryGetTemporaryChannelState(peer, id)` themselves. funding_created still carries the temp id. Only the initiator calls `UpgradeChannel`, which fires the `OnChannelUpgraded` event the Daemon's OpenChannelClientHandler waits on.
- `ForgetStaleChannels` only forgets fundee (non-initiator) channels still awaiting funding (`V1FundingSigned`/`ReadyForThem`) whose `FundingCreatedAtBlockHeight` is non-zero and at least 2016 blocks old. `FundingCreatedMessageHandler` sets that field to `IBlockchainMonitor.LastProcessedBlockHeight`; `HandleFundingConfirmationAsync` later overwrites it with the funding tx's first-seen height. Legacy rows with a zero height get it backfilled to the current block height on the next block, so their timeout starts then.
- `ConfirmUnconfirmedChannels` only re-drives `V1FundingSigned`/`ReadyForThem` channels whose watched funding tx is already `IsCompleted` (e.g. confirmed while offline). `HandleFundingConfirmationAsync` and `FundingConfirmedMessageHandler` ignore any other state, so channel_ready is sent once per confirmation. Re-sending channel_ready on reconnect belongs to channel_reestablish (not implemented).
- `AcceptChannel1MessageHandler` deliberately does not persist the initiator channel; `FundingSignedMessageHandler` saves it before publishing the funding tx. On failure it removes the temporary channel by its temporary id (or the upgraded channel) and releases the locked UTXOs; failures in the validation checks before its `try` still rely on the Daemon's OpenChannelClientHandler to release them.
- Per-channel lock (NL-033): `ChannelManager` holds the lock for the message's channel id (the temporary id during the open flow, the real id after) around dispatch and the raising of the replies; block handlers (`ForgetStaleChannels`, the backfill, `HandleFundingConfirmationAsync` → `ConfirmFundingAsync`) take it per channel and re-check the channel's state under it. A channel is keyed by its temporary id until funding_created/funding_signed and by its real id afterwards; the per-peer inbound loop already serializes the open flow. The IPC open-channel operation takes it through `StartOpeningChannelAsync` (store the temporary channel + raise open_channel).
- scid aliases (NL-103): `FundingConfirmedMessageHandler` generates `LocalAliases` that avoid every real scid and alias in `IChannelMemoryRepository`, and reuses them if the channel already has some. `LocalAliases` is never persisted, so after a restart old aliases are forgotten: they are no longer recognized for incoming HTLCs and new ones are generated.
- Handler discovery uses reflection (`Assembly.GetTypes()`), which trimming or AOT may break.

## Payments (ABCD W1-B: ONION M4-T2/T3/T4/T6, invoices)
Registered by `Payments/PaymentsServiceCollectionExtensions.AddPaymentsServices()` (all singletons; called from `AddApplicationServices`). It needs `ISphinxService` (`AddBitcoinInfrastructure`), `IHopPayloadSerializer` (`AddSerializationInfrastructureServices`), `IOnionReplayCache` (`AddInfrastructureServices`), `ISecureKeyManager` and `IOptions<NodeOptions>` (host), and a **Scoped `IInvoiceDbRepository` that shares the scope's DbContext with `IUnitOfWork`** (`AddRepositoriesInfrastructureServices` registers it, and `IPaymentDbRepository`/`IForwardCircuitDbRepository`, as the scope's `IUnitOfWork` properties).
- `Onion/IncomingOnionProcessor.ProcessAsync(onionRoutingPacket, paymentHash, updateAddPathKey?, checkReplay = true)` (M4-T2): peel with the node key → replay cache (only after a successful peel) → `IHopPayloadSerializer.DeserializeAsync` → `HopPayloadValidator`. Returns one of `IncomingOnionForward` (scid, `amt_to_forward`, `outgoing_cltv_value`, `NextPacket`), `IncomingOnionFinal` (payload), `IncomingOnionMalformed` (BADONION code + `sha256_of_onion` → `update_fail_malformed_htlc`) or `IncomingOnionFailed` (`FailureMessage` + shared secret → `update_fail_htlc` with `IFailureOnionService.CreateErrorPacket`). Never throws for a bad onion (only `ArgumentException` for a packet that is not 1366 bytes). Route blinding (M5) is refused: an `update_add_htlc` `path_key` → malformed `invalid_onion_blinding`; a payload with `current_path_key` → `update_fail_htlc` `invalid_onion_blinding` (BOLT 2). A replayed HMAC → `temporary_node_failure` (our choice; BOLT 4 only says "fail"). Pass `checkReplay: false` only when re-processing an HTLC this node already processed. Keep the shared secret with the HTLC (`HtlcEntity.OnionSharedSecret`).
- `FinalHop/FinalHopProcessor` (M4-T3, no MPP): `ProcessAsync(IInvoiceDbRepository, paymentHash, htlcAmount, htlcCltvExpiry, payload, height)` or the pure `Evaluate(InvoiceModel?, ...)`. First HTLC vs onion: `amount_msat < amt_to_forward` → 0x0013 (HTLC amount), `cltv_expiry < outgoing_cltv_value` → 0x0012 (HTLC cltv), both before the invoice lookup (as LND/CLN; they leak nothing about invoices). Then everything invoice-related → 0x400F with (HTLC amount, height): no payment_data, unknown hash, canceled/expired/already accepted or settled, secret mismatch, `total_msat != amt_to_forward`, paid below the amount or above twice it, `cltv_expiry < height + c`. It never mutates the invoice: on accept the caller does `invoice.Accept(result.AmountReceived)` + `UpdateAsync` in the fulfill's unit of work. Process each incoming HTLC once; a second run after accept fails as "already paid". The check is a read, not a check-and-mark: the W2-B switch MUST hold a per-payment-hash lock around re-read → `Evaluate` → `Accept` + `UpdateAsync` → save (same unit of work as the staged fulfill), or compare-and-set the status, so a second concurrent HTLC for the same hash sees Accepted and gets PERM|15.
- `Policy/HtlcForwardingPolicy : IForwardingPolicy` (M4-T4): the check order documented on `IForwardingPolicy`, over `NodeOptions.Routing` read on every call. `expiry_too_soon` when `outgoing_cltv_value <= height + ExpiryTooSoonBlocks` (inclusive, as LND); `expiry_too_far` when the incoming `cltv_expiry > height + MaxCltvExpiryDistance`; below `max(channel htlc_minimum, HtlcMinimumMsat)` → `amount_below_minimum`; above `HtlcMaximumMsat` or `AvailableToSend` → `temporary_channel_failure`.
- `Routing/` (M4-T6): `PaymentTarget.FromInvoice(Invoice)` (payee, hash, secret, amount, `c`, all `r` hints, metadata). `HintRouteBuilder.Build/TryBuild(target, amount, maxFee, height, ourNodeId, hasUsableChannelTo)`: the payee directly when it is a usable peer, else the first hint (in invoice order) whose first node is a usable peer; a hint containing our node starts after our entry. Per hop, from the payee back: final `outgoing_cltv_value` = height + `c` + `FinalCltvSafetyOffset` (3); each hint entry charges `ForwardingFee` on what it forwards and adds its `cltv_expiry_delta`. A route whose total CLTV exceeds `MaxCltvExpiryDistance`, or whose `Fee` exceeds the mandatory `maxFee` (hint fees are payee-chosen, so an unbounded invoice could charge ~4294x the amount), is skipped with its reason; the W2-C send path must pass the payer's fee limit (e.g. the RPC's `fee_limit_msat`). `PaymentRoute.Hops[0]` is our peer; `FirstHopAmount`/`FirstHopCltvExpiry` are our HTLC. `PaymentOnionFactory.CreateAsync(route)` builds the payloads (intermediate: amt, cltv, scid; final: amt, cltv, `payment_data` with total = amount, `payment_metadata`), draws a CSPRNG session key (re-drawn until it is a valid scalar, zeroed after) and returns `PaymentOnion` (packet + per-hop shared secrets for `DecryptErrorPacket`).
- `Invoices/InvoiceService : IInvoiceService`: CSPRNG preimage and secret, hash = SHA256(preimage), `Bolt11.Invoice` with the node `ISecureKeyManager` (W0-D encode path: `9` = bits 8 and 14 compulsory, no `basic_mpp`), `c` = `Routing.InvoiceMinFinalCltvExpiry`, `x` = the given expiry or `Routing.InvoiceExpirySeconds`, `CreatedAt` = the BOLT 11 timestamp; persisted in its own scope (`IInvoiceDbRepository.AddAsync` + `IUnitOfWork.SaveChangesAsync`) before it returns. Route hints (NL-245): one single-hop `r` field per `Open` channel whose peer's `channel_update` we hold (`IChannelUpdateService.TryGetRemoteChannelUpdate`, not disabled), with the **peer's** fee and `cltv_expiry_delta` (BOLT 11: the entry is the channel from its `pubkey` towards the payee, which the peer charges for), the real scid or, for an `option_scid_alias` channel, `RemoteAlias` (unverified against LND); with an amount, a channel whose peer balance or the update's htlc min/max cannot carry it is skipped; at most `InvoiceService.MaxRouteHints` (3), largest peer balance first. No peer update, no hint (as LND). `IChannelMemoryRepository`/`IChannelUpdateService` are optional constructor parameters: without them there are no hints. Cancel only moves Open → Canceled.
- `Send/PaymentService : IPaymentService, IPaymentOutcomeHandler` (ABCD W2-C, N8-T3 + M4-T6; singleton, registered by `Send/PaymentSendServiceCollectionExtensions.AddPaymentSendServices()`, which the composition root must call; it also adds `IOptions<PaymentSendOptions>`). `PayInvoiceAsync`: `Invoice.Decode` for `NodeOptions.BitcoinNetwork` (a decode failure, expiry, our own invoice, a missing/zero/different amount → `ArgumentException`; no processed block yet → `InvalidOperationException`; nothing persisted), then under a striped per-payment-hash lock: refuse an `InFlight`/`Succeeded` hash (plain `InvalidOperationException`), route with `HintRouteBuilder` over the peers that have an `Open` channel with a snapshot and a live link (`IPeerLivenessProbe`; the channel with the largest local balance) and the fee limit `PaymentSendOptions.GetMaxFee` (max(0.5 %, 5000 msat), as CLN), `PaymentOnionFactory`, persist the payment `InFlight` with every hop's shared secret (`PaymentHop`: the node, the scid that reaches it, the HTLC amount/expiry it receives), then `OfferHtlcAsync(..., HtlcOrigin.Local(hash))` and record the HTLC id in the next save. No route → the payment is stored `Failed` (no code, reason) and returned; a refused offer (`CommitmentRefusedException`/`KeyNotFoundException`) → `Failed` without code. Then it waits for the outcome (timeout/cancellation → returns it still `InFlight`). No automatic retries; a `Failed` hash may be paid again (the new attempt replaces it). **Hook for the HTLC switch (W2-B):** `IPaymentOutcomeHandler.HandleOutgoingHtlcFulfilledAsync`/`HandleOutgoingHtlcFailedAsync` for outgoing HTLCs whose origin is `HtlcOrigin.Local` (or that have no circuit); they return false for an event that is not ours or already applied (idempotent), match the payment by hash and recorded (channel, HTLC id), or, when the id is not recorded yet, by the HTLC's stored origin, save the outcome before returning (so call them before pruning on `OutgoingHtlcSettled`), and never take a channel lock. Fulfill: succeed when SHA256(preimage) = hash. Fail: `update_fail_malformed_htlc` → the code from hop 0; else `IFailureOnionService.DecryptErrorPacket` with the stored secrets + `FailureInterpreter` → `FailureCode`, `FailureSourceIndex` (erring hop, 0 = our peer), a local reason; unattributable → no code.

## Onion-routing (BOLT 4) hooks here
The onion library (M1+M2+M3) is used by `LocalOnlyHtlcSwitch` (peel + error onion, see above) and by `Payments/` (above: payload parsing, replay cache, final hop, forwarding policy); wiring the payment core into the switch comes with ABCD W2-B. All of these are DI singletons:
- `ISphinxService` (`src/NLightning.Domain/Protocol/Onion/Interfaces/`, registered by `AddBitcoinInfrastructure`).
- `IHopPayloadSerializer` (`src/NLightning.Domain/Serialization/Interfaces/`, registered by `AddSerializationInfrastructureServices`).
- `IOnionReplayCache` (registered by `AddInfrastructureServices`).
- `HopPayloadValidator` is a static Domain class.

`IHopPayloadSerializer` is declared in Domain (`src/NLightning.Domain/Serialization/Interfaces/`), so Application uses it without referencing Serialization.

The receive and send paths below are implemented by `IncomingOnionProcessor` and `PaymentOnionFactory`; they are kept as the reference call order.

Receive path (M4-T2, after the HTLC is irrevocably committed):
1. `var packet = new OnionPacket(add.Payload.OnionRoutingPacket.Span);`
2. `var peeled = sphinx.PeelAsLocalNode(packet, paymentHash, blindedPathTlv?.PathKey);`. Pass the update_add_htlc path_key only, never the payload's current_path_key. It throws `OnionException`:
   - A BADONION code (`ex.FailureCode.IsBadOnion()`) → `update_fail_malformed_htlc` with `ex.FailureData` (sha256_of_onion).
   - `InvalidOnionPayload` → `update_fail_htlc` encrypted with `ex.SharedSecret` (M3).
   - With a path_key, every failure comes back as `InvalidOnionBlinding`.
3. `if (!replayCache.TryAdd(packet.Hmac.Span))`: this is a replay, so fail it. Record the HMAC only after the peel succeeded.
4. `var payload = await hopPayloadSerializer.DeserializeAsync(peeled.Payload);`. Its offsets already count the stripped length prefix.
5. `HopPayloadValidator.Validate(payload, peeled.IsFinal, hasUpdateAddPathKey)`. When update_add_htlc carried a path_key, remap any `OnionException` from here on to `invalid_onion_blinding`.
6. If `peeled.IsFinal`, go to final-hop processing. Otherwise forward `peeled.NextPacket` (`.ToBytes()`) on the channel for `payload.ShortChannelId`.

Keep `peeled.SharedSecret` with the HTLC: failures need it later.

Send path (M4-T6):
- Serialize each `HopPayload` with `IHopPayloadSerializer.SerializeAsync`. That writes no length prefix, and `OnionHop` expects none.
- Call `sphinx.ConstructWithSharedSecrets(hops, sessionKey, paymentHash)` with a fresh CSPRNG session key.
- Keep the per-hop secrets for error decryption (M3).

Other hooks:
- The ChannelManager cases and handlers for UpdateAddHtlc, UpdateFulfillHtlc, UpdateFailHtlc, UpdateFailMalformedHtlc, CommitmentSigned, RevokeAndAck and UpdateFee exist (N6-T1); the onion is peeled only after `IncomingHtlcLockedIn` reaches the switch.
- Forwarding: resolve the next hop by ShortChannelId or its aliases through `IChannelMemoryRepository.FindChannels`. Then call `MessageFactory.CreateUpdateAddHtlcMessage`, which can't attach a BlindedPathTlv yet. Send the result through the `OnResponseMessageReady` event path.
- Failures: `CreateUpdateFailHtlcMessage` expects an already obfuscated `reason`, and no error-onion code exists yet (M3). `CreateUpdateFailMalformedHtlcMessage` takes sha256_of_onion plus a raw ushort failure code; cast from `FailureCode`.
