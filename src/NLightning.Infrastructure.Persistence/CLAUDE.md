# NLightning.Infrastructure.Persistence

EF Core 10 model for the node: one `NLightningDbContext`, entity classes used only for persistence, per-entity configuration, value converters, provider selection (DI) and a design-time factory for `dotnet ef`. There are **no repositories here**. Domain<->entity mapping lives in `src/NLightning.Infrastructure.Repositories` (`UnitOfWork`, `Database/**/**DbRepository.cs`). Migrations live in three sibling assemblies: `NLightning.Infrastructure.Persistence.{Postgres,Sqlite,SqlServer}/Migrations`.

## Add an entity/table (the common task)
1. `Entities/<Area>/<Name>Entity.cs`: `required` props, `internal <Name>Entity() { }`. Use value objects plus converters for ids and keys. Enums: either a raw `byte` property (`ChannelEntity.State`, `HtlcEntity.State/Direction`) or a `: byte` enum type directly (`AddressType`). Amounts: `long` sats / `ulong` msat with the unit in the name (`AmountSats`, `AmountMsat`); channel balances are `long LocalBalanceMsat/RemoteBalanceMsat` (migration `StoreMsatBalancesAndShortChannelId`, NL-191, which also added `Channels.ShortChannelId` and reset next HTLC ids of 1 to 0 on channels without HTLC rows, NL-190).
2. `EntityConfiguration/<Area>/<Name>EntityConfiguration.cs`: key (composite via `HasKey(x => new {...})`), `IsRequired`, `.HasConversion<XConverter>()`, relationships **explicitly** (see gotchas), SqlServer `varbinary(N)` using the Domain constants.
3. `NLightningDbContext`: add a `DbSet` and call `Configure<Name>Entity`.
4. Generate migrations for **all three** providers (below) and commit every `Migrations/*` file, including Designer and Snapshot, and the regenerated `CompiledModels/` (`add_migration.sh` regenerates them first; for a model change without a migration run `./scripts/optimize_model.sh`).
5. In Repositories: add `I<Name>DbRepository` in `src/NLightning.Domain/{Bitcoin,Channels,Node}/Interfaces` (Domain uses `Channels`, plural), implement it in `src/NLightning.Infrastructure.Repositories/Database/<Area>/` on `BaseDbRepository<TEntity>`, and add a lazily created (`??=`) property to `IUnitOfWork` (`src/NLightning.Domain/Persistence/Interfaces/IUnitOfWork.cs`) and `UnitOfWork`.

## Migrations (run from this directory)
- Full script: `./scripts/start_postgres.sh && ./scripts/start_sql.sh && ./scripts/add_migration.sh MyCamelCaseName`. It builds the 3 provider projects in Debug and runs `dotnet ef database update` / `migrations add` for each one. It needs Docker and `dotnet-ef`.
- Single provider: `NLIGHTNING_SQLITE='Data Source=./nltg.db' dotnet ef migrations add X --project ../NLightning.Infrastructure.Persistence.Sqlite --startup-project ../NLightning.Infrastructure.Persistence.Sqlite` (NL-233: the provider is always both `--project` and `--startup-project`, so `dotnet ef` builds and runs that provider's own fresh Debug output instead of a possibly stale assembly left in a shared bin folder; the design-time factory is found through the provider's reference to this project). Make sure no other `NLIGHTNING_*` var is set, because Postgres is checked first.
- Remove the last one: `./scripts/remove_migration.sh`, then revert the DbContext and entity edits by hand.
- Names must be CamelCase (dotnet format). Never copy migration files between providers: the snapshots differ.
- Runtime: migrations apply only when `Database:RunMigrations=true` (`src/NLightning.Daemon/Extensions/DatabaseExtensions.cs`, `MigrateDatabaseIfConfiguredAsync`; default written config is `false`).

## Compiled models (NativeAOT, NL-708)
- `CompiledModels/{Sqlite,Postgres,SqlServer}/` are EF Core compiled models of `NLightningDbContext`, one per provider, generated by `./scripts/optimize_model.sh` (`dotnet ef dbcontext optimize --nativeaot`; no database or Docker needed, ~20 s) into a temporary folder and replaces the committed ones only when all three providers succeeded and the result builds, so a failure (dotnet-ef missing, a generator or build error) leaves them intact (NL-767). Never edit them by hand. `add_migration.sh` runs the script first, so a migration never leaves them stale; after any other model change (entity, configuration, converter, `OnModelCreating`) run it yourself. The guard `test/NLightning.Integration.Tests/Persistence/CompiledModelTests` (non-Docker) fails when a compiled model differs from the runtime model (model and relational debug views, per-property mappings, converters, comparers and sentinels, and the bodies of every converter and comparer lambda, which the compiled models copy) for any provider; its SQLite case also adds, updates and reloads a channel graph on both models and compares the rows.
- `CompiledModels/CompiledModelCatalog` picks the provider's model; `DependencyInjection` calls `UseModel` with it when dynamic code is not supported (NativeAOT) or `Database:UseCompiledModel=true` (unset = AOT only; the JIT node builds its model from `OnModelCreating`). `optimize_model.sh` deletes the generated `DbContextModel` assembly attribute: with three models in one assembly EF must never pick one automatically (a test checks it).
- The generator's startup project is `src/NLightning.Infrastructure.Persistence.Design` (design-time only, referenced by nothing): its `NLightningDesignContextFactory` wraps `NLightningContextFactory`, and its `ValueObjectCSharpHelper` writes the `null` sentinel of a non-nullable byte-backed value object (`default(Hash)` converts to a null `byte[]`; the compiled property then has no sentinel). The script builds it with `-p:NltgNoCompiledModels=true` (this project without the generated code, `NLTG_NO_COMPILED_MODELS`), because stale models may not compile.
- Generator limits met so far: a converter that calls a `ReadOnlySpan<byte>` constructor through the implicit `byte[]` conversion is written as an uncompilable `op_Implicit` call (CS0571), so `ChannelIdConverter` uses `(ChannelId)bytes`; a property named `Source` collides with the generator's `source` lambda parameter (CS1503), so `AccountingPriceEntity.PriceSource` keeps the column `Source` (`source` on Postgres) through `HasColumnName`.
- NativeAOT runtime: a provider's default type mapping (`SqliteDecimalTypeMapping.Default`, ...) builds its comparer through `ValueComparer.CreateDefault(Type)` (`MakeGenericMethod`), so `CompiledModelCatalog` references `CreateDefault<T>` for every value type of the model (a real AOT binary failed on `decimal` without it); `CompiledModelTests` fails when a model value type is not in `RootedComparerTypes`. In a real osx-arm64 AOT binary (2026-10-02) all three models initialize, `SaveChanges` inserts and updates, raw SQL runs.
- Still missing for a NativeAOT node: precompiled queries. `./scripts/optimize_model.sh --check-queries` tries `--precompile-queries` on the repositories for SQLite and summarizes why EF 10 refuses (all or nothing; residue in NL-708: query roots through `BaseDbRepository.DbSet`, captured method parameters, dynamic composition, query syntax; the interceptors would also be provider-specific in the one Repositories assembly). EF also refuses migrations under NativeAOT ("Design-time DbContext operations are not supported"), compiled model or not.

## Gotchas
- Postgres uses snake_case (`UseSnakeCaseNamingConvention`). Sqlite and SqlServer use PascalCase. Raw SQL must handle both. `EnableSensitiveDataLogging()` is on only when `Database:EnableSensitiveQueryLogging=true` (all providers; NL-135). The design-time `NLightningContextFactory` still enables it for Postgres, which only affects `dotnet ef`.
- SQL Server `varbinary(N)` sizes must use the matching Domain constant (`CryptoConstants.CompactPubkeyLen` for pubkeys, not `TxIdLength`). `ChannelEntity.RemoteNodeId` was `varbinary(32)` until migration `FixRemoteNodeIdLength` (SqlServer only; NL-129). `test/NLightning.Integration.Tests/Persistence/PersistenceConfigurationTests.cs` asserts the SqlServer snapshot has no pending model changes, so a model edit without a SqlServer migration fails the test run.
- Convention-based shadow FKs: `PeerEntity.Channels` has no configured relationship, so EF created `PeerEntityNodeId` on channels. `ChannelEntity.ChangeAddress` created `ChangeAddressIsChange`/`ChangeAddressAddressType`. Configuring these explicitly changes the schema for all 3 providers.
- The unmapped `RevocationWatchEntity` stub (a pre-signed penalty per revoked commitment) was deleted with its repository (NL-095, BOLT 5 plan D3); the revocation log (`RevokedCommitmentEntity`) replaces it.
- `State`/`Direction` on `ChannelEntity`/`HtlcEntity` are raw `byte`. Compare with `== (byte)Enum.X`, not `.Equals(Enum.X)` (boxed enum never equals a byte).
- The migration name typo `AddBlockchaisStateAndWatchedTransaction` is baked into history. Do not rename it.
- The provider migration projects build into their own `bin/` (NL-223; the old shared `BaseOutputPath` override on this project's `bin/` is gone, so their parallel builds cannot collide and `dotnet ef` must run each provider as its own startup project — the scripts do, NL-233).
- `ChannelConfigs` is split per side since migration `SplitChannelParams` (NL-194): `Local*`/`Remote*` reserve, dust, htlc minimum, max accepted, max in flight and to_self_delay (`Local*` = what we announced). Its data step copied the old single set into both sides (`Remote*` columns are the renamed old ones), which is only approximate (a non-initiator announced the node's htlc_minimum_msat, an initiator never stored the peer's accept_channel limits), so migration `FlagInferredChannelParams` sets `ChannelConfigs.HasInferredParams` on every row that existed then (`ChannelParams.HasInferredParams`: don't enforce those limits); `test/NLightning.Integration.Tests/Persistence/ChannelMigrationDataTests.cs` runs such data steps on pre-migration Sqlite rows. Hand-written data steps go in as `migrationBuilder.Sql` between the generated operations (the designer-diff test ignores `SqlOperation`s); Postgres names are snake_case, SqlServer identifiers `[...]`.
- `ChannelDbRepository.UpdateAsync` detaches the child collections and synchronizes each child table by primary key (NL-192); a new child collection on `ChannelEntity` must be added to that sync too. HTLCs are no longer part of it: HTLC, commitment and fee-update rows are written only by `ChannelStateDbRepository`.
- `migrations add` does not connect to the database, so it works without the Postgres/SQL Server containers: from this directory, `NLIGHTNING_POSTGRES='…' dotnet-ef migrations add X --project ../NLightning.Infrastructure.Persistence.Postgres` (then `NLIGHTNING_SQLITE` / `NLIGHTNING_SQLSERVER` for the other two, one variable set at a time), after building the three provider projects in Debug (NL-233). The generated `.cs` files start with a BOM and end with a newline; run `dotnet format` before committing.
- Migration `AddCommitmentState` data steps (hand-written SQL at the end of `Up`): the scaffolder turned `AddMessageBytes` into `OnionRoutingPacket` (the onion is cut out at byte offset 86, empty for pre-onion rows) and `Signature` into `Sha256OfOnion` (Postgres `sha256of_onion`) or, on SqlServer, `FailReason`; the step nulls that column. It also copies the remote key set's point into `Channels.RemoteNextPerCommitmentPoint` for channels past channel_ready (NL-232). No commitment rows are created for existing channels.

## Remote signing workflows (NL-1305)

`SigningWorkflows` binds a normal-operation signing workflow to the channel, expected local/remote commitment numbers, snapshot fingerprint, signer identity, network and wire schema version. `SigningRequests` retains the exact opaque envelope and response for each immutable request identity and ordinal. There is no channel FK: signer work can precede channel persistence. The request-to-workflow FK restricts deletion; receipts are retained after consumption. A unique nullable `ActiveChannelId` permits one pending or blocked workflow per channel and releases the slot when consumed. Request identities and workflow ordinals are independently unique.

Intent and response writes use independent, short-lived units of work, completed before any subsequent network action. Workflow consumption and its request rows are staged on the caller's channel-transition unit of work and committed together with the transition. No network call holds a database transaction open. SQLite uses the existing `synchronous=FULL` connection interceptor; other providers retain their normal commit durability requirements.

The repository fails closed at count guards of 65,536 retained workflows and 262,144 retained requests, with a 1 MiB envelope and 4 MiB response limit. Count guards include staged rows; concurrent writers on different channels can slightly exceed a global count guard, so these are prototype limits rather than a strict shared quota. Rows are never evicted to admit new identities. The unique active-channel slot and optimistic state concurrency are consistency checks, not deployment-wide writer fencing.
