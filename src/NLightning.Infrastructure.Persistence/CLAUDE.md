# NLightning.Infrastructure.Persistence

EF Core 10 model for the node: one `NLightningDbContext`, entity classes used only for persistence, per-entity configuration, value converters, provider selection (DI) and a design-time factory for `dotnet ef`. There are **no repositories here**. Domain<->entity mapping lives in `src/NLightning.Infrastructure.Repositories` (`UnitOfWork`, `Database/**/**DbRepository.cs`). Migrations live in three sibling assemblies: `NLightning.Infrastructure.Persistence.{Postgres,Sqlite,SqlServer}/Migrations`.

## Layout
- `Contexts/NLightningDbContext.cs`: 20 DbSets (BlockchainStates, WatchedTransactions, WalletAddresses, Utxos, WatchedOutpoints, BroadcastTransactions, BlockHeaders, Channels, ChannelConfigs, ChannelKeySets, Htlcs, ChannelLocalAliases, RemoteShachains, Commitments, FeeUpdates, Peers, Invoices, Payments, PaymentHops, ForwardCircuits). Chain watch (migration `AddChainWatchAndBroadcasts`, BOLT 5 plan O0): `WatchedOutpointEntity` (PK `TransactionId, OutputIndex`; `ChannelId`, `Purpose` byte (`Domain.Onchain.Enums.WatchedOutpointPurpose`), `SpentByTransactionId?`/`SpentAtHeight?`/`SpentBlockHash?` of the spend in the active chain, `CreatedAt` UTC ticks; indexes `ChannelId`, `SpentAtHeight`; no FK, so a watch can outlive its channel row), `BroadcastTransactionEntity` (PK `TransactionId`; `ChannelId?`, `RawTransaction` (the fully signed tx, `varbinary(max)`), `Purpose`/`State` bytes (`BroadcastPurpose`, `BroadcastState`: Pending 0, Confirmed 1, Replaced 2, Abandoned 3), `FeeratePerKw` (long), `ReplacesTransactionId?`, `FirstBroadcastHeight`, `ConfirmedHeight?`/`ConfirmedBlockHash?`, `CreatedAt` ticks; indexes `State`, `ChannelId`, `ConfirmedHeight`) and `BlockHeaderEntity` (PK `Height`, never generated; `BlockHash`, `PreviousBlockHash`: the monitor's reorg ring of the last 100 processed blocks). The migration's hand-written data step (marked in each provider's `Up`) inserts one `FundingOutput` watch per channel with `State >= 2` that is not Closed (40) or Stale (50), `CreatedAt` = migration time in UTC ticks; `test/NLightning.Integration.Tests/Persistence/ChainWatchSchemaRoundTrip.cs` runs it on seeded rows (SQLite in CI, Postgres/SQL Server in `Docker/`). EF packages: EF Core 10.0.12, Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3 (and `Npgsql` 10.0.3 in the Daemon); generate migrations with `dotnet-ef` 10.0.12. Payments (migration `AddInvoicesPaymentsAndCircuits`, ABCD W1-C: BOLT2 N8, ONION M4-T7): `InvoiceEntity` (PK `PaymentHash`; preimage, payment secret, `AmountMsat?`, description, bolt11, expiry, min final CLTV, `Status` byte, `AmountReceivedMsat?`, `SettledAt?`; index `CreatedAt`), `PaymentEntity` (PK `PaymentHash`, one row per hash = latest attempt; payee, amount/fee msat, `Status` byte, `OutgoingChannelId?`/`OutgoingHtlcId?`, `Preimage?`, `FailureCode?`/`FailureSourceIndex?`/`FailureReason?`, `CompletedAt?`; indexes `Status`, `CreatedAt`) with child `PaymentHopEntity` (PK `PaymentHash, HopIndex`; node id, scid, amount, CLTV, 32-byte Sphinx `SharedSecret`; cascade), `ForwardCircuitEntity` (PK `IncomingChannelId, IncomingHtlcId`; incoming amount/CLTV/shared secret, payment hash, requested outgoing scid, outgoing amount/CLTV, `Status` byte, `OutgoingChannelId?`/`OutgoingHtlcId?`, `ResolvedAt?`; indexes `Status` and `(OutgoingChannelId, OutgoingHtlcId)`; no FKs). The same migration added `Htlcs.OriginKind?`/`OriginPaymentHash?`/`OriginIncomingChannelId?`/`OriginIncomingHtlcId?` (the `HtlcOrigin` of an HTLC we offered, indexed for the startup-replay lookups) and `Channels.MaxDustHtlcExposureMsat?` (the snapshot's dust policy, NL-242); no data step (existing rows get nulls). All timestamps of these tables are `DateTimeOffset` stored as UTC ticks (`ValueConverters/UtcTicksConverter`, a `long` on every provider, orderable on SQLite); amounts are `long` msat. Commitment state (migration `AddCommitmentState`, BOLT2 N5-T1): `HtlcEntity` is the engine's `HtlcRecord` (PK `ChannelId, HtlcId, Direction`; `State` 10-39, `OnionRoutingPacket`, `PathKey?`, removal columns `RemovalKind?`/`PaymentPreimage?`/`FailReason?`/`FailureCode?`/`Sha256OfOnion?`, `KnownPreimage?`, `OnionSharedSecret?`; the legacy `AddMessageBytes`/`ObscuredCommitmentNumber`/`Signature` are gone and rows in legacy states 0-3 are refused on load, NL-025); `CommitmentEntity` (PK `ChannelId, Slot`: 0 local current, 1 remote current, 2 remote unacked; number, feerate, local/remote msat, spec HTLCs as 53-byte records, remote per-commitment point, signature, length-prefixed HTLC signatures); `FeeUpdateEntity` (PK `ChannelId, Sequence`); `ChannelEntity.RemoteNextPerCommitmentPoint`, `SentCommitDiff`, `LastSentOrder`, `ErrorSent`, `DataLossDetected`. Mutual close (migration `AddShutdownState`, BOLT2 N10): `Channels.LocalShutdownScript?`, `RemoteShutdownScript?`, `ClosingTxId?` (TxId, `varbinary(32)` on SqlServer) and `ClosingTransaction?` (the fully signed tx), all nullable, no data step; written by `ChannelDbRepository.UpdateAsync` (not snapshot-owned). Commitments and FeeUpdates cascade from Channels without a navigation. `ChannelKeySets.LastRevealedPerCommitmentSecret` was dropped (NL-238). `RemoteShachainEntity` (migration `AddRemoteShachain`): PK `(ChannelId, Bucket)`, `Index` (`long`, 48-bit), `Secret` (32 bytes), FK to `Channels` with cascade but no navigation property. `ChannelEntity.LocalCommitmentNumber`/`RemoteCommitmentNumber` (migration `PersistCommitmentNumbers`, data step copies the revocation numbers). `OnModelCreating` calls `modelBuilder.Configure<X>Entity(_databaseType)`.
- `Entities/{Bitcoin,Channel,Node,Payment}/`: POCOs, mostly `required` props, each with an `internal` parameterless ctor for EF.
- `EntityConfiguration/{Bitcoin,Channel,Node,Payment}/`: `public static void Configure<X>Entity(this ModelBuilder, DatabaseType)`, plus private `OptimizeConfigurationForSqlServer` helpers (varbinary sizes, online indexes). Only `UtxoEntityConfiguration` also has `OptimizeConfigurationForPostgres` (concurrent indexes).
- `ValueConverters/`: ChannelId, CompactPubKey, Hash, ShortChannelId, TxId stored as `byte[]`, using the value objects' implicit conversions; `UtcTicksConverter` stores a `DateTimeOffset` as its UTC ticks (use it for new timestamp columns: EF SQLite cannot order `DateTimeOffset`, Npgsql refuses non-UTC offsets).
- `DependencyInjection.cs`: `AddPersistenceInfrastructureServices(services, configuration)`. It reads `Database:Provider` (postgres|postgresql|sqlite|sqlserver|microsoftsql), `Database:ConnectionString` and `Database:EnableSensitiveQueryLogging`, and sets the MigrationsAssembly for each provider. SQLite gets `Interceptors/SqliteDurabilityInterceptor` (`PRAGMA synchronous=FULL` on every opened connection, N5-T3).
- `Factories/NLightningContextFactory.cs`: design-time factory driven by env vars `NLIGHTNING_POSTGRES`, then `NLIGHTNING_SQLITE`, then `NLIGHTNING_SQLSERVER` (first one set wins).
- `Enums/DatabaseType.cs`, `Providers/DatabaseTypeProvider.cs`: pass the provider into the model.
- `scripts/`: add/remove migration, start/destroy docker Postgres (port 15432) and SQL Server (1433). `README.md` has the tooling notes.

## Add an entity/table (the common task)
1. `Entities/<Area>/<Name>Entity.cs`: `required` props, `internal <Name>Entity() { }`. Use value objects plus converters for ids and keys. Enums: either a raw `byte` property (`ChannelEntity.State`, `HtlcEntity.State/Direction`) or a `: byte` enum type directly (`AddressType`). Amounts: `long` sats / `ulong` msat with the unit in the name (`AmountSats`, `AmountMsat`); channel balances are `long LocalBalanceMsat/RemoteBalanceMsat` (migration `StoreMsatBalancesAndShortChannelId`, NL-191, which also added `Channels.ShortChannelId` and reset next HTLC ids of 1 to 0 on channels without HTLC rows, NL-190).
2. `EntityConfiguration/<Area>/<Name>EntityConfiguration.cs`: key (composite via `HasKey(x => new {...})`), `IsRequired`, `.HasConversion<XConverter>()`, relationships **explicitly** (see gotchas), SqlServer `varbinary(N)` using the Domain constants.
3. `NLightningDbContext`: add a `DbSet` and call `Configure<Name>Entity`.
4. Generate migrations for **all three** providers (below) and commit every `Migrations/*` file, including Designer and Snapshot.
5. In Repositories: add `I<Name>DbRepository` in `src/NLightning.Domain/{Bitcoin,Channels,Node}/Interfaces` (Domain uses `Channels`, plural), implement it in `src/NLightning.Infrastructure.Repositories/Database/<Area>/` on `BaseDbRepository<TEntity>`, and add a lazily created (`??=`) property to `IUnitOfWork` (`src/NLightning.Domain/Persistence/Interfaces/IUnitOfWork.cs`) and `UnitOfWork`.

## Migrations (run from this directory)
- Full script: `./scripts/start_postgres.sh && ./scripts/start_sql.sh && ./scripts/add_migration.sh MyCamelCaseName`. It builds the 3 provider projects and runs `dotnet ef database update` / `migrations add` for each one. It needs Docker and `dotnet-ef`.
- Single provider: `NLIGHTNING_SQLITE='Data Source=./nltg.db' dotnet ef migrations add X --project ../NLightning.Infrastructure.Persistence.Sqlite`. Make sure no other `NLIGHTNING_*` var is set, because Postgres is checked first.
- Remove the last one: `./scripts/remove_migration.sh`, then revert the DbContext and entity edits by hand.
- Names must be CamelCase (dotnet format). Never copy migration files between providers: the snapshots differ.
- Runtime: migrations apply only when `Database:RunMigrations=true` (`src/NLightning.Daemon/Extensions/DatabaseExtensions.cs`, `MigrateDatabaseIfConfiguredAsync`; default written config is `false`).

## Dependency rules
- The only project reference is `NLightning.Domain` (+ EF Core/Npgsql/Sqlite/SqlServer/EFCore.NamingConventions packages). Must NOT reference Application, Infrastructure, Infrastructure.Bitcoin, Serialization, Repositories or Daemon.
- No domain logic or mapping here. `InternalsVisibleTo` gives access only to `NLightning.Infrastructure.Repositories` and `DynamicProxyGenAssembly2` (Castle/Moq proxies) (`AssemblyInfo.cs`). Add a test assembly there if it has to build entities.

## Build / test
- Build: `dotnet build src/NLightning.Infrastructure.Persistence` (repo root). CI check (`.github/workflows/dotnet.yml`): `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"`.
- Non-Docker coverage: `test/NLightning.Integration.Tests/Persistence/` (Sqlite `:memory:` round-trips via `SqliteTestDatabase` and `SqliteDbTestContext`, provider option checks, pending-model-changes and designer-diff checks for all three providers, `ChannelStateDbRepositoryTests` for the commitment state, `CommitmentStateMigrationRoundTrip` for the `AddCommitmentState` data steps and `LegacyChannelMigrationRoundTrip` for those of `PersistCommitmentNumbers`, `SplitChannelParams`, `StoreMsatBalancesAndShortChannelId` and `FlagInferredChannelParams` on seeded rows (NL-237; `MigrationSqlDialect` writes the per-provider raw inserts), shared with the Docker `PostgresTests`/`SqlServerTests`); this project has no test project of its own. Otherwise coverage comes only from the Docker e2e tests (`AbcNetworkTests.cs`, `ChannelOpeningFlowTests.cs`), which configure `Database:Provider=Sqlite` and run `context.Database.Migrate()`: `dotnet test test/NLightning.Integration.Tests --filter "FullyQualifiedName~Docker"`. Add new round-trip tests next to `SqliteTestDatabase`/`SqliteDbTestContext`.

## Gotchas
- Postgres uses snake_case (`UseSnakeCaseNamingConvention`). Sqlite and SqlServer use PascalCase. Raw SQL must handle both. `EnableSensitiveDataLogging()` is on only when `Database:EnableSensitiveQueryLogging=true` (all providers; NL-135). The design-time `NLightningContextFactory` still enables it for Postgres, which only affects `dotnet ef`.
- SQL Server `varbinary(N)` sizes must use the matching Domain constant (`CryptoConstants.CompactPubkeyLen` for pubkeys, not `TxIdLength`). `ChannelEntity.RemoteNodeId` was `varbinary(32)` until migration `FixRemoteNodeIdLength` (SqlServer only; NL-129). `test/NLightning.Integration.Tests/Persistence/PersistenceConfigurationTests.cs` asserts the SqlServer snapshot has no pending model changes, so a model edit without a SqlServer migration fails the test run.
- Convention-based shadow FKs: `PeerEntity.Channels` has no configured relationship, so EF created `PeerEntityNodeId` on channels. `ChannelEntity.ChangeAddress` created `ChangeAddressIsChange`/`ChangeAddressAddressType`. Configuring these explicitly changes the schema for all 3 providers.
- `Entities/Bitcoin/RevocationWatchEntity.cs` is NOT in the DbContext, has no key, no configuration and no migration, yet `RevocationWatchDbRepository` (empty body, `BaseDbRepository<RevocationWatchEntity>`) exists in Repositories; using it would fail at runtime. Give the entity a key and configuration before adding a DbSet.
- `State`/`Direction` on `ChannelEntity`/`HtlcEntity` are raw `byte`. Compare with `== (byte)Enum.X`, not `.Equals(Enum.X)` (boxed enum never equals a byte).
- The migration name typo `AddBlockchaisStateAndWatchedTransaction` is baked into history. Do not rename it.
- Provider migration projects set `BaseOutputPath` to this project's `bin/`, so the four projects share one output folder.
- `ChannelConfigs` is split per side since migration `SplitChannelParams` (NL-194): `Local*`/`Remote*` reserve, dust, htlc minimum, max accepted, max in flight and to_self_delay (`Local*` = what we announced). Its data step copied the old single set into both sides (`Remote*` columns are the renamed old ones), which is only approximate (a non-initiator announced the node's htlc_minimum_msat, an initiator never stored the peer's accept_channel limits), so migration `FlagInferredChannelParams` sets `ChannelConfigs.HasInferredParams` on every row that existed then (`ChannelParams.HasInferredParams`: don't enforce those limits); `test/NLightning.Integration.Tests/Persistence/ChannelMigrationDataTests.cs` runs such data steps on pre-migration Sqlite rows. Hand-written data steps go in as `migrationBuilder.Sql` between the generated operations (the designer-diff test ignores `SqlOperation`s); Postgres names are snake_case, SqlServer identifiers `[...]`.
- `ChannelDbRepository.UpdateAsync` detaches the child collections and synchronizes each child table by primary key (NL-192); a new child collection on `ChannelEntity` must be added to that sync too. HTLCs are no longer part of it: HTLC, commitment and fee-update rows are written only by `ChannelStateDbRepository`.
- `migrations add` does not connect to the database, so it works without the Postgres/SQL Server containers: from this directory, `NLIGHTNING_POSTGRES='…' dotnet-ef migrations add X --project ../NLightning.Infrastructure.Persistence.Postgres` (then `NLIGHTNING_SQLITE` / `NLIGHTNING_SQLSERVER` for the other two, one variable set at a time), after building the three provider projects in Debug (NL-233). The generated `.cs` files start with a BOM and end with a newline; run `dotnet format` before committing.
- Migration `AddCommitmentState` data steps (hand-written SQL at the end of `Up`): the scaffolder turned `AddMessageBytes` into `OnionRoutingPacket` (the onion is cut out at byte offset 86, empty for pre-onion rows) and `Signature` into `Sha256OfOnion` (Postgres `sha256of_onion`) or, on SqlServer, `FailReason`; the step nulls that column. It also copies the remote key set's point into `Channels.RemoteNextPerCommitmentPoint` for channels past channel_ready (NL-232). No commitment rows are created for existing channels.

## Onion routing (BOLT 4) hooks
- The onion is persisted raw in `HtlcEntity.OnionRoutingPacket` (1366 bytes, `varbinary(max)` on SqlServer) and the incoming HTLC's Sphinx shared secret in `HtlcEntity.OnionSharedSecret` (written only by `ChannelStateDbRepository.SetOnionSharedSecretAsync`).
- Done (`AddInvoicesPaymentsAndCircuits`): forward circuits, invoices, payments with per-hop shared secrets, and the per-HTLC origin. Still to add, each as a new entity plus 3 migrations: failure reasons/messages; a persistent replay set (NL-078); an SCID to ChannelId map for hop-payload `short_channel_id` (our scid aliases already live in `ChannelLocalAliases`, keyed by the alias, the peer's alias in `Channels.RemoteAlias` and the real scid in `Channels.ShortChannelId`); and, later, BOLT 7 graph tables for route building.
- `ChannelEntity.ChangeAddressType` is a separate, redundant column; the real FK to `WalletAddresses` is (`ChangeAddressIndex`, shadow `ChangeAddressIsChange`, shadow `ChangeAddressAddressType`). `ChannelDbRepository` writes both.
