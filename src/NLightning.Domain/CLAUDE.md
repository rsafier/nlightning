# NLightning.Domain — agent guide

## Purpose
This is the pure domain layer: it holds value objects, models, wire-message models, and the interfaces that the outer layers implement. It uses the BCL only. There are **no** PackageReference or ProjectReference entries in `NLightning.Domain.csproj`. It targets net10.0 via `src/Directory.Build.props`. Serialization, crypto, persistence and DI all live in the outer layers.

## Layout (folder = namespace `NLightning.Domain.<Folder>...`)
- `Protocol/`: the wire model. It contains `Constants/MessageTypes.cs` (the ushort enum), `TlvConstants.cs`, `Messages/` (one sealed class per message), `Payloads/`, `Tlv/` (BaseTlv plus typed TLVs, and `TruncatedInt`: the one strict BOLT 1 tu16/tu32/tu64 codec, shared with the Infrastructure converters), `Models/TLVStream.cs` (the `TlvStream` class), `Models/CommitmentNumber.cs`, `Models/PerCommitmentIndex.cs`, `ValueObjects/` (BigSize, ChainHash, BitcoinNetwork) and `Interfaces/`. `Interfaces/` mixes the message contracts with key, secret, dust and transport services.
- `Channels/`: `Models/ChannelModel.cs` (aggregate), `Enums/ChannelState.cs`, `ValueObjects/` (ChannelId, ShortChannelId, Htlc, ChannelParams/ChannelParty, CommitmentKeys), `Factories/ChannelFactory.cs`, `Validators/ChannelOpenValidator.cs`, and the repository/manager interfaces. `Channels/Commitments/` is the pure BOLT 2 commitment state machine (see the section below).
- `Bitcoin/`: value objects (TxId, BitcoinScript, Witness), the `Transactions/` models, the `*ModelFactory` classes and the `*OutputInfo` types, plus ports (ILightningSigner, IFeeService, the Db/Memory repositories).
- `Crypto/`: CompactPubKey, PrivKey, Hash, Secret, CompactSignature, `CryptoConstants`, `ISha256` (hash through the one-shot `Sha256Extensions.ComputeHash`, which resets the state on failure) and `Interfaces/ISecp256K1Math` (EC tweak-mul/add port, implemented in Infrastructure.Bitcoin).
- `Protocol/Onion/`: BOLT 4 onion types (see the Onion routing section below).
- `Protocol/OnionMessages/` (BOLT 4 onion messages, plan `docs/agents/BOLT12_PLAN.md` wave M6): the M6-0 records and ports (`OnionMessageTlvs`, `OnionMessageTlvRecord`, `OnionMessageContents`, `WireBlindedPath`, `SciddirOrPubkey`, `Interfaces/IOnionMessage*`) and the pure OM0 codecs, all public and span-based, `TryX(..., out reason)` plus a throwing `Decode` (`FormatException`): `SciddirOrPubkeyCodec` (0/1 + SCID or a 02/03 point, any other first byte refused), `BlindedPathCodec` (one `blinded_path` (`TryRead` leaves trailing bytes, `TryDecode`/`Decode` need an exact fit) or a BOLT 12 `blinded_path*` list (`TryReadList`/`EncodeList`); `num_hops` 0, an `enclen` past the end and bad point prefixes refused, points not curve-checked; `TryToBlindedPath`/`ToBlindedPath(path, resolvedFirstNodeId)` map to M5's `BlindedPath`), `OnionMessageTlvsCodec` (strict `onionmsg_tlv`: increasing types, canonical bigsize, known 2/4/64/66/68, unknown even refused, unknown odd kept in `OtherRecords`; `Encode` sorts every record; `CountPayloadFields` counts types from 64 up, OM-R-07) and `MessagePathRecipientDataRules` (reader: `TryValidateNonFinalPayload`/`TryValidateFinalPayload` on the `onionmsg_tlv`, `TryValidateForReader` on the decrypted `BlindedRecipientData` (any `allowed_features` bit, non-final `path_id` or no next hop; both next hops present is valid, `next_node_id` wins; `payment_relay`/`payment_constraints` have no reader rule); creator: `TryValidateForWriter` (OM-S-04)). Every reader failure means ignore the message (no error replies). Ports of the onion-message crypto (NL-442, moved from Infrastructure.Bitcoin): `Interfaces/IOnionMessageUnwrapper` (`UnwrapAsLocalNode`/`Unwrap` → `OnionMessageUnwrapResult`: `Enums/OnionMessageUnwrapStatus` Ignored/Forward/Deliver, `IgnoreReason` text and `IgnoreKind` = `Enums/OnionMessageIgnoreReason` for metrics; its `internal` factories are for Infrastructure.Bitcoin) and `Interfaces/IBlindedMessagePathBuilder` (`CreatePath`, `CreateMessagePath`), both implemented in `Infrastructure.Bitcoin/Onion/OnionMessages/`. Tests in `test/NLightning.Domain.Tests/Protocol/OnionMessages/` (vector values in `OnionMessageVectorValues`).
- `Node/`: `FeatureSet.cs` (BOLT 9), `Options/FeatureOptions.cs` and `NodeOptions.cs`, and the peer interfaces. `NodeOptions.EnableHtlcs` is `bool?` (unset = on, on every network including mainnet since the BOLT 5 O6-T4 decision in gossip wave G-D; `false` turns HTLCs off); always read the effective `HtlcsEnabled`. `NodeOptions.ReconnectInitialDelay`/`ReconnectMaxDelay` (default 5 s / 10 min) are the reconnect backoff knobs, and `NodeOptions.Routing` is `Options/RoutingOptions` (bound from `Node:Routing`: fee base (`uint`, u32 as in channel_update / BOLT 11 hints)/ppm, `CltvExpiryDelta` >= 34 (default 40), `MaxCltvExpiryDistance` 2016, `ExpiryTooSoonBlocks` 18, `InvoiceMinFinalCltvExpiry` >= 18 (default 40), invoice expiry, HTLC min/max). `NodeOptions.FeeUpdates` is `Options/FeeUpdateOptions` (`Node:FeeUpdates`: `Enabled`, `Interval` 10 min, `ThresholdPercent` 20, `NonAnchorFeerateMarginPercent` 200 (>= 100), `MinFeeratePerKw` >= 253 (`FeeratePerKwFloor`), `MaxFeeratePerKw` 50,000, `MaxAnchorFeeratePerKw` 2,500; used by the Application fee scheduler, N9-T1) and `NodeOptions.MaxDustHtlcExposureMsat` (`ulong?`, default 50,000 sat, null disables; BOLT 2 `max_dust_htlc_exposure_msat`, stored with each channel's first snapshot, NL-254). `NodeOptions.GetValidationErrors()` covers the reconnect delays, `Routing` and `FeeUpdates`; `FeatureOptions.GetValidationErrors()` stays separate, and the daemon's `ValidateOnStart` must call both (NodeServiceExtensions).
- `Gossip/` (BOLT 7 plan G0-T4/G2-T1, pure): `Addresses/` (`AddressDescriptor` (type 1-5, address bytes, port; `FromHost`/`FromIpAddress`/`FromDnsHostname` (Punycode), `Host` gives Tor as `<base32>.onion`) and the strict `AddressDescriptorCodec`: `Encode`, `DecodeSingle` (the `remote_addr` TLV, exact length, `FormatException`), `EncodeList` (sender rules: ascending types, no port 0, one DNS, no Tor v2) and `DecodeList` (receiver rules: stop at the first unknown type incl. 0, drop port 0/Tor v2/hostnames with a character other than ASCII letters, digits, `-`, `_`, `.`, extra DNS dropped and `HasMultipleDns`, truncated known type = `IsMalformed`); `RemoteAddressTlv` wraps one descriptor (NL-008)); `GossipFeatures.HasUnknownEvenBits` (wire bitmap; "known" = the odd bit is a `Feature`); `Graph/` read model: `GraphPolicy` (record, raw msat `ulong`, `FromChannelUpdate`, `ExtraData` (unknown trailing fields), `HasSameFieldsAs` (compares `ExtraData` too); value equality over every field and `ExtraData` by content, `RawUpdate` left out, NL-354), `GraphChannel` (immutable record, `node_id_1 < node_id_2` enforced, `WithPolicy`/`WithSpentAtHeight`, `IsStale` = no policy or the older one past the limit, `HasUnknownEvenFeatures`, `GraphChannelVerification` persisted as a byte: Verified 0, Unverified 1, Own 2), `GraphNode` (alias 32 / color 3 bytes, filtered addresses), `IGraphView` (dense node indices + `GetAdjacency`) and its immutable implementation `GraphSnapshot`; `Validation/GossipValidator` (the no-crypto, no-chain receiver checks of 256/257/258 over `ChannelAnnouncementFields`/`NodeAnnouncementFields`/`ChannelUpdatePayload` with a `GossipValidationContext` (chain, clock, tip, 6 confirmations with a 1-block tolerance, 14-day future skew, 2-week stale, blacklist); results carry `Outcome` Accept/Ignore/Warn, `Reason`, the `B7-*` requirement id, `Forwardable`, `Routable`, `MayBlacklist` (set only when the caller passes `signaturesVerified: true` after stage 3 verified the message's signatures, and for a 256 only when the node ids differ, never from an unverified stage-1 call); an unknown even feature in a 256 is accepted as not routable, BOLT 7 wording). `Routing/Pathfinding/` (G4-T1, pure): `GraphPathfinder.FindPath/FindPaths(IGraphView, PathfindingRequest, k)`: backward Dijkstra from the payee with exact per-hop amounts (`ForwardingFee`) and CLTV deltas (relative to the height), cost `PathCostModel` (fee + CLTV risk + probability penalty, D6), probabilities from `LiquidityEstimates` (uniform bounds decayed with a half-life, prior 0.6; not thread-safe, pass a `Clone`), request limits (max hops 20, max total CLTV, max fee, exclusions, `PolicyOverrides` for failure updates (D9), `ExtraEdges` for private channels and route hints, `LocalChannels` live state that overrides our own `disable` bit and stale check, stale check, target unknown-even-feature gate), shadow CLTV (`ShadowCltv.ComputeOffset` random walk, cut to the limit), k diverse paths by penalizing earlier paths' edges; one label per node, so when a hop/CLTV/fee limit pruned a failed search it reruns ordered by that dimension first (exact for a single limit); `GraphPath.ToRoutingInfos()` gives the BOLT 11 `r`-shaped entries after our first channel. About 6 ms per query on a 50k-channel synthetic graph (Release, M-series).
- `Offers/` (BOLT 12, plan `docs/agents/BOLT12_PLAN.md`; `Interfaces/`, `Models/` requests/results and `OfferModel` are the B12-0 contracts; codecs from lane B12-A, B0): pure BCL codecs. `Bolt12TlvStream` (raw records in wire order: `Parse`/`TryParse(bytes, out stream, out reason)` = BOLT 1 only (increasing types, minimal BigSize, lengths), `Encode`, `EncodeRecord`, `Filter`, `ContentEquals` for the "exactly match" rules) and `Bolt12TlvStreamBuilder` (typed setters `SetTu64/SetTu32/SetUtf8/SetPoint/SetChains/SetPaths/SetPayInfos/SetFallbacks/SetBip353Name`, `new(stream, keep?)` copies received records incl. unknown ones, sorted on `Build`). Typed views `Offer` (`Fields`: `OfferFields`), `InvoiceRequest` (`OfferFields`, `Fields`: `InvoiceRequestFields`, `Signature`, `GetOfferStream()`), `Bolt12Invoice` (+ `InvoiceFields`, `GetInvoiceRequestStream()`), `InvoiceError` (ctor enforces the writer rules, parse is lenient: the spec reader is "FIXME"): `TryParse(stream | bytes | string, out view, out Bolt12Violation)` enforce the format (message ranges first, B12-ENC-04; unknown even types, B12-ENC-03; value formats incl. strict UTF-8, tu64/tu32, 64-byte signature and points on the curve via `Encoding/CompressedPointValidator` (BigInteger, no secp256k1 lib); a `blinded_path` with `num_hops` 0 is the message's reader id: OFR-03/IRQ-02/INV-03); unknown odd types stay in `Stream`. Strings: `Encoding/Bolt12Bech32` (bech32 without checksum or length limit, `+`/whitespace joins, either case never mixed, padding <= 4 zero bits); `Offer` reads/writes `lno`, `InvoiceRequest` `lnr`, `Bolt12Invoice` reads CLN's `lni` only. `Encoding/Bolt12TlvRanges` (`IsOfferField`, `IsInvoiceRequestField` (also the invoice's must-match part), `IsInvoiceField`, `IsSignatureField` 240-1000). `Encoding/Bolt12FieldCodec` (`FindUnknownEvenBit`/`IsBitSet` on big-endian feature bitmaps, list encoders). Validators (pure, return the first `Bolt12Violation(RequirementId, Reason, Field?)`, ids in `Validators/Bolt12RequirementIds`): `OfferValidator` (B12-OFR-03; `now`/`supportedChains` optional, null skips), `InvoiceRequestValidator` (B12-IRQ-02/04, B12-SIG-03: signature required only for an offer response, since a refund writer "MUST NOT include signature"; fail closed: a currency offer without a converter, or amount x quantity over u64, is rejected; `GetExpectedAmountMsat` returns null when it cannot compute; odd signature-range elements besides `signature` are ignored; offer match, arrival path and the signature itself are the handler's), `InvoiceValidator` (B12-INV-03, SIG-03; `ValidateAgainstRequest` = B12-INV-04 without signature/arrival path, `expectedNodeId` required for a paths-only offer (rejected without it); `GetUsablePathIndexes`, `AllowsMultiPart`/`RequiresMultiPart` (bits 16/17), `IsExpired`; `FallbackAddress.IsUsable`). `Signing/Bolt12MerkleTree` (`ComputeRoot`, `ComputeLeaves`, `GetSignatureDigest(tag, root)` = the BIP-340 message, `TaggedHash`); byte-exact against `signature-test.json`. Gotcha: the namespace `NLightning.Domain.Offers.Encoding` hides `System.Text.Encoding` inside `NLightning.Domain.Offers.*` (and test namespaces ending in `Offers.Encoding`): write `System.Text.Encoding.UTF8` there. Tests: `test/NLightning.Domain.Tests/Offers/`, vectors in `test/NLightning.Integration.Tests/BOLT12/` (loader `Tests.Utils/Vectors/Bolt12Vectors.cs`).
- `Payments/` (ABCD W0-C contracts; implementations come in later waves): `Models/` (`InvoiceModel`, `PaymentModel`, `ForwardCircuitModel` with forward-only status mutators and a validating `Restore` for persistence; `PaymentModel.Route` is the onion's route as `PaymentHop`s (node, scid, amount, CLTV, Sphinx shared secret; last hop = payee; optional ctor/`Restore` argument, empty when not recorded) so `HopSharedSecrets` can decrypt a failure after a restart; `ForwardingRequest`/`OutgoingChannelInfo`/`ForwardingDecision` for `IForwardingPolicy`; `PayInvoiceOptions` (per-call timeout, fee limit, part limit; NL-270) and `PayInvoiceResult` (the payment plus the call's HTLC attempts and most parts in flight) for the `IPaymentService.PayInvoiceAsync` overload that retries and splits), `Enums/` (persisted status bytes, never renumber), `ValueObjects/HtlcOrigin` (what an outgoing HTLC belongs to: `Local(paymentHash)` = kind 1 or `Forwarded(incomingChannelId, incomingHtlcId)` = kind 2; kind 0 is reserved so `default(HtlcOrigin).IsValid` is false and `OfferHtlcAsync` refuses it). `OfferHtlcAsync` saves the add and then returns the id, so the payment's/circuit's record of that id is a later save: a crash in between leaves a live HTLC whose circuit is still `Pending` (resolve it with `MarkFulfilled/MarkFailed(outgoingChannelId, outgoingHtlcId, at)`, valid from Pending) or whose payment has no `OutgoingHtlcId`; never fail either without first checking that no channel HTLC carries its origin. One stored payment per hash: a retry of a `Failed` payment replaces it, `Policies/ForwardingFee` (the BOLT 7 fee formula, 128-bit intermediate, rounded down) and `Interfaces/` (`IInvoiceDbRepository`, `IPaymentDbRepository`, `IForwardCircuitDbRepository` (staged writes, committed with `IUnitOfWork.SaveChangesAsync`; implemented in `Infrastructure.Repositories/Database/Payment/`, reached through `IUnitOfWork`), `IInvoiceService`, `IPaymentService`, `IForwardingPolicy`). Each interface's XML docs state its contract (persist before send, when it completes, which events resolve it).
- `Channels/Interfaces/IChannelOperations`: the only way payments/switch/IPC change a channel's HTLCs or feerate (offer/fulfill/fail/fail-malformed/update_fee/record onion secret). Contract in its XML docs: take the channel lock (callers hold none), check `HtlcsEnabled` + usable channel + engine rules (else `CommitmentRefusedException`, nothing persisted), persist the transition (and the `HtlcOrigin`) in one save, then enqueue; resolutions come back as channel domain events. The `FulfillHtlcAsync(..., Func<IUnitOfWork, Task> stageWithFulfill, ct)` overload stages the caller's writes (the final hop's invoice `Settled`, NL-253) in the fulfill's own save. `Exceptions/ChannelFailedException` (`FailedChannelId`, `MustBroadcast`, `RequirementId`) is the "send error and fail the channel" signal; the catcher persists `ChannelState.Failed` (35) and the error before sending it. Its `PeerMessage` is never blank (defaults to `DefaultPeerMessage`, "channel failed"). It derives from `ChannelErrorException`, so until N6-T3 adds a `catch (ChannelFailedException)` ahead of the generic handlers in PeerManager/ChannelManager, throwing it takes the old send-error-and-disconnect path without persisting Failed; don't throw it before then.
- `Channels/Policies/HtlcDeadlinePolicy` (BOLT2 plan N9-T2): pure BOLT 2 HTLC deadlines. `Evaluate(HtlcRecord, height, IncomingHtlcResolution)` → `HtlcDeadlineDecision(Action, RequirementId, DeadlineHeight)`: an offered HTLC in either commitment at `cltv_expiry + GraceBlocks` (2) → `FailChannel` (B2-CLTV-03); a received HTLC we fulfilled in either commitment, or locked in with its preimage known (`PreimageKnown`), at `cltv_expiry - FulfillSafetyBlocks` (18) → `FailChannel` (B2-CLTV-06); a locked-in, unremoved, `Unresolved` one at `cltv_expiry - FailBackBlocks` → `FailBackUpstream` (B2-FWD-03/CLTV-05); an `UnresolvedFinalHop` one (never forwarded, no preimage: the switch may still settle it) at the fulfillment deadline `cltv_expiry - FulfillSafetyBlocks` → `FailBackUpstream` (B2-CLTV-05; the forwarding distance would fail a payer's final HTLC, which is only about `min_final_cltv_expiry` away, almost at once); `AwaitingDownstream` never acts. `FailBackBlocks >= FulfillSafetyBlocks` is enforced. `ChannelSigningInfo.DataLossDetected` (from `ChannelModel.GetSigningInfo`) and `ILightningSigner.SignLocalCommitmentForBroadcast`/`MarkDataLoss` are the N9-T4 signer contract.

## Dependency rules
- Do NOT reference NBitcoin, libsodium, EF Core, Microsoft.Extensions.* or any other src project. Keep the code library-free.
- Declare interfaces here and implement them outward: Infrastructure, Infrastructure.Bitcoin, Infrastructure.Serialization, Application.
- Internals are exposed through `AssemblyInfo.cs`, which lists Application, Infrastructure(.Blazor/.Bitcoin/.Serialization), Infrastructure.Serialization.Tests, Infrastructure.Tests, Tests.Utils and `DynamicProxyGenAssembly2` (Moq proxies). **`NLightning.Domain.Tests` is not in that list**, so Domain tests can only use the public API.
- Domain has no DI of its own. Its factories and validators are registered in `AddApplicationServices` (`src/NLightning.Application/DependencyInjection.cs`); the rest in each layer's `DependencyInjection.cs`, composed by `NodeServiceExtensions.AddNltgNodeServices`.

## Conventions
- Namespaces are file-scoped. The prevailing style puts project `using` lines *after* the namespace line, written relative to the enclosing namespace (for example `using Money;` inside `NLightning.Domain.Channels.Models`). System usings go above the namespace line. Some files (e.g. `Bitcoin/Transactions/**`) instead use fully qualified `using NLightning.Domain...` above the namespace.
- Byte-backed value objects are mostly readonly structs or record structs over `byte[]` (`CompactSignature` is a `record` class). They validate length in the constructor and provide implicit conversions to and from byte[]/Span/Memory. `Hash`, `TxId`, `ChainHash`, `CompactSignature` and `BaseTlv` compare content with `SequenceEqual`; `Secret` and `PrivKey` compare in constant time (`CryptographicOperations.FixedTimeEquals`). All hash with the null-safe `GetByteArrayHashCode()` (`Utils/Extensions/ByteArrayExtensions.cs`), so `default(...)` values hash to 0; `ShortChannelId` hashes its parsed fields. `Hash`/`Secret`/`TxId`/`PrivKey` require exactly 32 bytes. `CompactPubKey` converts implicitly from `ReadOnlySpan<byte>` (so `byte[]` still converts, as a copy) rather than from `byte[]`, so `cond ? null : key` is `CompactPubKey?` instead of a runtime NullReferenceException.
- Models are classes with private setters and `UpdateX`/`AddX` mutators. `AddX` throws if the value is already set.
- Protocol failures throw `ChannelErrorException` (connection is usually closed) or `ChannelWarningException`. Only the exception's `PeerMessage` property is sent to the peer (see `src/NLightning.Infrastructure/Node/Services/PeerCommunicationService.cs`); the `Message` stays local.
- Build amounts with `LightningMoney.Satoshis(..)` or `MilliSatoshis(..)`. A raw `ulong`/`long` converts implicitly as **msat**.
- Mark Constants classes and exceptions `[ExcludeFromCodeCoverage]`. Name tests `Given_X_When_Y_Then_Z` (xUnit + Moq).
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate. The `.editorconfig` rules are at error severity, including `_field`/`s_field` naming.

## Adding a wire message (most common change)
1. Add the value to `Protocol/Constants/MessageTypes.cs`.
2. Add `Protocol/Payloads/XPayload.cs`, implementing `IChannelMessagePayload` (or `IMessagePayload`).
3. Add `Protocol/Messages/XMessage.cs` as a `sealed class : BaseChannelMessage` with `public new XPayload Payload => (XPayload)base.Payload;`. Build `Extension = new TlvStream(); Extension.Add(tlvs...)` only when a TLV is non-null.
4. For new TLVs: add a `TlvConstants` entry, add `Tlv/XTlv.cs : BaseTlv`, add a converter in `src/NLightning.Infrastructure/Protocol/Tlv/Converters`, and register it in `TlvConverterFactory` (`TlvStreamSerializer` looks converters up by runtime type).
5. Add the payload serializer and message-type serializer, registered in both dictionaries of both `PayloadSerializerFactory` and `MessageTypeSerializerFactory`.
6. Add `Create*` to `Protocol/Interfaces/IMessageFactory.cs` and implement it in `src/NLightning.Application/Protocol/Factories/MessageFactory.cs`.
7. Route the message: add a `case` to the `switch` in `src/NLightning.Application/Channels/Managers/ChannelManager.cs` `HandleChannelMessageAsync` (~line 88) plus an `IChannelMessageHandler<T>` (`src/NLightning.Application/Channels/Handlers/Interfaces/IChannelMessageHandler.cs`). Without these, the `default` branch throws a channel-scoped `ChannelWarningException` (message ignored, `warning` sent, connection kept). Add a round-trip test in `test/NLightning.Infrastructure.Serialization.Tests/Messages`.

## Gotchas
- `TlvConstants` numbers are scoped per message: 0 and 1 are each reused several times. Use the semantically correct constant, and never mix TLVs from different namespaces in one `TlvStream`.
- For FeeRangeTlv, `Value` is not the wire bytes (`RemoteAddressTlv.Value` is, since NL-008, and `FundingOutputContributionTlv.Value` is since wave sp1). Always go through the ITlvConverter. `FundingOutputContributionTlv` (tx_init_rbf/tx_ack_rbf type 0) is an **s64**: `long Satoshis` (negative for a splice-out RBF); the `LightningMoney` constructor stays for non-negative amounts, and the old `Amount` property is gone.
- File name ≠ type name for `Models/TLVStream.cs`, `Tlv/NetworksTLV.cs` and `Tlv/RequireConfirmedInputsTLV.cs`.
- `ChannelModel.UpdateState` accepts only strictly increasing `ChannelState` values, and additionally forbids moving into `V2Opening` from any V1 state or leaving `V2Opening` downward. Number any new state with that in mind (current values: 0,1,2,3,10,20,21,22,23,25,30,35,37,40,50; `ShuttingDown = 23` and `Negotiating = 25` sit between `Open` and `Closing`, `Failed = 35` and `OnchainResolving = 37` (BOLT 5 plan O1-T2: a commitment is on chain and its outputs are being resolved; set by the Application `OnchainChannelWatcher` since ABCD W5) between `Closing` and `Closed`).
- Networks (ABCD W4-D): `BitcoinNetwork` names are lower-cased; `ChainHash` knows mainnet, testnet (testnet3; the constant had 4 garbled bytes until W4-D), regtest and signet (`ChainConstants.Signet`, genesis `00000008...1ef6` reversed) plus registered custom networks, and throws otherwise. Read configured names with `BitcoinNetwork.Resolve(name)`, which throws `ArgumentException` for an unknown name (never fall back to mainnet). Custom signets (Mutinynet, `NetworkConstants.Mutinynet`, registered by default; others through `Node:CustomSignet:Name` = `CustomSignetOptions.Register()` or the static `BitcoinNetwork.RegisterCustomSignet`) resolve to `Signet`, and `new BitcoinNetwork("mutinynet")` is `Signet` too: same chain hash, `tb` addresses, `tbs` invoices. `BitcoinNetwork.Register(name, chainHash)` is static (it was an instance method). The registries are process-wide; tests that register a name should `Unregister` it.
- `ShortChannelId(ulong)` uses the BOLT 7 widths (block 24 bits, tx index 24 bits, output 16 bits; NL-101).
- `CommitmentNumber(openerPaymentBasepoint, accepterPaymentBasepoint, sha256)`: BOLT 3 obscuring is SHA256(opener || accepter), so pass the funder's basepoint first regardless of which side is local (`ChannelDbRepository` reload orders them by `IsInitiator`, NL-127). It is an immutable per-channel **obscuring helper** with no value of its own: `Obscure(n)`, `LockTime(n)`, `Sequence(n)` (n is a 48-bit commitment number, `MaxValue`). The numbers live on the channel: `ChannelModel.LocalCommitmentNumber` / `RemoteCommitmentNumber` (both 0 after the open, independent of each other, never changed at funding confirmation; NL-188). `ICommitmentTransactionModelFactory.CreateCommitmentTransactionModel(channel, side, commitmentNumber)` takes the number explicitly and `CommitmentTransactionModel.Number` carries it. For `Remote` that convenience overload uses `RemoteKeySet.CurrentPerCommitmentCompactPoint` and throws `InvalidOperationException` unless `RemoteKeySet.CurrentPerCommitmentIndex` is the index of that number (the point is commitment 0's during funding and commitment 1's after channel_ready); build any other remote commitment with the `CommitmentTxSpec` overload and an explicit point.
- Commitment numbers vs per-commitment indices (NL-187): numbers count up from 0, BOLT 3 secret indices count down from 2^48-1. `PerCommitmentIndex.From(n) = 2^48-1-n` (and `ToCommitmentNumber`). Every `ILightningSigner` per-commitment API (`GetPerCommitmentPoint`, `RevealPerCommitmentSecret`, `AdvanceLocalCommitment`) and `ICommitmentKeyDerivationService.DeriveLocalCommitmentKeys` take **numbers**; only the signer converts to an index. `RevealPerCommitmentSecret(channelId, n)` is guarded: it throws unless `n < ` the signer's local commitment number (`ChannelSigningInfo.LocalCommitmentNumber` at registration, then `AdvanceLocalCommitment` after each persisted local commitment; NL-189). `CommitmentKeys` has no secret. HTLC signatures: `SignRemoteHtlcTransactions`, `ValidateLocalHtlcSignatures`, `SignLocalHtlcTransaction` over `Bitcoin/Transactions/Models/HtlcSigningContext` (NL-057); `ChannelSigningInfo.RemoteHtlcBasepoint` is needed for validation, and `ChannelModel.GetSigningInfo()` fills it and the local number. `CommitmentTransactionModel.PerCommitmentPoint` is the holder's point (set by the factory). channel_ready's second point is `GetPerCommitmentPoint(channelId, LocalCommitmentNumber + 1)`. `ChannelKeySetModel.CurrentPerCommitmentIndex` is still an index (remote side: updated by channel_ready). The peer's revealed per-commitment secrets have one source only: the shachain (`ISecretStorageService` Insert/Export/Load + `IRemoteShachainDbRepository`). `ChannelKeySetModel.LastRevealedPerCommitmentSecret` and its column were dropped by migration `AddCommitmentState` (NL-238).
- `ChannelModel.Commitments` (N5) holds the engine snapshot (`ChannelCommitments?`, null until the wiring creates one), plus `SentCommitDiff`, `LastSentCommitmentMessage` (`Channels/Enums`), `ErrorSent` and `DataLossDetected` (`MarkErrorSent`/`MarkDataLossDetected`). Swap it only with `UpdateCommitments(next, ChannelStateExtras?)` **after** the transition was saved (I2). While a snapshot is set, `LocalBalance`/`RemoteBalance`, the next HTLC ids and the commitment/revocation numbers are read from it. Build the engine's `CommitmentParams` with `CommitmentParams.FromChannel(channel, maxDustHtlcExposureMsat?)` only (it carries `HasInferredLimits`; the old `ChannelModel.ToCommitmentParams` dropped it and was removed). Persistence port: `Channels/Interfaces/IChannelStateDbRepository` (`InitializeAsync`, `ApplyAsync(next, transition, extras)`, `LoadAsync` → `Models/PersistedChannelState` with the settled-HTLC archive and the shachain, onion shared secret get/set, `PruneSettledHtlcsAsync`); `IUnitOfWork.ChannelStateDbRepository`. `IHtlcDbRepository` is gone, and the legacy `Htlc` collections on `ChannelModel` are no longer persisted (always empty after a reload).
- `ChannelModel.LocalBalance`/`RemoteBalance` are **gross**: they still include that side's own pending offered HTLCs. `CommitmentTxSpec.FromChannel` (`Channels/Commitments/CommitmentTxSpec.cs`) takes each HTLC out of its offerer's balance to produce the **net** spec (`ToLocalMsat`/`ToRemoteMsat` from the local node's view, `FeeRatePerKw`, `Htlcs`; `Outgoing` = offered by us). The future update_add_htlc flow must not deduct an HTLC at add time (it would be subtracted twice); move the amount only when the HTLC is fulfilled or failed.
- `CommitmentTransactionModelFactory` has two entry points: `(channel, side, number)` (spec from the channel, remote point from `RemoteKeySet.CurrentPerCommitmentCompactPoint`) and the spec-driven `(channel, CommitmentTxSpec, side, number, remotePerCommitmentPoint)` (N2-T2): the channel supplies only static data (keys, funding output, obscuring factor, dust limits, to_self_delay, anchors, funder). The remote side **requires** the point, the local side rejects one (its point comes from the signer by number). Fees and trimming go through the static `Bitcoin/Transactions/Factories/CommitmentFeeCalculator` (724/1124 + 172 per untrimmed HTLC, HTLC fees 663/703 or **0 with anchors**, funder pays fee + 2x330 anchors, amounts rounded down). The factory never checks the channel reserve (NL-196; that is an update-validation rule); `ChannelOpenValidator` rejects an open_channel whose initial to_local and to_remote are both <= channel_reserve_satoshis (NL-220). The model carries `FeeRatePerKw`, `HasAnchors`, `ToSelfDelay`, `LocalDelayedPubKey`, `RevocationPubKey` for building HTLC transactions.
- `FeatureSet.DeserializeFromBytes` copies its input (it used to reverse the caller's array in place, which also scrambled `ChannelTypeTlv.Value` for multi-byte channel types). `new FeatureSet()` sets 5 compulsory bits: data_loss_protect, var_onion_optin, static_remote_key, payment_secret, channel_type. BOLT 9 dependencies and per-context masks (`Enums/FeatureContext`: I/N/C/9/B/T) live in `FeatureSet` (`GetDependencies`, `GetContexts`, `FilterByContext`); `FeatureOptions.GetNodeFeatures(context)` filters (default `Init`) and `GetValidationErrors()` is enforced at daemon start. Dependencies on ASSUMED features are deliberately not encoded, except zero_fee_commitments -> option_channel_type (still listed by BOLT 9). `IsCompatible` checks both sets' dependencies, treats ASSUMED features (0, 8, 12, 14, 44) the peer omits as set optional, and records a feature as Compulsory if either side requires it and Optional if both only support it, so callers' `negotiatedFeatures.X == Compulsory` branches are live. `ChannelTypeTlv` holds big-endian wire bytes: build it with `new ChannelTypeTlv(featureSet)` or `featureSet.GetWireBytes()`, never `GetBytes()` (little-endian).
- `ChannelModel.ChannelParams` (NL-194) holds `Local` (the `ChannelParty` values **we** announced) and `Remote` (the peer's), plus shared feerate, minimum depth, anchors and scid-alias use. Direction: `Local.HtlcMinimum/MaxAcceptedHtlcs/MaxHtlcValueInFlight` bind HTLCs the peer offers us; `Local.ChannelReserveAmount` is what the **peer** must keep; our commitment uses `Local.DustLimitAmount` and `Remote.ToSelfDelay`, the peer's uses `Remote.DustLimitAmount` and `Local.ToSelfDelay` (`CommitmentTransactionModelFactory`). The initiator's `Remote` is `ChannelParty.Unknown` until accept_channel (`UpdateRemoteParams`). `ToChannelType()` is the channel_type the initiator sends; the non-initiator echoes the opener's bytes. `ChannelOpenValidator` accepts only channel_type bits 12, 22, 46, 50 (and 46 only when scid_alias was negotiated). Upfront shutdown scripts live on the parties (`ChannelModel.Local/RemoteUpfrontShutdownScript` just forward).
- `FeatureSet.GetBytes` used to drop a highest set bit at a multiple of 8 (e.g. channel_type bit 40); fixed. `GetSetBits()`/`HasSameBits()` compare bit sets regardless of bitmap length.
- `LightningMoney` is a mutable reference type (NL-202; the commitment engine uses checked `ulong` msat instead). The `-` operator throws on underflow.
- The `protected internal BaseMessage(MessageTypes)` constructor installs `PlaceholderPayload`, whose `ChannelId` throws. `Error` and `Warning` messages are not `IChannelMessage`; `StfuMessage` is a `BaseChannelMessage` since the Q-0 contracts (splicing plan D3) and takes the channel path: `ChannelManager` routes it to the Application `StfuMessageHandler` under the channel's lock (Q1-T1, NL-019).

## Commitment state machine (BOLT 2 plan N4): `Channels/Commitments/`
Pure engine (no I/O, persistence or crypto), namespace `NLightning.Domain.Channels.Commitments`; tests in `test/NLightning.Domain.Tests/Channels/Commitments/`. Not wired into handlers yet (N5 persists it, N6 wires it).
- `Channels/Enums/HtlcState` holds core-lightning's `htlc_state`: 10-19 (we offered), 30-39 (they offered). Legacy values 0-3 (`Offered/Fulfilled/Failed/Expired`) still exist for old rows and are rejected by the machine. `HtlcStateTable` is the only place transitions live: `Next(state, HtlcEvent)` (throws `HtlcStateTransitionException : ChannelErrorException`), `TryNext`, and the flags `IsInLocalCommit/IsInRemoteCommit/IsRemovedFrom/IsRemoval/IsFinal/IsAddIrrevocablyCommitted/Owner`. Six events only: SendCommit, RecvCommit, SendRevoke, RecvRevoke, SendRemove, RecvRemove.
- `ChannelCommitments` (not `Commitments`, which would clash with the namespace) is an immutable `sealed record` snapshot: settled balances (msat, `ulong`, checked; open HTLCs stay in the offerer's balance, `Local + Remote == funding`), `Htlcs` (`ImmutableSortedDictionary<HtlcKey, HtlcRecord>`, key = direction + id), `FeeUpdates` (same state set, owner = funder; a commitment's feerate is the last update in it, a final one prunes older ones), next HTLC ids (start at 0), `LocalCommit`, `RemoteCommit`, `RemoteNextCommit` (unacked; blocks signing, D7) and `RemoteNextPerCommitmentPoint`. Build with `Create(...)` (after open) or `Restore(...)` (from persistence; validates states, owners, ids and balances).
- Every operation returns `CommitmentsResult { Next, Outbound, Transition, Events }` and never mutates the receiver: `SendAdd/ReceiveAdd`, `SendFulfill/SendFail/SendFailMalformed`, `ReceiveFulfill/ReceiveFail/ReceiveFailMalformed` (preimage checks take an `ISha256`), `SendFee/ReceiveFee(feerate, min, max)`, `SendCommit(ICommitmentSigner)`, `ReceiveCommit(CommitmentSignatures, ICommitmentVerifier)` (also performs our revoke and returns an `OutboundRevokeAndAck(revokedNumber, nextNumber)` **placeholder**: the caller derives the secret only after persisting, I3), `ReceiveRevoke(secret, nextPoint, IRevocationVerifier)`, `RevertUncommitted()` (disconnect). `Outbound` items are engine records (`OutboundAddHtlc`, `OutboundCommitmentSigned`, ...), not wire messages. `ChannelTransition` lists upserted/settled/dropped HTLCs and which parts changed, for a single save; `ReceiveRevoke` also sets `RevokedRemoteCommit` (the peer commitment it revoked, null for every other operation), which the persistence layer writes to the revocation log in the RAA's save (BOLT 5 plan O1-T1).
- Domain events (N4-T4, invariant I8): `Channels/Commitments/Events/` holds `IChannelDomainEvent` (`ChannelId`, `HtlcId`) and five records. `IncomingHtlcLockedIn(channelId, HtlcRecord)` is raised exactly once, by the `ReceiveRevoke` that moves an incoming HTLC 33 -> 34. `OutgoingHtlcFulfilled(channelId, id, hash, preimage)` is raised by `ReceiveFulfill` at once, only the first time the preimage is learnt (a fulfill re-sent after `RevertUncommitted` raises nothing, because `KnownPreimage` survives). `OutgoingHtlcFailed(channelId, id, hash, HtlcRemoval)` is raised only by the `ReceiveRevoke` that makes an outgoing fail/fail-malformed final (state 19), never earlier. `OutgoingHtlcSettled(channelId, id, hash, kind)` is raised for every outgoing HTLC that reaches 19 (after `OutgoingHtlcFailed` for a failure). `IncomingHtlcSettled(channelId, id, hash, kind)` (ABCD W2-B, NL-243) is raised by the `ReceiveCommit` whose revoke makes our removal of an incoming HTLC final (state 39), so the switch can prune its archived row. Within one result, events are ordered by HTLC key. `ChannelDomainEvents.DerivePending(channelId, records)` / `DerivePending(commitments, unprunedSettled)` derives the still-pending events from persisted records with the same rules (incoming in 34 -> locked-in; incoming in 39 -> incoming settled; outgoing with a known preimage -> fulfilled; outgoing in 19 -> failed and/or settled). It is the startup replay: pass every open record plus the settled records not yet pruned. Consumers must therefore be idempotent. The engine's events are computed by the internal `ChannelDomainEvents.FromChange(before, after, settled)` in `Result`, so every raised event is re-derivable from the transition it came with (the simulator checks this after every step). `Channels/Interfaces/IHtlcSwitch.HandleAsync(IChannelDomainEvent, ct)` is the consumer port (no implementation yet; N6-T2).
- Local rule breaks throw `CommitmentRefusedException` (never sent to the peer); peer rule breaks throw `CommitmentViolationException : ChannelErrorException` (`MustFailChannel` for B2-RAA-R01). Both carry `RequirementId` = the `B2-*` row of the plan matrix. Update checks live in `Channels/Validators/UpdateValidator` (internal) and use "prospective" views: adds count as soon as they exist, removals only once committed in that commitment, feerate = max(current, latest pending). Receiver checks judge only what the peer provably knew when it sent the update (both directions cross): `update_add_htlc` affordability (B2-ADD-R02) and the R03 counts leave out our adds the peer has not signed yet (states 10-12) and count our removals it has acked (state 37, credited to the offerer on fail, the receiver on fulfill) as done (`peerView`, matching LND's sender view), and `update_fee` (B2-FEE-R03) is checked on our current `LocalCommit`, as BOLT 2 words it. Because these are lenient, `ReceiveCommit` makes the delayed check ("MAY delay this check until the update_fee is committed"): when the peer is the funder, the new local commitment must leave it enough for `FunderCostMsat`, else a violation (B2-FEE-R03 if the commitment carries a new feerate, else B2-ADD-R02) before any signature is verified or anything revoked. B2-ADD-S04 (non-funder sender) checks the funder's fee on both commitments ("the updated local or remote transaction"); the fee-spike buffer (B2-ADD-S03) is also applied to both; the non-funder reserve refusal is B2-ADD-S01. The two receiver fixes came from the two-engine simulator (see below).
- `HtlcRecord.KnownPreimage` holds the preimage the peer revealed with `update_fulfill_htlc` for an HTLC we offered. Unlike `Removal` it survives `RevertUncommitted` (B2-RE-04: a reverted fulfill resets the HTLC to 14 with `Removal = null` but keeps the preimage), so N5 must persist the preimage column from `KnownPreimage` (never from `Removal` alone) and must not clear it when writing an upserted row.
- `RevertUncommitted` must run on every disconnect **and** after every `Restore` before `channel_reestablish`: a restored state-30 add is otherwise kept, and `ReceiveAdd` treats the peer's compliant re-send of that id as B2-ADD-R07 (the BOLT 2 "ignore a repeated id after reconnection" path is N7's).
- BOLT 3 fees and trimming have one implementation (NL-231): `Bitcoin/Transactions/Factories/CommitmentFeeCalculator`. The `…Satoshis` members hold the formulas (ulong), the `LightningMoney` members serve the transaction factories, and the `CommitmentSpec` members (`UntrimmedHtlcCount`, `TrimmedHtlcTotalMsat`, `CommitmentBaseFeeSatoshis(spec, …)`, `FunderCostMsat`, `IsHtlcTrimmed(spec, htlc, …)`) serve the engine and `UpdateValidator`; all delegate to the same formulas, so the engine's `num_htlcs` and fees can never diverge from the built transaction.
