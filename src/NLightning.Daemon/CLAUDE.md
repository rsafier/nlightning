# NLightning.Daemon (NLTG node host)

The executable Lightning node, and the DI **composition root** for the whole stack. `Program.cs` uses top-level statements and does the following in order: reads config, handles `--stop`, `--status` and `--help`, unlocks or creates the key (`SecureKeyManager`), optionally daemonizes, builds the Generic Host, applies optional EF migrations, then runs `NltgDaemonService`. That service starts FeeService, PeerManager (BOLT 8 TCP), BlockchainMonitor and the named-pipe IPC server. The CLI (`src/NLightning.Client`) talks to it over IPC. There is no protocol logic in this project; that lives in Application and Infrastructure.*.

## Layout
- `Program.cs`: entrypoint. Sets `MessagePackSerializer.DefaultOptions = NLightningMessagePackOptions.Options` (line ~132) before building the host.
- `Extensions/NodeServiceExtensions.cs`: the single DI root. `AddNltgNodeServices(configuration, secureKeyManager)` registers the whole node graph: every layer (`AddApplicationServices`, `AddBitcoinInfrastructure`, `AddInfrastructureServices`, `AddPersistenceInfrastructureServices`, `AddRepositoriesInfrastructureServices`, `AddSerializationInfrastructureServices`), the `FeeService` HttpClient, the options, the scoped client handlers and the IPC router and command handlers. `ConfigureNltgServices(secureKeyManager, configPath)` calls it and adds only the hosted service, `NamedPipeIpcService` and `CookieFileAuthenticator` (they need `configPath`). The Docker tests call `AddNltgNodeServices` through `NLightningTestNode` (NL-156).
- `Extensions/NodeConfigurationExtensions.cs`: config path and network resolution (`BitcoinNetwork.Resolve`: an unknown `--network` throws `ArgumentException` before any directory is created; `--network mutinynet` or any custom signet named by its directory file's `Node:CustomSignet:Name` uses `~/.nltg/<name>` but returns and configures `signet`, with `Node:CustomSignet:Name` set; see `docs/agents/MUTINYNET.md`), the default `appsettings.json` template (`CreateDefaultConfigJson`: per network the bitcoind RPC port, on signets ZMQ 28332/28333, a `Node:CustomSignet` section and no DNS seeds; `FeeEstimation` with `Source`/`RateUnit` (mempool.space for the network, mutinynet.com for Mutinynet, `Fixed` on regtest; no `RateMultiplier`, NL-288); it always writes `Node:EnableHtlcs`: true on regtest and signets, and `null` on mainnet and testnet (the key stays for the operator, and null binds as unset, so `NodeOptions.HtlcsEnabled`'s code default applies: the BOLT 5 O6-T4 gate; the template test compares against that default, not a fixed value); a `Gossip` section with the BOLT 7 mainnet gate (plan D12, G5-T5): `Enabled` and `SyncEnabled` true everywhere (mainnet included since wave d12), `RelayEnabled` false on mainnet and true elsewhere, `AllowPublicChannelsOnMainnet` false and `AcceptPublicChannels` true everywhere, so on mainnet `AllowPublicChannelsOnMainnet` alone gates public channels, ours and a peer's (every value equals the code default, written so it is visible; `NodeServiceExtensionsTests.Given_DefaultConfigJson_When_Bound_Then_GossipMainnetGateIsExplicit`); and a `Node:Routing` section with every `RoutingOptions` default except `HtlcMaximumMsat`, taken from `new RoutingOptions()` so it cannot drift), and Serilog.
- `Extensions/DatabaseExtensions.cs`: migrates only when `Database:RunMigrations=true`.
- `Services/GossipGraphHostedService.cs` (BOLT 7 G2-T4/T5): registered by `ConfigureNltgServices` **before** `NltgDaemonService`, so it starts first (`GossipIngress.StartAsync`: graph load, workers, write-behind; then `GraphPruner.Start()`, subscribed before the chain monitor's first block) and stops last (pruner, then the ingress, which flushes the graph). Nothing starts while `Gossip:Enabled` is false (default on everywhere, mainnet included since wave d12, plan D12). The gossip query/sync side (BOLT 7 G3-T1/G3-T2) needs no start: `AddNltgNodeServices` calls `AddGossipSyncServices()` and binds/validates `GossipSyncOptions` (`Gossip:SyncEnabled`, `SyncPeers`, `MaxScidsPerReply`, `MaxScidsPerQuery`, `SyncReplyTimeout`, `SyncRotationInterval`, `MissedScidRetryInterval`, `SyncFilterBacklog`, `MaxQueuedQueriesPerPeer`); its timers start with the first peer and stop when the container disposes it. The relay of other nodes' gossip (G3-T3) needs no start either: `AddNltgNodeServices` calls `AddGossipRelayOriginTracking()` after `AddGossipGraphServices()` (the peer services' `IGossipIngress` becomes the origin-recording `OriginTrackingGossipIngress` over `GossipIngress`) and binds/validates `GossipRelayOptions` (`Gossip:RelayEnabled` (unset = on everywhere but mainnet, kept by the D12 decision), `RelayFlushInterval`, `RelayCollectInterval`, `RelayTickInterval`, `BacklogMessagesPerSecond`, `MaxTrackedOrigins`); the relay's timer starts with the first peer filter.
- `Services/NltgDaemonService.cs`: the main hosted service. Start order is fee, the channel key index reconciliation (`EnsureLastUsedChannelIndexAtLeast` with `IChannelDbRepository.GetHighestLocalKeyIndexAsync`, every channel row; SECURITY_REVIEW SR-19), peers, `IPaymentOutcomeHandler.ReconcileInFlightPaymentsAsync` (payments a crash left without an HTLC id, once every channel is loaded), the safety services, `IMempoolReactor.Start()` (BOLT 5 O8, subscribed before the monitor's mempool loop runs), chain monitor, the onion replay pruner, IPC; the reactor and the pruner stop before the chain monitor. Stop runs in parallel; `IPeerStorageService.StopAsync()` (writes the delayed peer blobs) runs after the peers stopped. `Node:Payments` binds `PaymentSendOptions` (default fee limit, `MaxParts`, `MaxAttempts`, `MinPartMsat`, `ExpiryTooSoonExtraBlocks` of our payments; optional).
- `Services/Ipc/`: `NamedPipeIpcService`, `LengthPrefixedIpcFraming` (IpcFraming.cs), `IpcRequestRouter` (IpcRouting.cs), `CookieFileAuthenticator`, `Factories/IpcErrorFactory`.
- `Ipc/Interfaces/` (internal): `IIpcCommandHandler`, `IIpcFraming`, `IIpcRequestRouter`, `IIpcAuthenticator`.
- `Ipc/Handlers/`: one singleton `IIpcCommandHandler` per `ClientCommand` (NodeInfo, ConnectPeer, ListPeers, GetAddress, WalletBalance, OpenChannel, OpenChannelSubscription, ListChannels, CreateInvoice, PayInvoice, ListInvoices, ListPayments, CloseChannel, ForceCloseChannel, PendingSweeps, ChainStatus, ListNodes, ListGraphChannels, GetRoute, DescribeGraph, ExportChanBackup, VerifyChanBackup, RestoreChanBackup, DisconnectPeer; next free `ClientCommand` 24). `ClientCommandIpcHandler<TIpcReq, TClientReq, TClientResp, TIpcResp>` is the base for a command served by a scoped client handler (deserialize, `CreateScope`, map both ways); the four invoice/payment handlers use it. It maps a `ClientException` to its code, a client handler that cannot be resolved (payment services not registered) to `invalid_operation` "not available on this node", and anything else to `server_error`.
- `Handlers/`: scoped `IClientCommandHandler<TReq,TResp>` classes for multi-step flows and anything that reads the database (`OpenChannelClientHandler`, `OpenChannelClientSubscriptionHandler`, `ListChannelsClientHandler`, and the invoice/payment handlers `CreateInvoiceClientHandler`, `PayInvoiceClientHandler`, `ListInvoicesClientHandler`, `ListPaymentsClientHandler` over `IInvoiceService`/`IPaymentService`). `ListChannelsClientHandler` lists the in-memory channels (live state) and then the persisted ones not in memory (closed/stale); it reports `ChannelModel.LocalCommitmentNumber`/`RemoteCommitmentNumber` (NL-188), counts pending HTLCs from the commitment snapshot (`ChannelModel.Commitments`, non-final states per direction; NL-241), reports `ChannelModel.DataLossDetected`, the node's `RoutingOptions` fee policy, and `IsReestablished` from the Domain `IReestablishTracker` (N7: true once channel_reestablish was exchanged on the peer's current connection, or the channel opened on it; memory only). Since wave sp2 (lane SP2-D) it also fills `Fundings` (IPC key 23: the current funding, the pending splices in creation order, then replaced fundings whose short channel id the optional `IRetiredScidMap` still resolves; discarded ones left out; a channel without `ChannelFundings` rows, or a unit of work that stores none, lists its funding output as the current funding) with depths from the optional `IBlockchainMonitor.LastProcessedBlockHeight` (null without it or while unconfirmed), and `RetiredShortChannelIds` (key 24) from the same map. The payment handlers validate their arguments (zero amount/expiry/timeout, `take` outside 1-1000, negative `skip`) and turn the services' `ArgumentException`/`InvalidOperationException` into `ClientException(invalid_operation)`. `PayInvoice` maps only an exact `InvalidOperationException` (the contract's duplicate-hash refusal) to `invalid_operation`; subclasses such as `ObjectDisposedException` and any other exception become `server_error` whose message says the payment may still be in flight (check listpayments), since they can happen after the HTLC was offered. `PayInvoice` waits 60 s by default (at most 300: it holds one of the `NamedPipeIpcService.MaxServerInstances` = 64 pipe instances for the whole wait; the timeout also ends the retries), passes the request's `MaxFee`/`MaxParts` (1-`PaymentSendOptions.MaxPartsLimit`, else `invalid_operation`) as `PayInvoiceOptions` to `IPaymentService.PayInvoiceAsync` (NL-270) and returns the call's `Attempts`/`Parts` with the payment, and a failed payment is a normal response, not an error. The Docker tests call these handlers directly (resolve `IClientCommandHandler<CreateInvoiceClientRequest, CreateInvoiceClientResponse>` etc. from a scope).
- `Handlers/CloseChannelClientHandler` (ClientCommand 13, BOLT2 N10): calls `IChannelCloseService` (Application) with the request's feerate, `NoFeeRange` and wait (default 30 s, at most 300 s; 0 returns once our shutdown is out); an unknown channel is `invalid_channel`, a channel that can't be closed now `invalid_operation`. `Node:Close` binds `ChannelCloseOptions` (`SendFeeRange`, `ConfirmationDepth`, `MaxFeeMultiplier`). CLI: `closechannel <channel_id> [feerate_per_kw|0] [wait_seconds] [nofeerange]`.
- BOLT 5 (ABCD W5, plan O2-T5/O3-T6): `Handlers/ForceCloseChannelClientHandler` (ClientCommand 14) fails the channel through `IChannelFailureService.FailChannelAsync` with a broadcast (`B5-FAIL-05`; the peer gets "channel force closed by the operator"); an unknown channel is `invalid_channel`, `NotApplicable` (not funded, in a mutual close (`Closing`), closed, already resolving on chain) `invalid_operation`; the response carries the channel state, the failure status name (`Broadcast`, `Rebroadcast`, `PublishFailed`, `RefusedDataLoss`, ...) and our commitment txid. `Handlers/PendingSweepsClientHandler` (ClientCommand 15, scoped `IUnitOfWork`) lists every `ChannelCloses` row with its `OutputResolutions` (amount decoded from `OutputDescriptorData`) and the channel's state (memory, else the database; Closed ones only with `IncludeClosed`). `Node:Onchain` binds `OnchainOptions` (`ReasonableDepth` 6, `IrrevocableDepth` 100). CLI: `forceclosechannel <channel_id>`, `pendingsweeps [channel_id] [all]`.
- Anchors reserve (NL-379, NL-385): `OpenChannelClientHandler` takes the optional `IAnchorReserveService` (registered by `AddBitcoinInfrastructure`); after the factory built the channel it calls `EnsureCanFundAsync(amount, channel)` and locks the funding with `LockFundingUtxosAsync(amount, channel)` (keeps `Node:Anchors` reserve after the funding transaction's worst-case fee at the channel feerate, skips outputs of pending broadcasts) and calls `ReleasePendingChannel(temporary id)` when the open ends either way; an `InsufficientFundsException`/`AnchorReserveException` becomes `ClientException(not_enough_balance)` before anything is sent. Without the service it falls back to the plain two-argument lock. `walletbalance` (`GetWalletBalanceIpcHandler`, optional `IAnchorReserveService`) adds keys 2-5 to `WalletBalanceIpcResponse`: `AnchorReserve`, `AnchorsChannelCount`, `AvailableBalance` (confirmed, not locked/reserved/spent by a pending broadcast) and `SpendableBalance` (available minus the reserve); the CLI prints them.
- Public channels (BOLT 7 plan G1-T1, NL-341): `openchannel <node> <sats> [push_sats] [--public]` (CLI `OpenChannelMessageHandler.ParseArguments`, the flag anywhere after the command) → key 4 `IsPublic` of `OpenChannelIpcRequest` (absent = private, older clients) → `OpenChannelClientRequest.IsPublic`. `OpenChannelClientHandler` refuses it on mainnet unless `Gossip:AllowPublicChannelsOnMainnet` (plan D12) and together with zero-conf, and sends `channel_flags.announce_channel` from the channel the factory built. `AddNltgNodeServices` binds `GossipOptions` from `Gossip` (`AcceptPublicChannels` default true, `AllowPublicChannelsOnMainnet` false (also refuses a peer's public `open_channel` on mainnet), `AnnouncementDepth` 6 (regtest only may lower it), `AnnounceAddresses` (none by default; `host:port`, IPv6 in brackets, `.onion` = Tor v3, else DNS), `OwnGossipFlushInterval` 60 s, `NodeAnnouncementRefreshInterval` 13 days, `DisableAfter` 20 min: an announced channel whose peer stays away that long gets a disabled `channel_update`, NL-349) with `ValidateOnStart` (`GossipOptions.GetValidationErrors`: a bad announced address stops the start). Our `node_announcement` reads `Node:Alias` (at most 32 UTF-8 bytes) and `Node:Color` (`RRGGBB`, default `3399ff`), validated with `NodeOptions`. The announcement services and the own-gossip relay (G1-T4..T7) come from `AddApplicationServices` (`AddGossipServices`); nothing to start in the host (the relay's timer starts with our first message).
- Gossip graph (BOLT 7 G2-T6): `Handlers/ListNodesClientHandler` (ClientCommand 17, `listnodes [node_id]`: announced nodes ordered by node id with alias, `#rrggbb` color, addresses as `host:port`, feature hex, timestamp and the number of graph channels) and `Handlers/ListGraphChannelsClientHandler` (ClientCommand 18, `listgraphchannels [BLOCKxTXxOUTPUT] [node_id]`: channels ordered by short channel id, both policies, verification, capacity, `SpentAtHeight`); both read `IGraphStore.GetSnapshot()` and refuse with `invalid_operation` while the graph is disabled. The short channel id crosses IPC as the 8-byte number (`ListGraphChannelsIpcResponse.ToNumber`), like `listchannels`. `Handlers/GetRouteClientHandler` (ClientCommand 19, BOLT 7 G4-T4, `getroute <node_id> <amount_msat> [--max-fee-msat] [--final-cltv]`): `IRouteQueryService.QuoteRouteAsync` (the payment service; resolved through `GetPaymentLayerService`), each hop with the channel its HTLC arrives on, amount, `cltv_expiry` and the fee it keeps, plus the probability estimate; no route, a zero amount or our own node id is `invalid_operation`. `Handlers/DescribeGraphClientHandler` (ClientCommand 20, BOLT 7 G5-T4, `describegraph [--channels] [--nodes] [--limit <n>] [--offset <n>]`): the Application `GossipGraphDescriber` (singleton registered here with the node's `IGraphStore`, `GossipIngress` and `GossipSyncManager`, each optional) gives the counts (channels, spent, unverified, own, without a policy, policies, disabled directions, announced and graph nodes, and the capacity of the unspent verified and own channels), the store's pending writes and `GraphMemoryEstimate`, the ingress queue, dropped messages and orphans, and each connection's sync state (`GossipSyncManager.GetPeerStates()`: negotiated queries, sync peer, last completed range sync, both filters, stopped querying, queued work); `--channels`/`--nodes` add a page (by short channel id / node id, offset and limit 1-1000, default 100, `NextChannelOffset`/`NextNodeOffset` null on the last page; a non-zero offset pages one listing, so it is refused with both); a bad offset or limit and a disabled graph are `invalid_operation`. The relay and the outboxes (NL-360, NL-375): the handler takes the optional `IGossipRelayScheduler` (read through `GossipRelayScheduler.GetStatus()`: relay on, messages pending for the relay flushes, paused connections, the connected peers' outbox gossip messages and bytes) and `IPeerManager` (`PeerManager.RefusedOutboxGossipCount`, and the outbox depths when there is no relay); null without them. The config template writes `Gossip:MaxOutboxGossipPerPeer` (10,000) and `MaxOutboxGossipBytesPerPeer` (4,194,304) on every network. `Node:Invoices:RouteHints` (`InvoiceOptions`: Auto/Always/Never) and `Node:Invoices:PublicChannelGracePeriod` (Auto: how long an announced channel must be in our graph before hints are left out, 10 min) are bound here too.
- Dual-funded opens (wave sp1 lane SP1-F, NL-037): `openchannel <node> <sats> --dual-fund` (CLI `OpenChannelMessageHandler.DualFundOption`, anywhere after the command) → key 5 `IsDualFunded` of `OpenChannelIpcRequest` (absent = v1) → `OpenChannelClientRequest.IsDualFunded`. `OpenChannelClientHandler` (optional `IDualFundedOpenService` argument) then refuses a push amount and zero-conf, checks the confirmed balance, and awaits `IDualFundedOpenService.OpenAsync` (the amount is our contribution, the request's feerate the funding feerate, `IsPublic` the channel flag); a `FailureReason` or an `InvalidOperationException` (no `option_dual_fund` with the peer, no service) is `invalid_operation`; the response carries the v2 channel id once both `tx_signatures` were exchanged, and since NL-535 the published funding txid and output index (`OpenChannelClientResponse.FundingTxId`/`FundingOutputIndex`, IPC keys 1/2), so the operator can `bumpopen` before the first confirmation. `OpenChannelClientSubscriptionHandler` (optional `IServiceScopeFactory`): with `ReportFundingChanges` (IPC request key 2, `KnownFundingTxId` key 1; absent from an older client, which keeps the old wait-for-the-next-update behavior) it subscribes first, then answers at once or on the next update when the channel is ready or is `V1FundingSigned` on a funding txid other than the known one, a V2 channel's attempt only once its `BroadcastTransactions` row exists (an RBF attempt moves the funding output before it is signed); once the funding is signed a peer disconnection no longer fails the wait and no connected peer is needed; a cancelled call (the client's Ctrl-C) never releases the channel's UTXOs. `ListChannelsClientHandler` lists, for a V2 channel still `V1FundingSigned`, the other signed or `TxSignaturesSent` attempts of the open (its `InteractiveTxSessions` rows) after the current funding as `Pending`/`Initial` fundings (the CLI prints "Pending (another attempt of the dual-funded open)"). The integrator binds `DualFundingOptions` from `Node:DualFund` (`AcceptContributionSat`, `MatchOpenerContribution`, `OpenTimeout`) in `AddNltgNodeServices` (and adds the keys to the config template).
- Chain-processing halt (NL-216): `Handlers/ChainStatusClientHandler` (ClientCommand 16, `chainstatus`) reports `IBlockchainMonitor.IsChainProcessingHalted` with `ChainProcessingHaltReason`, the last processed block, bitcoind's tip (null, not an error, when bitcoind cannot be asked) and, while halted, `Domain.Bitcoin.Constants.ChainProcessingHalt.RefusedOperations`. While halted `OpenChannelClientHandler` and `PayInvoiceClientHandler` refuse with `invalid_operation` before anything is sent (the pay handler takes the monitor as an optional second argument, passed by its factory); the protocol-side refusals are in Application (see its CLAUDE.md).
- Operator commands (NL-152 remainder, wave rf1): `Extensions/OperatorIpcServiceExtensions.AddOperatorIpcServices()` registers `Handlers/DisconnectPeerClientHandler` (scoped) and `Ipc/Handlers/DisconnectPeerIpcHandler` (ClientCommand 24, `disconnect <node_id> [--force]`): an unconnected peer is `invalid_operation`; a peer whose channels (not Closed/Stale, from `IChannelMemoryRepository`) have HTLCs in flight (non-final records of the commitment snapshot, `Handlers/PeerChannelSummary`) is refused with `invalid_operation` unless `Force`; otherwise `IPeerManager.DisconnectPeer`, which suppresses the reconnect loop: the node does not reconnect that peer until the next `connect` or a restart (the peer may still connect to us), and its temporary channels are forgotten (NL-392). The check and the disconnect are not atomic. `listpeers` (`ListPeersIpcHandler`) counts channels and HTLCs in flight from memory (`PeerInfoIpcResponse` key 5 `HtlcsInFlight`); `info` (`NodeInfoIpcHandler`, optional `IPeerManager`/`IChannelMemoryRepository`) adds keys 8-11: peers, Open channels, opening (state below Open) and closing (between Open and Closed) channels. `OpenChannelClientHandler` waits at most `OpenTimeout` (2 min) for accept_channel and forgets the temporary channel of every failed, timed-out or cancelled open (NL-392), under the temporary channel's lock (optional `IChannelLockProvider`): a cleanup that races an accept_channel handler waits for it, and once that handler upgraded the channel nothing is returned and a timed-out open reports the new channel id; a plain `InvalidOperationException` from the funding lock call itself (too few UTXOs after the balance check) is `not_enough_balance` (NL-393), while one from `EnsureCanFundAsync` or a subclass such as `ObjectDisposedException` keeps its own error. `AddNltgNodeServices` calls `AddOperatorIpcServices()` once (a duplicate command crashes `IpcRequestRouter`).
- On-chain withdraw (wave m6 lane w1): `Extensions/WithdrawIpcServiceExtensions.AddWithdrawIpcServices()` registers `IWalletSpendService` (`Infrastructure.Bitcoin/Wallet/AddWalletSpendServices`), `Handlers/WithdrawClientHandler` (scoped) and `Ipc/Handlers/WithdrawIpcHandler` (ClientCommand 25, `withdraw <address> <amount_sat|all> [--sat-per-vb <n>]`); every registration is a TryAdd (the IPC handler through `TryAddEnumerable`), so a second call adds nothing. The handler refuses amount 0, more than 21M BTC and a fee rate outside 1-1,000 sat/vB (`invalid_operation`) before the service, converts sat/vB to sat/kw with `FeeRateConverter.SatPerVByteToSatPerKw` (x 250, floored at 253, so 1 sat/vB is 253 sat/kw and passes the service's floor), and maps `WalletSpendException` (address/network -> `invalid_address`, the rest -> `invalid_operation`), `AnchorReserveException` and `InsufficientFundsException` (-> `not_enough_balance`). `AddNltgNodeServices` calls `services.AddWithdrawIpcServices();` (the Docker proof's own call adds nothing). `NltgDaemonService` (and `NLightningTestNode`) call `IWalletSpendService.ReleaseOrphanedReservationsAsync` once after the chain monitor has started (it releases `withdraw` reservations a crash left without their `WalletSend` row); a `withdraw` runs it too. A `WalletSend` row is never bumped or abandoned: the printer tells the operator not to retry a refused withdrawal (both could confirm).

- Splicing (wave SP1 lane SP1-E, splicing plan §3.10): `Extensions/SpliceIpcServiceExtensions.AddSpliceIpcServices()` (TryAdd, idempotent) registers `Handlers/SpliceInClientHandler`/`SpliceOutClientHandler` (scoped, built through `GetPaymentLayerService<ISpliceService>`, so a node without the Application's `AddSpliceServices()` answers `invalid_operation` "not available") and `Ipc/Handlers/SpliceIpcHandlers` (ClientCommand 33 `splicein`, 34 `spliceout`). ## Adding an IPC command
1. Add an enum value in `src/NLightning.Domain/Client/Enums/ClientCommand.cs`. Append only: the values go over the wire.
2. Add `[MessagePackObject]` `XIpcRequest`/`XIpcResponse` in `src/NLightning.Transport.Ipc/Requests|Responses`. Use append-only `[Key(n)]`. If a new Domain value object crosses the wire, add a formatter in `MessagePack/Formatters` and register it in `NLightningFormatterResolver`.
3. Add `internal sealed XIpcHandler : IIpcCommandHandler` in `Ipc/Handlers/`, using `NodeInfoIpcHandler.cs` as the template. Deserialize `envelope.Payload`. Return an envelope that copies Version, Command and CorrelationId with `Kind = IpcEnvelopeKind.Response`. On failure, return `IpcErrorFactory.CreateErrorEnvelope(envelope, ErrorCodes.X, msg)` with a code from `Domain/Client/Constants/ErrorCodes.cs`. Use `ce.ErrorCode` for a `ClientException`, not `ce.Message`. Resolve client handlers by their `IClientCommandHandler<TReq, TResp>` interface, never by casting to the concrete type.
4. Register it with `services.AddSingleton<IIpcCommandHandler, XIpcHandler>()` in `NodeServiceExtensions.AddNltgNodeServices`. The router does `ToDictionary(h => h.Command)`, so a duplicate command throws at resolve time.
5. Long-running or awaited flows go in a scoped `IClientCommandHandler` in `Handlers/`, registered with `AddScoped`. The IPC handler calls `CreateScope()` and resolves it per request. Follow the `TaskCompletionSource(RunContinuationsAsynchronously)` + event subscribe/`finally` unsubscribe pattern used in `OpenChannelClientHandler`.
6. On the client side, add a method to `src/NLightning.Client/Ipc/NamedPipeIpcClient.cs`, a printer, a case in `Program.cs` and help text in `ClientUtils.ShowUsage`.

## Conventions
- File-scoped namespace first. `NLightning.*` usings go after it and are written relative (`using Domain.Client.Enums;`). System, Microsoft and third-party usings go above it. (`Program.cs` has no namespace, so it uses fully qualified `using NLightning.*;` at the top.)
- IPC handlers are singletons, so resolve anything scoped (`IUnitOfWork`, `IBitcoinWalletService`, client handlers) through `CreateScope()` and never inject it directly.
- Options use `AddOptions<T>().BindConfiguration(section).ValidateOnStart()` for `Node` (`NodeOptions`, with a `PostConfigure` for `ListenAddresses`/`Network`/chain hash; `Node:Routing` and `Node:EnableHtlcs` bind through it, and `IOptions<RoutingOptions>` is registered as the same, validated `NodeOptions.Routing` instance), `Bitcoin` (`BitcoinOptions`) and `FeeEstimation` (`FeeEstimationOptions`). `Database` is not an options class: `AddPersistenceInfrastructureServices(configuration)` reads it raw, and `DatabaseExtensions` reads `Database:RunMigrations`. `Serilog` is read via `ReadFrom.Configuration` in `NodeConfigurationExtensions.ConfigureNltg`. Env vars use the prefix `NLTG_` with `__` for nesting.
- Register new services in their own layer's `DependencyInjection.cs`. A layer service that needs the node key takes `ISecureKeyManager` from DI (as `LocalLightningSigner` does in `AddBitcoinInfrastructure`). `NodeServiceExtensions` owns only what needs `configPath` (`NamedPipeIpcService`, `CookieFileAuthenticator`), the Daemon's own handlers, the `FeeService` HttpClient (Microsoft.Extensions.Http is a Daemon package) and the options.

## Gotchas
- Always pass args through `DaemonUtils.NormalizeArgs` before `AddCommandLine` (done in `ReadInitialConfiguration` and for `Host.CreateDefaultBuilder`): it maps `-n`/`-c` to `--network`/`--config`, turns bare flags (`--daemon`, `--stop`, ... or any `--x` that is last or followed by `--y`/`-n`/`-c`/`-h`/`-?`) into `--x=true` so they don't swallow the next argument, keeps `--daemon true|false` as a pair, and drops the password options. `DaemonUtils.GetDaemonArgument` reads `--daemon` from the normalized form.
- With `--config`, the network comes from `Node:Network` in the file. Without it, the dir is `~/.nltg/<network>` (default `mainnet`), the template is written with that network, and `Node:Network` is set to it in memory when the file omits it. A file whose `Node:Network` differs from the dir (older templates wrote `regtest` into `~/.nltg/mainnet`) fails startup with an `InvalidOperationException` instead of being silently overridden.
- Creating a new key requires reachable bitcoind RPC (for birth height). The key password comes from `PasswordUtils.ResolvePassword`: `--password-file`, `--password-stdin`, `--password` (warns: visible in the process list), then `NLTG_PASSWORD`, else an interactive prompt. `Program.cs` clears `NLTG_PASSWORD` from its own environment after reading it. `ReadInitialConfiguration` uses `NltgEnvironmentVariablesSource`, which drops `NLTG_PASSWORD`, so the password never reaches `IConfiguration`. A `--password-file` with group/other permission bits is read but logged as a warning. `ReadInitialConfiguration` creates a new `~/.nltg/<network>` (and `~/.nltg`) 0700 and the template `appsettings.json` 0600 (`Utilities/FilePermissionUtils`), and warns at every start when the configuration directory or file has group/other bits (it never chmods an existing path).
- On Unix the IPC pipe is a Unix socket at `{configPath}/nltg.ipc` (`NodeConstants.NamedPipeFile`). Each connection carries one request and one response, with a native-endian 4-byte length prefix and a 10MB cap. `NamedPipeIpcService` writes a new random cookie to `{configPath}/nltg.cookie` (mode 0600 on Unix) on every start and deletes it on stop. Both ends open the pipe with `PipeOptions.CurrentUserOnly` (on Windows an ACL for the current user; on Unix a peer-credential check) and the server also chmods the socket to 0600 for every instance (`RestrictSocketPermissions`). A client must send its request within `RequestReadTimeout` (30 s) or the connection is closed; before authentication an error reply never carries the exception message; `LengthPrefixedIpcFraming` reads with `MessagePackSecurity.UntrustedData`. `CookieFileAuthenticator` rereads the cookie per request and compares with `CryptographicOperations.FixedTimeEquals` (an empty cookie never matches). Threat model: `docs/agents/SECURITY_REVIEW.md`.
- Daemonizing re-executes the program with `--daemon-child` (`DaemonUtils.BuildDaemonChildArgs` drops `--daemon` and the password options): on Unix through `/bin/sh -c UnixDaemonLauncherScript` (`nohup ... &`, stdout/stderr to /dev/null, stdin handed to the child through fd 3 because a background job of a non-interactive shell otherwise reads /dev/null, cwd kept), on Windows with `Process.Start`. The parent writes the password as one UTF-8 line into the child's stdin (`WritePasswordToChild`, which refuses a password with a line break) and the child reads it with the `--password-stdin` that `BuildDaemonChildArgs` appends (`PasswordUtils.OpenStdinReader`: UTF-8 whenever stdin is redirected); `NLTG_PASSWORD` is removed from the child's environment, so the password is never in `/proc/<pid>/environ` (SECURITY_REVIEW SR-11). The parent writes the PID file. There is no `fork()`. At start `SensitiveLoggingUtils` warns when `Database:EnableSensitiveQueryLogging` is on (EF would log preimages and per-commitment secrets, SR-12).
