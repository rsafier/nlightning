# NLightning.Infrastructure.Bitcoin

This project is the NBitcoin-backed implementation of the Domain's Bitcoin and crypto ports. It builds BOLT 3 funding and commitment transactions from Domain models and generates the output scripts. It also handles BOLT 3 key derivation, the local signer, HD key storage, the wallet, fee polling, and chain monitoring over bitcoind RPC plus ZMQ `rawblock` (and `rawtx` for the mempool, O8). It also holds the BOLT 4 Sphinx core (`Onion/`); the only protocol-message code is `InteractiveTransactionService` (tx_add/remove payload validation). `ITlvConverterFactory` is registered by `AddInfrastructureServices`/`AddSerializationInfrastructureServices`, not here. Target is net10.0 (via src/Directory.Build.props), csproj version 1.0.0.

## Layout
- `Builders/`: `CommitmentTransactionBuilder`, `FundingTransactionBuilder` and `FundingOutputBuilder`. They take a Domain `*Model`/`*OutputInfo` and return an UNSIGNED tx as Domain `SignedTransaction(txid, rawBytes)`. `FundingTransactionBuilder` returns `FundingTransactionBuildResult` (tx + funding output index; inputs and outputs are both BIP 69 ordered, so a rebuild from the same UTXOs gives the same txid) and never mutates the model; the caller sets `FundingOutputInfo.TransactionId/Index`. Change/dust/fee decisions are made in Domain `FundingTransactionModelFactory` (typed `InsufficientFundsException`, dust change folded into the fee). `CommitmentTransactionBuilder.BuildWithOutputMap` returns `CommitmentTransactionBuildResult` (unsigned tx + `HtlcOutputsInTxOrder`: each untrimmed `HtlcOutputInfo` with its `Vout`, in transaction order, which is the order of HTLC transactions and `htlc_signatures`); `Build` is a wrapper returning only the tx. Outputs are sorted with a stable `OrderBy` over `TransactionOutputComparer`, so identical outputs keep the model order. `HtlcTransactionBuilder` (`IHtlcTransactionBuilder`, singleton in `AddBitcoinInfrastructure`) builds HTLC-timeout/HTLC-success txs from a Domain `HtlcTransactionModel` (made by the static Domain `HtlcTransactionModelFactory` from the commitment model + its output map): `Build` returns `HtlcTransactionBuildResult` (unsigned tx, spent witness script, spent amount: the BIP 143 sighash inputs) and `AddWitness` assembles `0 <remotesig> <localsig> <preimage|empty> <witnessScript>` (remote sighash `SINGLE|ANYONECANPAY` with anchors, else `ALL`; local always `ALL`). `ClosingTransactionBuilder` (`IClosingTransactionBuilder`, singleton in `AddBitcoinInfrastructure`, BOLT2 plan N10-T2) builds the BOLT 3 legacy closing tx from a Domain `ClosingTransactionModel` (version 2, locktime 0, the funding outpoint with sequence 0xFFFFFFFF, outputs ordered by amount then scriptpubkey as memcmp with the shorter first) and `AddWitness(unsigned, funding, localSig, remoteSig)` assembles `0 <sig for the lesser funding key> <sig for the greater> <2-of-2 script>`, both `SIGHASH_ALL`; sign it with `ILightningSigner.SignChannelTransaction` and check the peer's with `ValidateSignature`. BOLT 3 has no closing-tx vector: `Builders/ClosingTransactionBuilderTests` checks each field and verifies the signed tx with NBitcoin's interpreter. `SweepTransactionBuilder` (`ISweepTransactionBuilder`, BOLT 5 plan O3-T1) builds sweeps and claims from Domain `SweepInput`s: version 2, one output to the destination script, `nSequence` = the input's CSV or 0xFFFFFFFD, `nLockTime` = the `cltv_expiry` of the timeout claims; timeout claims are never batched with any other spend kind and all share one `cltv_expiry` (the caller groups them by expiry), and a preimage claim (whose `CltvExpiry` is its deadline) is refused when `nLockTime >= cltv_expiry`; `Build(inputs, destination, feeratePerKw, lockTime)` charges `SweepWeights.FeeSat` of the estimated weight (73-byte signatures), `BuildWithFee` an absolute fee (RBF); it validates each input for its spend kind (CSV, point, pubkey, cltv, 32-byte preimage, secret, a revocation pubkey whose HASH160 is in the script) and refuses an output below the destination's dust limit. `AddWitnesses(unsigned, sigs)` / `Sign(unsigned, signer, channelId)` assemble the BOLT 3 witnesses (internal static `CreateWitness`). `PenaltyTransactionBuilder` (`IPenaltyTransactionBuilder`, O5-T1) wraps it: `BuildBatched` (penalty inputs plus optionally our `to_remote`), `BuildSingle`, `BuildSplit` (one tx per input, B5-REV-08); nLockTime 0, every input replaceable. Both are singletons through `Onchain/OnchainServiceCollectionExtensions.AddOnchainBitcoinServices()` (the sweep builder needs `IOptions<NodeOptions>`). The interfaces are in `Builders/Interfaces/`, except `IFundingOutputBuilder`, which sits in `Builders/`.
- `Outputs/`: `BaseOutput` (implements Domain `IOutput`) and `BaseHtlcOutput`, with subclasses `FundingOutput`, `ToLocalOutput`, `ToRemoteOutput`, `ToAnchorOutput`, `OfferedHtlcOutput`, `ReceivedHtlcOutput`, `HtlcResolutionOutput` and `ChangeOutput`.
- `Comparers/TransactionOutputComparer.cs`: BOLT 3 output ordering (amount, then scriptPubKey, then cltv_expiry).
- `Services/`: `KeyDerivationService` (BOLT 3 derivation and per-commitment secrets), `CommitmentKeyDerivationService`, `PerCommitmentSecretVerifier` (Domain `IPerCommitmentSecretVerifier`, singleton in `AddBitcoinInfrastructure`: `Verify(secret, point)` checks `secret*G == point` and rejects invalid scalars; `VerifyAndStore(secret, remoteCommitmentNumber, point, shachain)` inserts into the peer's shachain at `PerCommitmentIndex.From(n)` only after the point matched; the revoke_and_ack receive check), `FeeService` (register it with `Services/FeeServiceCollectionExtensions.AddFeeServices(primaryHandler?)`: one singleton for `FeeService` and `IFeeService` with its own long-lived `HttpClient` (30 s timeout), replacing any earlier `IFeeService`; the Daemon (`AddNltgNodeServices`) and the Docker test node use it, so the instance the daemon starts is the one `DustService`, the close coordinator, `ChannelFactory` and `FeeUpdateScheduler` read; `FeeEstimation:Source` = `Http` (mempool.space-style JSON, value in `RateUnit`, default sat/vB), `Bitcoind` (`estimatesmartfee` through its own lazily created RPC client from `BitcoinOptions`, `ConfirmationTarget`, `EstimateMode`) or `Fixed` (`FixedFeeRatePerKw`); invalid options throw in the constructor; every rate goes through `FeeRateConverter` (sat/vB x 250, never below 253 sat/kw; NL-288, the old `RateMultiplier` is ignored with a warning); `GetCachedFeeRatePerKw` returns a copy and, until the first estimate (not started, or every fetch failed), `FallbackFeeRatePerKw` (default 2500, at least 253), never 0; a failed refresh keeps an earlier estimate; an HttpClient timeout is logged, only our own cancellation is silent; the internal constructor takes the bitcoind estimator as a delegate for tests; per confirmation target (`GetFeeRatePerKwAsync(uint target, ct)`, NL-296, BOLT 5 sweeps/penalties): `Bitcoind` asks `estimatesmartfee` for that target (cached per target, node-wide rate when it has none), `Http` picks the mempool.space bucket of the last response (`fastestFee` 1, `halfHourFee` 2-3, `hourFee` up to 143, `economyFee` from 144; the node-wide rate when the bucket is missing), `Fixed` the fixed rate), `DustService` (singleton in `AddBitcoinInfrastructure`; depends on `IFeeService`, which the host registers) and `InteractiveTransactionService` (not registered in any DI container).
- `Signers/LocalLightningSigner.cs`: implements `ILightningSigner`. Channel key m/6425'/0'/0'/0/i has hardened children 0'-5' (funding, revocation, payment, delayed, htlc, per-commitment seed). `GetPerCommitmentPoint`/`RevealPerCommitmentSecret` take a **commitment number** and derive the secret at index `PerCommitmentIndex.From(n) = 2^48-1-n` (NL-187). **Revocation guard (NL-189):** `RevealPerCommitmentSecret(channelId, n)` throws `SignerException` unless `n < LocalCommitmentNumber`; that number comes from `ChannelSigningInfo.LocalCommitmentNumber` at `RegisterChannel` (re-registering never lowers it) and moves only through `AdvanceLocalCommitment(channelId, n)` (monotonic; call it only after the new local commitment is persisted). There is no index-keyed or unguarded secret API any more; `CommitmentKeys` carries no secret (local keys are derived from the point). **HTLC signatures (NL-057):** `SignRemoteHtlcTransactions` (our sigs for the peer's commitment, key `htlc_basepoint_secret + SHA256(point || htlc_basepoint)` from the protected virtual `GetHtlcBasepointSecret`, `SINGLE|ANYONECANPAY` with anchors else `ALL`), `ValidateLocalHtlcSignatures` (count, compact parse, low-S, verify against `ChannelSigningInfo.RemoteHtlcBasepoint` tweaked by our point) and `SignLocalHtlcTransaction` (our own HTLC tx, always `ALL`). Each takes a Domain `HtlcSigningContext(HtlcTransactionBuildResult, PerCommitmentPoint, HasAnchors)`; signatures are RFC 6979 without low-R grinding, `MakeCanonical()`. **Broadcast signing and data loss (N9-T4):** `SignLocalCommitmentForBroadcast(channelId, number, unsignedCommitment, remoteSignature)` validates the peer's signature, signs with our funding key and returns the transaction with the BOLT 3 witness `0 <sig1> <sig2> <funding script>` in the script's key order (byte-exact against Appendix C commit tx 0, `test/NLightning.Infrastructure.Bitcoin.Tests/Signers/LocalLightningSignerBroadcastTests`); it refuses `number <` the current local commitment number (revoked, I4). `MarkDataLoss(channelId)` (also set by `RegisterChannel` when `ChannelSigningInfo.DataLossDetected`; sticky) makes it refuse `SignChannelTransaction`, `SignRemoteHtlcTransactions`, `SignLocalHtlcTransaction` and the broadcast signing with `SignerException` (I12). **Invariant S1 (BOLT 5 plan §3.5, O2-T1):** `SignLocalCommitmentForBroadcast` calls `MarkBroadcastSigned(channelId, n)` before it returns; `RegisterChannel` applies `ChannelSigningInfo.BroadcastSignedCommitmentNumber` with `MarkBroadcastSigned`, so the host restores the mark by filling that field from the persisted commitment broadcast row (O2-T2 wiring; not done yet, the mark is memory only until then). The I4/S1 checks, the broadcast signature and its mark hold a per-channel `System.Threading.Lock` shared with `AdvanceLocalCommitment`, `RevealPerCommitmentSecret`, `MarkBroadcastSigned` and `RegisterChannel`, so S1 holds without the caller's channel lock. Once marked (sticky, the lowest number wins, `TryGetBroadcastSignedCommitment` reads it) the signer refuses `RevealPerCommitmentSecret(m >= n)`, `AdvanceLocalCommitment(> n)`, `SignLocalCommitmentForBroadcast` of any other number (the same number may be signed again for a rebroadcast), `SignChannelTransaction` and `SignRemoteHtlcTransactions`; `SignLocalHtlcTransaction` (our HTLC-timeout/success for the on-chain resolution) stays allowed. The broadcast path signs the funding input through the private unguarded `SignFundingInput`. **Sweeps (BOLT 5 plan O3-T1):** `SignSweepInput(channelId, SweepSigningContext)` signs one input (`SIGHASH_ALL`, BIP 143, RFC 6979, low-S, 64-byte compact) with the key the context's `SweepKeyKind` names: `DelayedPayment` (delayed basepoint secret tweaked by our point), `Payment` (payment basepoint secret, static_remotekey; a null witness script means P2WPKH, script code P2PKH), `HtlcRemotePoint` (HTLC basepoint secret tweaked by the peer's point) or `Revocation` (`DeriveRevocationPrivKey(revocation basepoint secret, peer secret)`, and a given point must equal `secret * G`). The derived pubkey or its HASH160 must be pushed by the witness script, else `SignerException` (a wrong kind, point or secret never signs). Not blocked by data loss or S1. The basepoint secrets come from the protected virtual `GetRevocationBasepointSecret`/`GetPaymentBasepointSecret`/`GetDelayedPaymentBasepointSecret`/`GetHtlcBasepointSecret` (tests override them with the Appendix C secrets: `test/.../Signers/AppendixCSweepSigner`); derived keys are wiped after use. **Channel announcements (BOLT 7 plan G1-T2):** `SignChannelAnnouncement(channelId, unsignedAnnouncement, scid)` takes the payload bytes after the four signatures (`len`, `features`, `chain_hash`, `short_channel_id`, the two node ids, the two bitcoin keys, unknown trailing bytes) and returns `ChannelAnnouncementSignatures(node, bitcoin)` over their double-SHA256 (node key through `SignNodeMessage`, funding key through the same NBitcoin.Secp256k1 RFC 6979 low-S path, wiped after use). It parses the bytes and refuses (`SignerException`) another chain, a SCID other than the argument, the channel's funding output index or the channel's real SCID (re-read from the source when there is one, else the registered `ChannelSigningInfo.ShortChannelId`; unknown SCID refused), node ids not strictly ascending, neither being ours, the other not the registered `RemoteNodeId`, our slot's bitcoin key not our funding key, the other not the peer's, and anything after data loss. Tests: `Signers/LocalLightningSignerChannelAnnouncementTests.cs` (the assembled 256 verifies all four signatures, both node orders). **BOLT 7 node signatures (W0-E):** `SignNodeMessage(Hash)` signs the given 32-byte hash as is with the node key (from `ISecureKeyManager.GetNodeKeyPair()`, whose private-key copy is zeroed after parsing) through NBitcoin.Secp256k1 (`ECPrivKey.TrySignECDSA`: RFC 6979, low-S, 64-byte compact); `VerifyNodeMessage(hash, signature, nodeId)` returns false for an unparsable signature/pubkey and accepts high-S (normalized first; BOLT 7 relays may malleate s). The caller hashes: for channel_update `ChannelUpdatePayload.GetSignatureHash()` = SHA256d of the bytes after the signature. Tests: `Signers/LocalLightningSignerNodeMessageTests.cs` (an LND-captured channel_update verifies with LND's node id). The verification itself is `Gossip/GossipSignatureVerifier.VerifyCompact` (G0-T3), which `VerifyNodeMessage` delegates to.
- `Managers/SecureKeyManager.cs`: implements `ISecureKeyManager`. The master key lives in locked memory, and the key file is encrypted with Argon2id + XChaCha20-Poly1305.
- `Wallet/`: `BitcoinChainService` (RPC, incl. `GetBlockHashAsync` for reorg detection, `GetBlockAsync(uint256 hash)` (also a stale block) and `GetUnspentOutputAsync(outPoint)` (`gettxout` with the mempool, so an output a mempool transaction spends is not reported; with its height) for the wallet rollback; both are default interface methods answering null, so other implementations need no change; `GetBlockTxIdsAsync(height)` (BOLT 7 G2-T2: `getblockhash` + `getblock <hash> 1`, the block hash and its txids in block order, null when the height is out of range (-8) or the block is pruned (-1); the default interface method reads the whole block through `GetBlockAsync(height)`, which is what `FakeBitcoinChain` uses)), `BitcoinWalletService` (deposit addresses; a new batch of 10 starts one past the highest stored index of that type and chain, 0 when there is none, NL-283; lookup and generation run under a process-wide `SemaphoreSlim`, so two scopes never generate the same indexes), `BlockchainMonitorService` (ZMQ, watched txs, watched outpoints, UTXOs, the broadcast set, reorgs; BOLT 5 plan O0). Interfaces are in `Wallet/Interfaces/`; `IBlockchainMonitor` extends the Domain ports `IChainBroadcaster` and `IOutpointWatcher` (`src/NLightning.Domain/Onchain/Interfaces/`), which `AddBitcoinInfrastructure` registers as the same singleton. The monitor keeps watching a wallet address after a deposit (as after a restart, which reloads them all). `TrackWatchedTransaction` follows a watch row the caller saved in its own save (the mutual close saves it with Closing) and `PublishTransactionAsync` only broadcasts (nothing stored). **Per block (NL-214):** everything a block changes (first sightings and depths of watched txs, deposits and wallet spends, outpoint spends, confirmations of our broadcasts, the blockchain state and the header ring) is staged in one unit of work without touching memory; memory is updated and the events are raised (`OnNewBlockDetected`, `OnBlockInputs`, `OnTransactionConfirmed`, `OnWalletMovementDetected`, `OnWatchedOutpointSpent`, in that order; `OnBlockInputs` (BOLT 7 G2-T5, Domain `BlockInputsEventArgs`) lists every non-coinbase input's outpoint of the block and is built only when someone listens: the graph pruner) only after that save, so a failed attempt leaves nothing and raises nothing. **Outpoints (O0-T2):** `WatchOutpointAsync` (own save) / `TrackWatchedOutpoint` (caller's save) are persisted watches, reloaded at start (`GetActiveAsync`, every watch of a channel that is not Closed/Stale); `WatchOutpointSpend`/`StopWatchingOutpointSpend` stay memory-only. Every stored channel past funding_created gets its funding output watched: at start (`AddMissingFundingOutpointsAsync`), when a watched funding tx is first seen in a block (`AddFundingOutpointIfMissingAsync`, the fundee path, before the block's spends are checked) and at funding_signed (funder, `FundingSignedMessageHandler`). `OnWatchedOutpointSpent` (`OutpointSpentEventArgs`: channel, spending tx, height, index in block, the spent outpoint, block hash) is raised for every processed block that spends the outpoint, also on a replayed block (the last processed block is replayed at start) and on a new branch after a reorg, so listeners must be idempotent. **Broadcasts (O0-T1, NL-258):** `PublishAsync(model)` sends a tx whose `BroadcastTransactionModel` row the caller saved (never throws for a refusal; true when accepted or already known), `SaveAndPublishAsync` saves it first; every `Pending` row is sent again after each processing round and at start, also when processing is halted (a halted round or a halted startup rewind), until a processed block holds it (then `Confirmed`). A refusal is logged at Warning the first time and then every `RefusalWarningInterval` (6) refusals in a row, at Debug in between; before each rebroadcast round the monitor drops the in-memory entries whose stored row is no longer `Pending` (`Replaced` by the O6 sweep scheduler, `Abandoned` by the watcher or the scheduler), so they are not sent again without a restart; there is no abandonment rule for a transaction the node keeps refusing (a funding tx the node refuses for good is retried forever, NL-259 follow-up). `PublishAndWatchTransactionAsync` saves the watch and a pending row (purpose `Unspecified`) in one save, then sends and still throws a refusal. **Reorgs (O0-T3, NL-096):** the hashes of the last `HeaderRingSize` (100) processed blocks are kept (`BlockHeaders`). A block whose hash differs from the stored one at its height, or the next block whose parent is not our tip, starts a rewind, unless bitcoind still has our last processed block at its height: then the block is a late notification of an orphan and is dropped (no rewind, no `OnBlockDisconnected`). The fork point is the highest ring height, searched from our last processed block down (capped at bitcoind's tip), whose hash bitcoind still has; one save resets the first-seen height of pending watches above it, clears outpoint spends and broadcast confirmations above it, deletes the headers and rewinds the state; memory is reloaded, `OnBlockDisconnected` is raised per disconnected block (highest first), then the active chain from the fork point to its tip is queued. A watch already completed in a disconnected block is made pending again in the rollback save (NL-292): its confirmation is raised again from the new branch, and `Application/Onchain/Reorg/FundingReconfirmationHandler` moves the channel's short channel id there (Docker `Onchain/OnchainSmokeTests`, a regular test since ABCD wave 6). A reorg deeper than the ring, or a chain tip below our height at start with no ring hash in common, halts processing. A block below our height with the stored hash (e.g. after `reconsiderblock`) is dropped. The tip is processed at start (NL-215). `IsChainProcessingHalted` is on `IBlockchainMonitor` with `ChainProcessingHaltReason` (set with the flag at every halt site, cleared when a round completes; NL-216: the daemon's `chainstatus` reports both and the channel operations refuse new risk while halted). **Mempool (BOLT 5 O8, NL-098):** with `BitcoinOptions.WatchMempool` (default true) `InitializeZmqSockets` also subscribes to `rawtx` on `ZmqTxPort`, read by its own long-running loop (`MonitorMempool`, all frames of a message at once); `ProcessMempoolTransaction(tx)` (internal, tests call it directly) raises `OnWatchedOutpointSpentInMempool` (`MempoolSpendEventArgs`) once per spent watched outpoint, and once per spent output of a transaction it reported before (`SpendsUnconfirmedParent`: a commitment and its HTLC transaction both unconfirmed). A transaction is handled once (bitcoind announces it again when a block holding it is connected): seen txids and reported parents are each remembered up to `MaxRememberedMempoolTransactions` (10,000), the oldest forgotten first. Nothing is saved, no watch is marked spent and no confirmed event is raised: only a processed block confirms a spend. Each handler is called on its own (one that throws does not stop the others). Wallet effects of disconnected blocks are rolled back in the same save (NL-293): deposits confirmed above the fork are removed (`TrySpendUtxo`; they come back when their transaction is mined on the new branch; a lock to a channel is lost with them, logged) and wallet outputs a disconnected block spent are added back when `GetUnspentOutputAsync` reports them unspent in the active chain and not spent by a mempool transaction (an output whose spend is back in the mempool is left to that spend confirming again, so coin selection never double-spends our own pending funding; the disconnected blocks are read by hash; candidates are P2WPKH inputs whose key is a watched address and every taproot key-path input). Spent UTXO rows are still deleted, so an output whose spend is not found this way (a block bitcoind can no longer serve) is not restored.

Vectors: `test/NLightning.Integration.Tests/BOLT4/OnionVectorTests.cs` (onion-test.json byte-exact construct + peel chain, onion-error-test.json per-hop keys, blinded-payment-onion-test.json peel chain); unit tests in `test/NLightning.Infrastructure.Bitcoin.Tests/Onion/`.
- `Onchain/` (BOLT 5 plan O2-T4): `ChainTxMapper` (static; `FromTransaction(Transaction)` and `TryParse(bytes, out ChainTx?)`, false for garbage, never throws) and `CommitmentOutputMapper : Onchain/Interfaces/ICommitmentOutputMapper` (singleton through `OnchainServiceCollectionExtensions.AddOnchainBitcoinServices()`; needs `ICommitmentTransactionModelFactory` from `AddApplicationServices` and `ICommitmentTransactionBuilder`). `Map(channel, CommitmentTxSpec, CommitmentCase, number, remotePoint?, ChainTx?)` rebuilds the commitment with the same factory/builder that signed it (Local: our point from the signer; Remote/Revoked: the given point, for a revoked one `secret * G`) and returns a Domain `CommitmentOutputMap`: with the rebuilt txid on chain (or no tx given) the builder's own HTLC vout map is used and the other outputs are matched by script; with another txid every output on chain is matched by scriptPubKey (identical scripts by amount, then in order), unmatched vouts go to `UnmappedVouts`. The output candidates are converted exactly as `CommitmentTransactionBuilder` converts them (anchor script forms follow the presence of anchor outputs), so keep the two in step. `Map(model, htlcs, case, tx?)` takes an already built model. `FindPaymentToRemote(tx, ourPaymentBasepoint, hasAnchors)` finds our static_remotekey `to_remote` in a peer commitment we cannot rebuild (data loss). Tests: `test/NLightning.Infrastructure.Bitcoin.Tests/Onchain/` (all 16 Appendix C commitments as local, remote and revoked, the 9 Appendix F ones, script fallback, trimmed/missing HTLCs, preimage extraction from all Appendix C HTLC txs).
- `Gossip/` (BOLT 7 plan G0-T3, G2-T2): `GossipSignatureVerifier` (Domain `IGossipSignatureVerifier`: `Verify(hash, sig, key)` and `VerifyAll(checks)`, false for an empty list; compact 64-byte ECDSA over the caller's 32-byte hash, high-S normalized first, false (never a throw) for anything unparsable or a `default` value; the internal static `VerifyCompact` is the one implementation, also behind `LocalLightningSigner.VerifyNodeMessage`). Internal `GossipSignedRanges` builds `GossipSignatureCheck`s from **raw** payloads (without the 2-byte type) for captured vectors and tests: channel_announcement = 4 checks over SHA256d(payload[256..]) (node_sig_1/2 with node_id_1/2, bitcoin_sig_1/2 with bitcoin_key_1/2), node_announcement over SHA256d(payload[64..]) by the node_id after features and timestamp, channel_update over SHA256d(payload[64..]) by the caller's direction key, announcement_signatures = node and bitcoin signature over the given channel_announcement hash; the typed Domain payloads (`GetSignatureHash()`, D1) remain the node's codec. `FundingOutputLookup` (Domain `IFundingOutputLookup`, D3): `LookupAsync(scid)` = `getblockcount` (height above tip: `BlockNotFound`), `getblockhash(height)`, the txid list (`IBitcoinChainService.GetBlockTxIdsAsync`, `getblock <hash> 1`; null = `BlockUnavailable`, a pruned node), `TransactionIndexOutOfRange`, then `GetUnspentOutputAsync` (`gettxout` with the mempool; on null a second `GetConfirmedUnspentOutputAsync` (`gettxout` without the mempool) tells `OutputSpentInMempool` (unspent on chain, spent by a mempool tx: transient) from `OutputSpentOrMissing`); an output reported at another height, or `getblockhash(height)` naming another block after `gettxout` than the one whose txid list was used (a reorg that re-mined the tx at another index), drops the cached height and retries once, then `ChainMoved`; `getblock` RPC_MISC_ERROR counts as pruned (`BlockUnavailable`) only when its message says "pruned" (`BitcoinChainService.IsPrunedBlockError`), other -1 errors are `ChainUnavailable`; any RPC failure is `ChainUnavailable` (transient, never an exception; only cancellation throws). `VerifyAsync(scid, key1, key2, expectedAmount?)` also checks the script is the P2WSH of the sorted 2-of-2 (`TryCreateFundingScriptPubKey`, `ScriptMismatch`, also for a key that is not a point) and the amount (zero or not the expected: `AmountMismatch`). Results carry txid, amount (capacity), script and `Confirmations` (tip - height + 1; the 6-block rule is the caller's). Txid lists sit in an LRU by height (`ChainLookupCacheHeights`, 256), used only while `getblockhash` names the same block and dropped from the disconnected height up on `IOutpointWatcher.OnBlockDisconnected` (unsubscribed on `Dispose`); `ChainLookupConcurrency` (4) lookups at once and `ChainLookupsPerSecond` (50, burst the same) through the internal `TokenBucketRateLimiter` on a `TimeProvider`. `FundingOutputLookupOptions` uses the plan's `Gossip:*` key names, so the host can bind it from the `Gossip` section. `GossipBitcoinServiceCollectionExtensions.AddGossipBitcoinServices()` registers both (TryAdd singletons; `TimeProvider` and `IOutpointWatcher` optional). ## Adding a new output or transaction type
1. Output script: subclass `BaseOutput` (or `BaseHtlcOutput`) in `Outputs/`, and pass the redeem script (from a static `Generate*Script(...)`) and the `ScriptType` to `base(amount, script, scriptType)`; `ScriptType` is a get-only base property, never a virtual override (the base ctor derives `ScriptPubKey` from it). Throw `InvalidScriptException` when `script.IsUnspendable || !script.IsValid`.
2. If the output goes on commitment txs, add the Domain `*OutputInfo` -> output conversion in `CommitmentTransactionBuilder.Build` and check how `TransactionOutputComparer` tie-breaks it.
3. For a new transaction type (e.g. HTLC-success/timeout): add a data-only Domain model/factory in `src/NLightning.Domain/Bitcoin/Transactions/`, then add an `IXBuilder` in `Builders/Interfaces/` and `XBuilder` in `Builders/`. Signing goes through `ILightningSigner` (add a method there and implement it in `LocalLightningSigner`).
4. Register singletons in `DependencyInjection.AddBitcoinInfrastructure` (only `IBitcoinWalletService` is scoped). `ILightningSigner` (`LocalLightningSigner`) is registered there too and takes the host's `ISecureKeyManager` from DI. `SecureKeyManager` and `FeeService` (`AddFeeServices`) are registered by the host (`NodeServiceExtensions.AddNltgNodeServices`, which the Docker tests also use). Services in `AddBitcoinInfrastructure` may depend on them (e.g. `CommitmentKeyDerivationService` takes `ILightningSigner`).
5. Add tests in `test/NLightning.Infrastructure.Bitcoin.Tests/<Folder>/`, plus BOLT 3 vectors in `test/NLightning.Integration.Tests/BOLT3/` if applicable.

## Conventions
- Use a file-scoped namespace. External usings (NBitcoin, Microsoft.*) go above it; NLightning usings go below it as relative names (`using Domain.Money;`).
- Domain value objects cross the boundary as bytes and are converted here (`new PubKey(compactPubKey)`, `new uint256(txId)`). Domain stays NBitcoin-free.
- Resolve the network with `nodeOptions.BitcoinNetwork.ToNBitcoinNetwork()` (`Networks/NBitcoinNetworkResolver`, W4-D): mainnet/testnet/regtest map to NBitcoin's, signet and every custom signet (Mutinynet) to `Bitcoin.Instance.Signet`, anything else throws. The `Wallet/` services (`BitcoinChainService`, `BitcoinWalletService`, `BlockchainMonitorService`) use it; the builders, `LocalLightningSigner` and `SecureKeyManager` still call `Network.GetNetwork(name)` (knows `signet`, throws otherwise). See `docs/agents/MUTINYNET.md`.
- Singletons that need the DB create a scope per operation: `CreateScope()` then `GetRequiredService<IUnitOfWork>()` (see `Wallet/BlockchainMonitorService.cs`).
- Guard logging with `_logger.IsEnabled(...)`. Name tests `Given_X_When_Y_Then_Z` (xUnit v3 + Moq).
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate: `_field`/`s_field` naming, no unused usings.

## Gotchas (verified bugs)
- `WatchedTransactionModel.TransactionIndex` is the position in the block (coinbase = 0), a `uint` capped at 24 bits (NL-102). Rows written before migration `WidenWatchedTransactionIndex` may hold the old watched-only index, and channels confirmed then carry a wrong persisted `ShortChannelId`; nothing repairs them.
- `BlockchainMonitorService.ProcessNewBlockAsync` (the ZMQ entry point, internal; tests call it directly) serializes its callers with `_newBlockSemaphore` and drops a block above bitcoind's tip (a ZMQ endpoint of another chain, NL-310). That guard is not full protection against a misconfigured endpoint: a foreign block at or below our tip is dropped as stale by the existing `DoesNotExtendProcessedChain`/`IsProcessedTipActiveAsync` path (no rewind, our tip is still active). The check costs one `getblockcount` RPC per ZMQ block; if it fails, the notification is dropped and logged, and the next block's catch-up recovers it. Tests that start a real monitor must not subscribe to a real ZMQ port: the Mutinynet container publishes `rawblock` on 127.0.0.1:28332 (the daemon's signet default), so use `Tests.Utils/Mocks/SilentZmqEndpoint` (loopback ports held by listeners that never speak ZMQ), as `ChainMonitorHarness` and `BlockchainMonitorServiceTests` do.
- `BlockchainMonitorService` block failures (NL-097): a block whose `ProcessBlock` throws is retried `MaxBlockProcessingAttempts` (3) times with doubling backoff from `BlockRetryBaseDelay` (1s); then the round halts with a Critical log and `IsChainProcessingHalted` is set, leaving it and later blocks queued (never skipped). The next ZMQ block or a restart retries from it. The queue holds at most `MaxQueuedBlocks` (144); later blocks are refetched from bitcoind once it drains. Replays (the last processed block is re-queued on start, and failed blocks are retried) skip deposits whose UTXO is already in `IUtxoMemoryRepository`, but still re-raise `OnNewBlockDetected`. Each attempt is its own unit of work, so a failed attempt persists nothing (NL-214). The halt only recovers if the failure is transient; nothing fails the node if it persists (NL-216: the flag and its reason are on `IBlockchainMonitor`, shown by `chainstatus`, and new channel risk is refused while it is set).
- `InteractiveTransactionService` validates messages **received from the peer**: its `isInitiator` ctor flag means the local node, and it passes `!isInitiator` to the `Tx*Validator`s as the sender role. Serial ids are unique across inputs and outputs together; removals are checked against the matching collection.
- `SecureKeyManager` writes v2 key files (random 16-byte salt, random 24-byte nonce, Argon2id 64 MiB/3 passes, all stored in the file). v1 files (fixed `s_legacySalt`, zero nonce, 64 KiB) are still read and are rewritten as v2 by `FromFilePath`, after copying the original to `<file>.v1.bak`. Writes are atomic (temp file + move) and keep the target's Unix mode (new files `0600`) and symlinks. Passwords are hashed as full UTF-8; a file that only opens with the old libsodium truncated encoding (first `password.Length` UTF-8 bytes) is also rewritten. The node key (`GetNodeKeyPair`) is the master key itself. `ComputeNodeSharedSecret` (node-key ECDH) copies it out of locked memory only for the operation and wipes the copy. `ISecureKeyManager` implementations: `SecureKeyManager`, the Docker `FakeSecureKeyManager`, and the test-only `EcdhOnlyKeyManager` (Moq cannot set up its span-parameter method).
- `LocalLightningSigner.SignChannelTransaction` hardcodes input 0 + SIGHASH_ALL (commitment and closing txs only); HTLC transactions go through the HTLC methods above.
- `LocalLightningSigner.SignWalletTransaction` throws NotImplementedException. Channel signing info is no longer memory-only (NL-067): built with an `IChannelSigningInfoSource` (the DI registration passes `sp.GetService<IChannelSigningInfoSource>()`, which `AddRepositoriesInfrastructureServices` registers), the signer loads and registers a channel it does not know from the database on first use (`TryGetSigningInfo`: every channel-id API, including `TryGetBroadcastSignedCommitment`), with the persisted local commitment number (revocation guard), data-loss flag and broadcast mark (S1). Without a source (unit tests, harnesses) registration stays manual. `RegisterChannel` again refreshes the SCID, the peer's node id and htlc basepoint of an already registered channel, but never its key index, funding keys or outpoint (a mismatch throws `SignerException` before any guard or mark is touched; the first registration is kept). `SignChannelAnnouncement` refuses a private channel (`ChannelSigningInfo.AnnounceChannel` false, BOLT 7). A lookup of an unknown channel is a synchronous database read on every call (no negative cache); `SignLocalCommitmentForBroadcast` does it before taking the commitment lock. Closed and Stale channels are not loaded.
- `BitcoinChainService`'s constructor makes a blocking RPC call, so DI resolution fails if bitcoind is down.

## Onion-routing (BOLT 4) hooks
- `Ecdh.SecP256K1Dh` already computes the Sphinx per-hop shared secret, SHA256(compressed(k*P)).
- EC math for ephemeral-key blinding lives behind the Domain port `ISecp256K1Math` (`MultiplyPubKey`, `MultiplyPrivKey`, `AddPubKeys`, `AddPrivKeys`), implemented by `Crypto/Functions/Secp256K1Math.cs` (on `NLightningCryptoContext`, registered as a singleton in `AddBitcoinInfrastructure`). `KeyDerivationService` consumes it; do not reintroduce private EC helpers. Sphinx code that needs EC math should depend on `ISecp256K1Math`, except the per-hop key chain in `OnionBuilder.ComputeHopKeys`, which works on `ECPrivKey` directly (CreatePubKey/ECDH/TweakMul on one parsed key, ~35% faster and ~70% fewer managed allocations per hop than the `IEcdh` + `ISecp256K1Math` round trips).
- Peeling needs node-key ECDH: `ISphinxService.PeelAsLocalNode` does it through `ISecureKeyManager.ComputeNodeSharedSecret` (the node key never leaves the key manager; route blinding tweaks the ephemeral key, ECDH(k*t, E) = ECDH(k, t*E), instead of the node key); `Peel(..., PrivKey nodeKey, ...)` takes the key explicitly. `OnionPeeler` takes either through its `NodeEcdh` delegate. The two are named differently on purpose, because a `byte[]` converts implicitly to both `PrivKey` and `CompactPubKey` (the path key).
- Every packet-caused `Peel` failure is an `OnionException` (only caller bugs, such as a bad node key or a `default` packet, throw anything else): BADONION codes (`InvalidOnionVersion`/`Key`/`Hmac`/`Blinding`) carry sha256_of_onion as `FailureData`; framing errors (after the HMAC verified) are `InvalidOnionPayload` with data `00 0000` (type 0, offset 0) and a copy of the shared secret in `OnionException.SharedSecret` (needed to encrypt the non-BADONION failure). For `OnionPacketKind.Payment` with a path_key every failure is remapped to `InvalidOnionBlinding` (original as inner exception). `pathKey` is only the path_key received with the onion (update_add_htlc TLV 0 / onion_message), never the payload's current_path_key. `OnionPacketKind.OnionMessage` allows payloads of 0-1 bytes. `PeeledOnion.PathKeySharedSecret` is ECDH(path_key, node_key) for M5. `ConstructWithSharedSecrets` returns the per-hop secrets without a second ECDH pass. Semantic hop-payload validation is not done here.
- Error onions (M3): `Onion/FailureOnionService` (internal, Domain `IFailureOnionService`, singleton in `AddBitcoinInfrastructure`). It needs `IFailureMessageSerializer`, which only `AddSerializationInfrastructureServices` registers (this project cannot reference Serialization), so resolve it where both layers are added (the Daemon and the Docker DI do). `CreateErrorPacket(ss, message, minFailurePadLength = 256)` = ammag XOR (HMAC(um, body) || body); the internal static `CreateErrorPacket(ss, framedBody)` takes pre-framed bytes. `CreateErrorPacketFromMalformed(incomingSs, code, sha256OfOnion)` converts an `update_fail_malformed_htlc` (via `FailureMessage.FromMalformed`, then `CreateErrorPacket`; this node is the erring node). `WrapErrorPacket` truncates to 32768 then XORs the ammag stream (self-inverse). `DecryptErrorPacket(hopSecrets, packet)` runs max(27, hops) iterations, using a constant all-zero dummy secret past the route end, constant-time HMAC compare, and never attributes a dummy iteration; returns `null` when no hop matches (or the packet is < 32 bytes), else `DecryptedFailure` (message null if the framing/failuremsg is unparsable). Vectors: `test/NLightning.Integration.Tests/BOLT4/FailureOnionVectorTests.cs` (onion-error-test.json and the inline spec trace, every hop, both directions).
- Replay-set pruning (NL-327): `Onion/OnionReplayBlockPruner` subscribes to `IBlockchainMonitor.OnNewBlockDetected` (`Start()`/`StopAsync()`, the host's job, after the monitor starts and before it stops) and calls `IOnionReplayStore.PruneAsync(height)` on its own task: one prune at a time, coalesced to the highest height seen, lower/repeated heights ignored, a failed prune logged and retried at once when a higher block arrived during it, else by the next block (the requested height is kept); `WhenIdleAsync()` for tests. **Not wired yet**: nothing registers it or calls `Start()`/`StopAsync()` in the daemon's hosted service or the Docker `NLightningTestNode`, so a running node still prunes only lazily in `TryAddAsync`. The SQLite proof awaits `WhenIdleAsync()` after every block, because `SqliteTestDatabase` shares one connection and a prune overlapping the next block's save transaction fails. Registered by `Onion/OnionReplayPruningServiceCollectionExtensions.AddOnionReplayBlockPruner()` (TryAdd singleton; needs `IBlockchainMonitor` and `IOnionReplayStore`). Tests: `test/NLightning.Infrastructure.Bitcoin.Tests/Onion/OnionReplayBlockPrunerTests`, SQLite proof in `Integration.Tests/Persistence/ChainMonitorPersistenceTests`.
- Attributable failures (M3b): `Onion/AttributionDataService` (internal, Domain `IAttributionDataService`, singleton through `Onion/AttributionServiceCollectionExtensions.AddOnionAttributionServices()`, needs `IFailureOnionService`). Layout: hold times (20 × u32 BE, this node's first) then 210 truncated HMACs; node `x`'s block starts at `x*20 - x(x-1)/2` and holds positions 19-x..0, `hmac_0_y` at index `19 - y`; `hmac_0_y` = first 4 bytes of HMAC(um, message || hold_times[0..y] || hmac_j_(y-j) for j = 1..y at `start(j) + 19 - y`). Update = shift right (prune the left-most HMAC of each block, drop the last hold time and node 19's block), put hold time and 20 HMACs in front, XOR the `ammagext` stream; a missing or wrong-length downstream block counts as all zero. The message is the return packet before the node's own `ammag` (for the erring node the created packet XORed once more, the stream being self-inverse), the downstream `fulfillment_payload` for an intermediate fulfill, nothing for the final node's fulfill. The origin verifies hop `i` at position `route length - 1 - i` (only up to the legacy erring hop; every hop when none), shifting left after each hop (pruned bytes are never covered within 20 hops); routes over 20 hops are not verified. `fulfillment_payload`: `fulfillment_payload_tlvs` (records sorted, `padding` type 1 so the stream is a multiple of 256, 256 when possible; a stream of 255 or 256 bytes cannot be padded exactly, so e.g. padding alone takes 512) ChaCha20-Poly1305 under HMAC("fulfillment", ss) with a zero nonce and no AD (the Infrastructure `ChaCha20Poly1305` with nonce 0); intermediates XOR `ammag`; the origin peels hops 0..n-2 and decrypts with hop n-1's key, reading the stream strictly (canonical BigSize, increasing types, no unknown even type). Vectors: `test/NLightning.Integration.Tests/BOLT4/AttributionVectorTests.cs` (both inline traces byte for byte at every hop, origin verification, tampering, partial support).
- HTLC-success/timeout transactions are built, signed and vector-tested (NL-056, NL-057): `test/NLightning.Integration.Tests/BOLT3/Bolt3HtlcSignerVectorTests` checks our `local_htlc_signature`s (Appendix C/F) byte for byte, validates every `remote_htlc_signature` (Appendix F only as `SINGLE|ANYONECANPAY`), rejects tampered/high-S/reordered/missing sigs, and, signing as node B, reproduces the `remote_htlc_signature` list in output order. The offered/received HTLC scripts and commitment building with HTLCs are complete and vector-tested.
