# NLightning.Infrastructure.Bitcoin

This project is the NBitcoin-backed implementation of the Domain's Bitcoin and crypto ports. It builds BOLT 3 funding and commitment transactions from Domain models and generates the output scripts. It also handles BOLT 3 key derivation, the local signer, HD key storage, the wallet, fee polling, and chain monitoring over bitcoind RPC plus ZMQ `rawblock`. It also holds the BOLT 4 Sphinx core (`Onion/`); the only protocol-message code is `InteractiveTransactionService` (tx_add/remove payload validation). `ITlvConverterFactory` is registered by `AddInfrastructureServices`/`AddSerializationInfrastructureServices`, not here. Target is net10.0 (via src/Directory.Build.props), csproj version 1.0.0.

## Layout
- `Builders/`: `CommitmentTransactionBuilder`, `FundingTransactionBuilder` and `FundingOutputBuilder`. They take a Domain `*Model`/`*OutputInfo` and return an UNSIGNED tx as Domain `SignedTransaction(txid, rawBytes)`. `FundingTransactionBuilder` returns `FundingTransactionBuildResult` (tx + funding output index; inputs and outputs are both BIP 69 ordered, so a rebuild from the same UTXOs gives the same txid) and never mutates the model; the caller sets `FundingOutputInfo.TransactionId/Index`. Change/dust/fee decisions are made in Domain `FundingTransactionModelFactory` (typed `InsufficientFundsException`, dust change folded into the fee). `CommitmentTransactionBuilder.BuildWithOutputMap` returns `CommitmentTransactionBuildResult` (unsigned tx + `HtlcOutputsInTxOrder`: each untrimmed `HtlcOutputInfo` with its `Vout`, in transaction order, which is the order of HTLC transactions and `htlc_signatures`); `Build` is a wrapper returning only the tx. Outputs are sorted with a stable `OrderBy` over `TransactionOutputComparer`, so identical outputs keep the model order. `HtlcTransactionBuilder` (`IHtlcTransactionBuilder`, singleton in `AddBitcoinInfrastructure`) builds HTLC-timeout/HTLC-success txs from a Domain `HtlcTransactionModel` (made by the static Domain `HtlcTransactionModelFactory` from the commitment model + its output map): `Build` returns `HtlcTransactionBuildResult` (unsigned tx, spent witness script, spent amount: the BIP 143 sighash inputs) and `AddWitness` assembles `0 <remotesig> <localsig> <preimage|empty> <witnessScript>` (remote sighash `SINGLE|ANYONECANPAY` with anchors, else `ALL`; local always `ALL`). `ClosingTransactionBuilder` (`IClosingTransactionBuilder`, singleton in `AddBitcoinInfrastructure`, BOLT2 plan N10-T2) builds the BOLT 3 legacy closing tx from a Domain `ClosingTransactionModel` (version 2, locktime 0, the funding outpoint with sequence 0xFFFFFFFF, outputs ordered by amount then scriptpubkey as memcmp with the shorter first) and `AddWitness(unsigned, funding, localSig, remoteSig)` assembles `0 <sig for the lesser funding key> <sig for the greater> <2-of-2 script>`, both `SIGHASH_ALL`; sign it with `ILightningSigner.SignChannelTransaction` and check the peer's with `ValidateSignature`. BOLT 3 has no closing-tx vector: `Builders/ClosingTransactionBuilderTests` checks each field and verifies the signed tx with NBitcoin's interpreter. `SweepTransactionBuilder` (`ISweepTransactionBuilder`, BOLT 5 plan O3-T1) builds sweeps and claims from Domain `SweepInput`s: version 2, one output to the destination script, `nSequence` = the input's CSV or 0xFFFFFFFD, `nLockTime` = the `cltv_expiry` of the timeout claims; timeout claims are never batched with any other spend kind and all share one `cltv_expiry` (the caller groups them by expiry), and a preimage claim (whose `CltvExpiry` is its deadline) is refused when `nLockTime >= cltv_expiry`; `Build(inputs, destination, feeratePerKw, lockTime)` charges `SweepWeights.FeeSat` of the estimated weight (73-byte signatures), `BuildWithFee` an absolute fee (RBF); it validates each input for its spend kind (CSV, point, pubkey, cltv, 32-byte preimage, secret, a revocation pubkey whose HASH160 is in the script) and refuses an output below the destination's dust limit. `AddWitnesses(unsigned, sigs)` / `Sign(unsigned, signer, channelId)` assemble the BOLT 3 witnesses (internal static `CreateWitness`). `PenaltyTransactionBuilder` (`IPenaltyTransactionBuilder`, O5-T1) wraps it: `BuildBatched` (penalty inputs plus optionally our `to_remote`), `BuildSingle`, `BuildSplit` (one tx per input, B5-REV-08); nLockTime 0, every input replaceable. Both are singletons through `Onchain/OnchainServiceCollectionExtensions.AddOnchainBitcoinServices()` (the sweep builder needs `IOptions<NodeOptions>`). The interfaces are in `Builders/Interfaces/`, except `IFundingOutputBuilder`, which sits in `Builders/`.
- `Outputs/`: `BaseOutput` (implements Domain `IOutput`) and `BaseHtlcOutput`, with subclasses `FundingOutput`, `ToLocalOutput`, `ToRemoteOutput`, `ToAnchorOutput`, `OfferedHtlcOutput`, `ReceivedHtlcOutput`, `HtlcResolutionOutput` and `ChangeOutput`.
- `Comparers/TransactionOutputComparer.cs`: BOLT 3 output ordering (amount, then scriptPubKey, then cltv_expiry).
- `Services/`: `KeyDerivationService` (BOLT 3 derivation and per-commitment secrets), `CommitmentKeyDerivationService`, `PerCommitmentSecretVerifier` (Domain `IPerCommitmentSecretVerifier`, singleton in `AddBitcoinInfrastructure`: `Verify(secret, point)` checks `secret*G == point` and rejects invalid scalars; `VerifyAndStore(secret, remoteCommitmentNumber, point, shachain)` inserts into the peer's shachain at `PerCommitmentIndex.From(n)` only after the point matched; the revoke_and_ack receive check), `FeeService` (registered by the Daemon via `AddHttpClient<IFeeService, FeeService>`), `DustService` (singleton in `AddBitcoinInfrastructure`; depends on `IFeeService`, which the host registers) and `InteractiveTransactionService` (not registered in any DI container).
- `Signers/LocalLightningSigner.cs`: implements `ILightningSigner`. Channel key m/6425'/0'/0'/0/i has hardened children 0'-5' (funding, revocation, payment, delayed, htlc, per-commitment seed). `GetPerCommitmentPoint`/`RevealPerCommitmentSecret` take a **commitment number** and derive the secret at index `PerCommitmentIndex.From(n) = 2^48-1-n` (NL-187). **Revocation guard (NL-189):** `RevealPerCommitmentSecret(channelId, n)` throws `SignerException` unless `n < LocalCommitmentNumber`; that number comes from `ChannelSigningInfo.LocalCommitmentNumber` at `RegisterChannel` (re-registering never lowers it) and moves only through `AdvanceLocalCommitment(channelId, n)` (monotonic; call it only after the new local commitment is persisted). There is no index-keyed or unguarded secret API any more; `CommitmentKeys` carries no secret (local keys are derived from the point). **HTLC signatures (NL-057):** `SignRemoteHtlcTransactions` (our sigs for the peer's commitment, key `htlc_basepoint_secret + SHA256(point || htlc_basepoint)` from the protected virtual `GetHtlcBasepointSecret`, `SINGLE|ANYONECANPAY` with anchors else `ALL`), `ValidateLocalHtlcSignatures` (count, compact parse, low-S, verify against `ChannelSigningInfo.RemoteHtlcBasepoint` tweaked by our point) and `SignLocalHtlcTransaction` (our own HTLC tx, always `ALL`). Each takes a Domain `HtlcSigningContext(HtlcTransactionBuildResult, PerCommitmentPoint, HasAnchors)`; signatures are RFC 6979 without low-R grinding, `MakeCanonical()`. **Broadcast signing and data loss (N9-T4):** `SignLocalCommitmentForBroadcast(channelId, number, unsignedCommitment, remoteSignature)` validates the peer's signature, signs with our funding key and returns the transaction with the BOLT 3 witness `0 <sig1> <sig2> <funding script>` in the script's key order (byte-exact against Appendix C commit tx 0, `test/NLightning.Infrastructure.Bitcoin.Tests/Signers/LocalLightningSignerBroadcastTests`); it refuses `number <` the current local commitment number (revoked, I4). `MarkDataLoss(channelId)` (also set by `RegisterChannel` when `ChannelSigningInfo.DataLossDetected`; sticky) makes it refuse `SignChannelTransaction`, `SignRemoteHtlcTransactions`, `SignLocalHtlcTransaction` and the broadcast signing with `SignerException` (I12). **Invariant S1 (BOLT 5 plan §3.5, O2-T1):** `SignLocalCommitmentForBroadcast` calls `MarkBroadcastSigned(channelId, n)` before it returns; `RegisterChannel` applies `ChannelSigningInfo.BroadcastSignedCommitmentNumber` with `MarkBroadcastSigned`, so the host restores the mark by filling that field from the persisted commitment broadcast row (O2-T2 wiring; not done yet, the mark is memory only until then). The I4/S1 checks, the broadcast signature and its mark hold a per-channel `System.Threading.Lock` shared with `AdvanceLocalCommitment`, `RevealPerCommitmentSecret`, `MarkBroadcastSigned` and `RegisterChannel`, so S1 holds without the caller's channel lock. Once marked (sticky, the lowest number wins, `TryGetBroadcastSignedCommitment` reads it) the signer refuses `RevealPerCommitmentSecret(m >= n)`, `AdvanceLocalCommitment(> n)`, `SignLocalCommitmentForBroadcast` of any other number (the same number may be signed again for a rebroadcast), `SignChannelTransaction` and `SignRemoteHtlcTransactions`; `SignLocalHtlcTransaction` (our HTLC-timeout/success for the on-chain resolution) stays allowed. The broadcast path signs the funding input through the private unguarded `SignFundingInput`. **Sweeps (BOLT 5 plan O3-T1):** `SignSweepInput(channelId, SweepSigningContext)` signs one input (`SIGHASH_ALL`, BIP 143, RFC 6979, low-S, 64-byte compact) with the key the context's `SweepKeyKind` names: `DelayedPayment` (delayed basepoint secret tweaked by our point), `Payment` (payment basepoint secret, static_remotekey; a null witness script means P2WPKH, script code P2PKH), `HtlcRemotePoint` (HTLC basepoint secret tweaked by the peer's point) or `Revocation` (`DeriveRevocationPrivKey(revocation basepoint secret, peer secret)`, and a given point must equal `secret * G`). The derived pubkey or its HASH160 must be pushed by the witness script, else `SignerException` (a wrong kind, point or secret never signs). Not blocked by data loss or S1. The basepoint secrets come from the protected virtual `GetRevocationBasepointSecret`/`GetPaymentBasepointSecret`/`GetDelayedPaymentBasepointSecret`/`GetHtlcBasepointSecret` (tests override them with the Appendix C secrets: `test/.../Signers/AppendixCSweepSigner`); derived keys are wiped after use. **BOLT 7 node signatures (W0-E):** `SignNodeMessage(Hash)` signs the given 32-byte hash as is with the node key (from `ISecureKeyManager.GetNodeKeyPair()`, whose private-key copy is zeroed after parsing) through NBitcoin.Secp256k1 (`ECPrivKey.TrySignECDSA`: RFC 6979, low-S, 64-byte compact); `VerifyNodeMessage(hash, signature, nodeId)` returns false for an unparsable signature/pubkey and accepts high-S (normalized first; BOLT 7 relays may malleate s). The caller hashes: for channel_update `ChannelUpdatePayload.GetSignatureHash()` = SHA256d of the bytes after the signature. Tests: `Signers/LocalLightningSignerNodeMessageTests.cs` (an LND-captured channel_update verifies with LND's node id).
- `Managers/SecureKeyManager.cs`: implements `ISecureKeyManager`. The master key lives in locked memory, and the key file is encrypted with Argon2id + XChaCha20-Poly1305.
- `Wallet/`: `BitcoinChainService` (RPC, incl. `GetBlockHashAsync` for reorg detection), `BitcoinWalletService` (deposit addresses), `BlockchainMonitorService` (ZMQ, watched txs, watched outpoints, UTXOs, the broadcast set, reorgs; BOLT 5 plan O0). Interfaces are in `Wallet/Interfaces/`; `IBlockchainMonitor` extends the Domain ports `IChainBroadcaster` and `IOutpointWatcher` (`src/NLightning.Domain/Onchain/Interfaces/`), which `AddBitcoinInfrastructure` registers as the same singleton. The monitor keeps watching a wallet address after a deposit (as after a restart, which reloads them all). `TrackWatchedTransaction` follows a watch row the caller saved in its own save (the mutual close saves it with Closing) and `PublishTransactionAsync` only broadcasts (nothing stored). **Per block (NL-214):** everything a block changes (first sightings and depths of watched txs, deposits and wallet spends, outpoint spends, confirmations of our broadcasts, the blockchain state and the header ring) is staged in one unit of work without touching memory; memory is updated and the events are raised (`OnNewBlockDetected`, `OnTransactionConfirmed`, `OnWalletMovementDetected`, `OnWatchedOutpointSpent`, in that order) only after that save, so a failed attempt leaves nothing and raises nothing. **Outpoints (O0-T2):** `WatchOutpointAsync` (own save) / `TrackWatchedOutpoint` (caller's save) are persisted watches, reloaded at start (`GetActiveAsync`, every watch of a channel that is not Closed/Stale); `WatchOutpointSpend`/`StopWatchingOutpointSpend` stay memory-only. Every stored channel past funding_created gets its funding output watched: at start (`AddMissingFundingOutpointsAsync`), when a watched funding tx is first seen in a block (`AddFundingOutpointIfMissingAsync`, the fundee path, before the block's spends are checked) and at funding_signed (funder, `FundingSignedMessageHandler`). `OnWatchedOutpointSpent` (`OutpointSpentEventArgs`: channel, spending tx, height, index in block, the spent outpoint, block hash) is raised for every processed block that spends the outpoint, also on a replayed block (the last processed block is replayed at start) and on a new branch after a reorg, so listeners must be idempotent. **Broadcasts (O0-T1, NL-258):** `PublishAsync(model)` sends a tx whose `BroadcastTransactionModel` row the caller saved (never throws for a refusal; true when accepted or already known), `SaveAndPublishAsync` saves it first; every `Pending` row is sent again after each processing round and at start, also when processing is halted (a halted round or a halted startup rewind), until a processed block holds it (then `Confirmed`). A refusal is logged at Warning the first time and then every `RefusalWarningInterval` (6) refusals in a row, at Debug in between; there is no abandonment rule yet (a funding tx the node refuses for good is retried forever, NL-259 follow-up). `PublishAndWatchTransactionAsync` saves the watch and a pending row (purpose `Unspecified`) in one save, then sends and still throws a refusal. **Reorgs (O0-T3, NL-096):** the hashes of the last `HeaderRingSize` (100) processed blocks are kept (`BlockHeaders`). A block whose hash differs from the stored one at its height, or the next block whose parent is not our tip, starts a rewind, unless bitcoind still has our last processed block at its height: then the block is a late notification of an orphan and is dropped (no rewind, no `OnBlockDisconnected`). The fork point is the highest ring height, searched from our last processed block down (capped at bitcoind's tip), whose hash bitcoind still has; one save resets the first-seen height of pending watches above it, clears outpoint spends and broadcast confirmations above it, deletes the headers and rewinds the state; memory is reloaded, `OnBlockDisconnected` is raised per disconnected block (highest first), then the active chain from the fork point to its tip is queued. A watch already completed in a disconnected block is logged Critical and not rolled back (its consumer, e.g. the funding confirmation and the SCID, is not undone; BOLT 5 plan O6-T3, so NL-096 is only partly fixed; the Docker `Onchain/OnchainSmokeTests` explicit test reproduces the stale SCID). A reorg deeper than the ring, or a chain tip below our height at start with no ring hash in common, halts processing. A block below our height with the stored hash (e.g. after `reconsiderblock`) is dropped. The tip is processed at start (NL-215). `IsChainProcessingHalted` is on `IBlockchainMonitor` (NL-216; no IPC or channel-operation gate yet). Wallet effects of disconnected blocks are not rolled back: a deposit stays a spendable UTXO and a wallet spend stays deleted (spent UTXO rows are deleted, so a rollback needs a spent-at height first).
- `Crypto/`: `Functions/Ecdh.cs` (internal; `IEcdh` = SHA256(compressed k*P)), `Functions/Secp256K1Math.cs` (`ISecp256K1Math`: pubkey/privkey tweak-mul and add, validated via `ECPubKey`/`ECPrivKey.TryCreate`), `Contexts/NLightningCryptoContext.cs` (internal blinded secp256k1 Context), `Hashes/Ripemd160.cs`.

Vectors: `test/NLightning.Integration.Tests/BOLT4/OnionVectorTests.cs` (onion-test.json byte-exact construct + peel chain, onion-error-test.json per-hop keys, blinded-payment-onion-test.json peel chain); unit tests in `test/NLightning.Infrastructure.Bitcoin.Tests/Onion/`.

The output candidates are converted exactly as `CommitmentTransactionBuilder` converts them (anchor script forms follow the presence of anchor outputs), so keep the two in step. `Map(model, htlcs, case, tx?)` takes an already built model. `FindPaymentToRemote(tx, ourPaymentBasepoint, hasAnchors)` finds our static_remotekey `to_remote` in a peer commitment we cannot rebuild (data loss). ## Adding a new output or transaction type
1. Output script: subclass `BaseOutput` (or `BaseHtlcOutput`) in `Outputs/`, and pass the redeem script (from a static `Generate*Script(...)`) and the `ScriptType` to `base(amount, script, scriptType)`; `ScriptType` is a get-only base property, never a virtual override (the base ctor derives `ScriptPubKey` from it). Throw `InvalidScriptException` when `script.IsUnspendable || !script.IsValid`.
2. If the output goes on commitment txs, add the Domain `*OutputInfo` -> output conversion in `CommitmentTransactionBuilder.Build` and check how `TransactionOutputComparer` tie-breaks it.
3. For a new transaction type (e.g. HTLC-success/timeout): add a data-only Domain model/factory in `src/NLightning.Domain/Bitcoin/Transactions/`, then add an `IXBuilder` in `Builders/Interfaces/` and `XBuilder` in `Builders/`. Signing goes through `ILightningSigner` (add a method there and implement it in `LocalLightningSigner`).
4. Register singletons in `DependencyInjection.AddBitcoinInfrastructure` (only `IBitcoinWalletService` is scoped). `ILightningSigner` (`LocalLightningSigner`) is registered there too and takes the host's `ISecureKeyManager` from DI. `SecureKeyManager` and `FeeService` (HttpClient) are registered by the host (`NodeServiceExtensions.AddNltgNodeServices`, which the Docker tests also use). Services in `AddBitcoinInfrastructure` may depend on them (e.g. `CommitmentKeyDerivationService` takes `ILightningSigner`).
5. Add tests in `test/NLightning.Infrastructure.Bitcoin.Tests/<Folder>/`, plus BOLT 3 vectors in `test/NLightning.Integration.Tests/BOLT3/` if applicable.

## Conventions
- Use a file-scoped namespace. External usings (NBitcoin, Microsoft.*) go above it; NLightning usings go below it as relative names (`using Domain.Money;`).
- Domain value objects cross the boundary as bytes and are converted here (`new PubKey(compactPubKey)`, `new uint256(txId)`). Domain stays NBitcoin-free.
- Resolve the network with `Network.GetNetwork(nodeOptions.BitcoinNetwork)` and throw on an unknown one (every class here does, the `Wallet/` services since BOLT 5 plan O0).
- Singletons that need the DB create a scope per operation: `CreateScope()` then `GetRequiredService<IUnitOfWork>()` (see `Wallet/BlockchainMonitorService.cs`).
- Guard logging with `_logger.IsEnabled(...)`. Name tests `Given_X_When_Y_Then_Z` (xUnit v3 + Moq).
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate: `_field`/`s_field` naming, no unused usings.

## Gotchas (verified bugs)
- `WatchedTransactionModel.TransactionIndex` is the position in the block (coinbase = 0), a `uint` capped at 24 bits (NL-102). Rows written before migration `WidenWatchedTransactionIndex` may hold the old watched-only index, and channels confirmed then carry a wrong persisted `ShortChannelId`; nothing repairs them.
- `BlockchainMonitorService` block failures (NL-097): a block whose `ProcessBlock` throws is retried `MaxBlockProcessingAttempts` (3) times with doubling backoff from `BlockRetryBaseDelay` (1s); then the round halts with a Critical log and `IsChainProcessingHalted` is set, leaving it and later blocks queued (never skipped). The next ZMQ block or a restart retries from it. The queue holds at most `MaxQueuedBlocks` (144); later blocks are refetched from bitcoind once it drains. Replays (the last processed block is re-queued on start, and failed blocks are retried) skip deposits whose UTXO is already in `IUtxoMemoryRepository`, but still re-raise `OnNewBlockDetected`. Each attempt is its own unit of work, so a failed attempt persists nothing (NL-214). The halt only recovers if the failure is transient; nothing fails the node if it persists (the flag is on `IBlockchainMonitor`, NL-216).
- `InteractiveTransactionService` validates messages **received from the peer**: its `isInitiator` ctor flag means the local node, and it passes `!isInitiator` to the `Tx*Validator`s as the sender role. Serial ids are unique across inputs and outputs together; removals are checked against the matching collection.
- `SecureKeyManager` writes v2 key files (random 16-byte salt, random 24-byte nonce, Argon2id 64 MiB/3 passes, all stored in the file). v1 files (fixed `s_legacySalt`, zero nonce, 64 KiB) are still read and are rewritten as v2 by `FromFilePath`, after copying the original to `<file>.v1.bak`. Writes are atomic (temp file + move) and keep the target's Unix mode (new files `0600`) and symlinks. Passwords are hashed as full UTF-8; a file that only opens with the old libsodium truncated encoding (first `password.Length` UTF-8 bytes) is also rewritten. The node key (`GetNodeKeyPair`) is the master key itself. `ComputeNodeSharedSecret` (node-key ECDH) copies it out of locked memory only for the operation and wipes the copy. `ISecureKeyManager` implementations: `SecureKeyManager`, the Docker `FakeSecureKeyManager`, and the test-only `EcdhOnlyKeyManager` (Moq cannot set up its span-parameter method).
- `LocalLightningSigner.SignChannelTransaction` hardcodes input 0 + SIGHASH_ALL (commitment and closing txs only); HTLC transactions go through the HTLC methods above.
- `LocalLightningSigner.SignWalletTransaction` throws NotImplementedException, and channel signing info is memory-only (re-register via `RegisterChannel`).
- `BitcoinChainService`'s constructor makes a blocking RPC call, so DI resolution fails if bitcoind is down.

## Onion-routing (BOLT 4) hooks
- `Ecdh.SecP256K1Dh` already computes the Sphinx per-hop shared secret, SHA256(compressed(k*P)).
- EC math for ephemeral-key blinding lives behind the Domain port `ISecp256K1Math` (`MultiplyPubKey`, `MultiplyPrivKey`, `AddPubKeys`, `AddPrivKeys`), implemented by `Crypto/Functions/Secp256K1Math.cs` (on `NLightningCryptoContext`, registered as a singleton in `AddBitcoinInfrastructure`). `KeyDerivationService` consumes it; do not reintroduce private EC helpers. Sphinx code that needs EC math should depend on `ISecp256K1Math`, except the per-hop key chain in `OnionBuilder.ComputeHopKeys`, which works on `ECPrivKey` directly (CreatePubKey/ECDH/TweakMul on one parsed key, ~35% faster and ~70% fewer managed allocations per hop than the `IEcdh` + `ISecp256K1Math` round trips).
- Peeling needs node-key ECDH: `ISphinxService.PeelAsLocalNode` does it through `ISecureKeyManager.ComputeNodeSharedSecret` (the node key never leaves the key manager; route blinding tweaks the ephemeral key, ECDH(k*t, E) = ECDH(k, t*E), instead of the node key); `Peel(..., PrivKey nodeKey, ...)` takes the key explicitly. `OnionPeeler` takes either through its `NodeEcdh` delegate. The two are named differently on purpose, because a `byte[]` converts implicitly to both `PrivKey` and `CompactPubKey` (the path key).
- Every packet-caused `Peel` failure is an `OnionException` (only caller bugs, such as a bad node key or a `default` packet, throw anything else): BADONION codes (`InvalidOnionVersion`/`Key`/`Hmac`/`Blinding`) carry sha256_of_onion as `FailureData`; framing errors (after the HMAC verified) are `InvalidOnionPayload` with data `00 0000` (type 0, offset 0) and a copy of the shared secret in `OnionException.SharedSecret` (needed to encrypt the non-BADONION failure). For `OnionPacketKind.Payment` with a path_key every failure is remapped to `InvalidOnionBlinding` (original as inner exception). `pathKey` is only the path_key received with the onion (update_add_htlc TLV 0 / onion_message), never the payload's current_path_key. `OnionPacketKind.OnionMessage` allows payloads of 0-1 bytes. `PeeledOnion.PathKeySharedSecret` is ECDH(path_key, node_key) for M5. `ConstructWithSharedSecrets` returns the per-hop secrets without a second ECDH pass. Semantic hop-payload validation is not done here.
- Error onions (M3): `Onion/FailureOnionService` (internal, Domain `IFailureOnionService`, singleton in `AddBitcoinInfrastructure`). It needs `IFailureMessageSerializer`, which only `AddSerializationInfrastructureServices` registers (this project cannot reference Serialization), so resolve it where both layers are added (the Daemon and the Docker DI do). `CreateErrorPacket(ss, message, minFailurePadLength = 256)` = ammag XOR (HMAC(um, body) || body); the internal static `CreateErrorPacket(ss, framedBody)` takes pre-framed bytes. `CreateErrorPacketFromMalformed(incomingSs, code, sha256OfOnion)` converts an `update_fail_malformed_htlc` (via `FailureMessage.FromMalformed`, then `CreateErrorPacket`; this node is the erring node). `WrapErrorPacket` truncates to 32768 then XORs the ammag stream (self-inverse). `DecryptErrorPacket(hopSecrets, packet)` runs max(27, hops) iterations, using a constant all-zero dummy secret past the route end, constant-time HMAC compare, and never attributes a dummy iteration; returns `null` when no hop matches (or the packet is < 32 bytes), else `DecryptedFailure` (message null if the framing/failuremsg is unparsable). Vectors: `test/NLightning.Integration.Tests/BOLT4/FailureOnionVectorTests.cs` (onion-error-test.json and the inline spec trace, every hop, both directions).
- HTLC-success/timeout transactions are built, signed and vector-tested (NL-056, NL-057): `test/NLightning.Integration.Tests/BOLT3/Bolt3HtlcSignerVectorTests` checks our `local_htlc_signature`s (Appendix C/F) byte for byte, validates every `remote_htlc_signature` (Appendix F only as `SINGLE|ANYONECANPAY`), rejects tampered/high-S/reordered/missing sigs, and, signing as node B, reproduces the `remote_htlc_signature` list in output order. The offered/received HTLC scripts and commitment building with HTLCs are complete and vector-tested.
