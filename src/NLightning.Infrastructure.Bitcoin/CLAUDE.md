# NLightning.Infrastructure.Bitcoin

This project is the NBitcoin-backed implementation of the Domain's Bitcoin and crypto ports. It builds BOLT 3 funding and commitment transactions from Domain models and generates the output scripts. It also handles BOLT 3 key derivation, the local signer, HD key storage, the wallet, fee polling, and chain monitoring over bitcoind RPC plus ZMQ `rawblock`. It also holds the BOLT 4 Sphinx core (`Onion/`); the only protocol-message code is `InteractiveTransactionService` (tx_add/remove payload validation). `ITlvConverterFactory` is registered by `AddInfrastructureServices`/`AddSerializationInfrastructureServices`, not here. Target is net10.0 (via src/Directory.Build.props), csproj version 1.0.0.

## Layout
- `Builders/`: `CommitmentTransactionBuilder`, `FundingTransactionBuilder` and `FundingOutputBuilder`. They take a Domain `*Model`/`*OutputInfo` and return an UNSIGNED tx as Domain `SignedTransaction(txid, rawBytes)`. `FundingTransactionBuilder` returns `FundingTransactionBuildResult` (tx + funding output index; inputs and outputs are both BIP 69 ordered, so a rebuild from the same UTXOs gives the same txid) and never mutates the model; the caller sets `FundingOutputInfo.TransactionId/Index`. Change/dust/fee decisions are made in Domain `FundingTransactionModelFactory` (typed `InsufficientFundsException`, dust change folded into the fee). `CommitmentTransactionBuilder.BuildWithOutputMap` returns `CommitmentTransactionBuildResult` (unsigned tx + `HtlcOutputsInTxOrder`: each untrimmed `HtlcOutputInfo` with its `Vout`, in transaction order, which is the order of HTLC transactions and `htlc_signatures`); `Build` is a wrapper returning only the tx. Outputs are sorted with a stable `OrderBy` over `TransactionOutputComparer`, so identical outputs keep the model order. `HtlcTransactionBuilder` (`IHtlcTransactionBuilder`, singleton in `AddBitcoinInfrastructure`) builds HTLC-timeout/HTLC-success txs from a Domain `HtlcTransactionModel` (made by the static Domain `HtlcTransactionModelFactory` from the commitment model + its output map): `Build` returns `HtlcTransactionBuildResult` (unsigned tx, spent witness script, spent amount: the BIP 143 sighash inputs) and `AddWitness` assembles `0 <remotesig> <localsig> <preimage|empty> <witnessScript>` (remote sighash `SINGLE|ANYONECANPAY` with anchors, else `ALL`; local always `ALL`). The interfaces are in `Builders/Interfaces/`, except `IFundingOutputBuilder`, which sits in `Builders/`.
- `Outputs/`: `BaseOutput` (implements Domain `IOutput`) and `BaseHtlcOutput`, with subclasses `FundingOutput`, `ToLocalOutput`, `ToRemoteOutput`, `ToAnchorOutput`, `OfferedHtlcOutput`, `ReceivedHtlcOutput`, `HtlcResolutionOutput` and `ChangeOutput`.
- `Comparers/TransactionOutputComparer.cs`: BOLT 3 output ordering (amount, then scriptPubKey, then cltv_expiry).
- `Services/`: `KeyDerivationService` (BOLT 3 derivation and per-commitment secrets), `CommitmentKeyDerivationService`, `PerCommitmentSecretVerifier` (Domain `IPerCommitmentSecretVerifier`, singleton in `AddBitcoinInfrastructure`: `Verify(secret, point)` checks `secret*G == point` and rejects invalid scalars; `VerifyAndStore(secret, remoteCommitmentNumber, point, shachain)` inserts into the peer's shachain at `PerCommitmentIndex.From(n)` only after the point matched; the revoke_and_ack receive check), `FeeService` (registered by the Daemon via `AddHttpClient<IFeeService, FeeService>`), `DustService` (singleton in `AddBitcoinInfrastructure`; depends on `IFeeService`, which the host registers) and `InteractiveTransactionService` (not registered in any DI container).
- `Signers/LocalLightningSigner.cs`: implements `ILightningSigner`. Channel key m/6425'/0'/0'/0/i has hardened children 0'-5' (funding, revocation, payment, delayed, htlc, per-commitment seed). `GetPerCommitmentPoint`/`RevealPerCommitmentSecret` take a **commitment number** and derive the secret at index `PerCommitmentIndex.From(n) = 2^48-1-n` (NL-187). **Revocation guard (NL-189):** `RevealPerCommitmentSecret(channelId, n)` throws `SignerException` unless `n < LocalCommitmentNumber`; that number comes from `ChannelSigningInfo.LocalCommitmentNumber` at `RegisterChannel` (re-registering never lowers it) and moves only through `AdvanceLocalCommitment(channelId, n)` (monotonic; call it only after the new local commitment is persisted). There is no index-keyed or unguarded secret API any more; `CommitmentKeys` carries no secret (local keys are derived from the point). **HTLC signatures (NL-057):** `SignRemoteHtlcTransactions` (our sigs for the peer's commitment, key `htlc_basepoint_secret + SHA256(point || htlc_basepoint)` from the protected virtual `GetHtlcBasepointSecret`, `SINGLE|ANYONECANPAY` with anchors else `ALL`), `ValidateLocalHtlcSignatures` (count, compact parse, low-S, verify against `ChannelSigningInfo.RemoteHtlcBasepoint` tweaked by our point) and `SignLocalHtlcTransaction` (our own HTLC tx, always `ALL`). Each takes a Domain `HtlcSigningContext(HtlcTransactionBuildResult, PerCommitmentPoint, HasAnchors)`; signatures are RFC 6979 without low-R grinding, `MakeCanonical()`.
- `Managers/SecureKeyManager.cs`: implements `ISecureKeyManager`. The master key lives in locked memory, and the key file is encrypted with Argon2id + XChaCha20-Poly1305.
- `Wallet/`: `BitcoinChainService` (RPC), `BitcoinWalletService` (deposit addresses), `BlockchainMonitorService` (ZMQ, watched txs, UTXOs). Interfaces are in `Wallet/Interfaces/`.
- `Crypto/`: `Functions/Ecdh.cs` (internal; `IEcdh` = SHA256(compressed k*P)), `Functions/Secp256K1Math.cs` (`ISecp256K1Math`: pubkey/privkey tweak-mul and add, validated via `ECPubKey`/`ECPrivKey.TryCreate`), `Contexts/NLightningCryptoContext.cs` (internal blinded secp256k1 Context), `Hashes/Ripemd160.cs`.
- `Onion/`: BOLT 4 Sphinx. `SphinxService` (Domain `ISphinxService`, singleton in `AddBitcoinInfrastructure`, optional `ISecureKeyManager` for `PeelAsLocalNode`) over internal `OnionBuilder` (hop keys, variable-length filler, construction) and `OnionPeeler` (version -> key -> path_key tweak -> constant-time HMAC -> 2x rho stream -> canonical bigsize framing -> next epk = E*SHA256(E||ss)). `SphinxKeyGenerator` (HMAC(label, ss) keys, blinding factor, sha256_of_onion, and the per-hop ECDH `ComputeSharedSecret` on a parsed `ECPrivKey` hashed with one-shot BCL `SHA256.HashData`, also used statically by `SecureKeyManager.ComputeNodeSharedSecret` so `PeelAsLocalNode` allocates no hash state or NBitcoin `Key`/`PubKey` per ECDH; one generator + one `ChaCha20Stream` per construct/peel, and `IEcdh` is not used in the Sphinx hot path) and `SphinxBigSize` (this project cannot reference Serialization, so hop payloads cross as raw TLV bytes). Vectors: `test/NLightning.Integration.Tests/BOLT4/OnionVectorTests.cs` (onion-test.json byte-exact construct + peel chain, onion-error-test.json per-hop keys, blinded-payment-onion-test.json peel chain); unit tests in `test/NLightning.Infrastructure.Bitcoin.Tests/Onion/`.
- `Encoders/Bech32Encoder.cs`: internal. NLightning.Bolt11 uses it through InternalsVisibleTo (`AssemblyInfo.cs`).
- `Options/` (`BitcoinOptions` from config section "Bitcoin", `FeeEstimationOptions` from "FeeEstimation"), `Exceptions/InvalidScriptException.cs`, `Utils/ScriptCoinUtils.cs`.
- DEAD CODE: everything left in `Transactions/` is commented out (`PenaltyTransaction` is an empty class; the commented HTLC transaction classes were deleted for NL-056), and the `Adapters/OutputAdapters/` interfaces have no implementations. Don't revive either one. New transaction types follow the Builder-over-Domain-model pattern.

## Adding a new output or transaction type
1. Output script: subclass `BaseOutput` (or `BaseHtlcOutput`) in `Outputs/`, and pass the redeem script (from a static `Generate*Script(...)`) and the `ScriptType` to `base(amount, script, scriptType)`; `ScriptType` is a get-only base property, never a virtual override (the base ctor derives `ScriptPubKey` from it). Throw `InvalidScriptException` when `script.IsUnspendable || !script.IsValid`.
2. If the output goes on commitment txs, add the Domain `*OutputInfo` -> output conversion in `CommitmentTransactionBuilder.Build` and check how `TransactionOutputComparer` tie-breaks it.
3. For a new transaction type (e.g. HTLC-success/timeout): add a data-only Domain model/factory in `src/NLightning.Domain/Bitcoin/Transactions/`, then add an `IXBuilder` in `Builders/Interfaces/` and `XBuilder` in `Builders/`. Signing goes through `ILightningSigner` (add a method there and implement it in `LocalLightningSigner`).
4. Register singletons in `DependencyInjection.AddBitcoinInfrastructure` (only `IBitcoinWalletService` is scoped). `SecureKeyManager`, `LocalLightningSigner` and `FeeService` are NOT registered there; they are wired by hand in `src/NLightning.Daemon/Extensions/NodeServiceExtensions.cs` AND in the Docker tests (`test/NLightning.Integration.Tests/Docker/AbcNetworkTests.cs`, `ChannelOpeningFlowTests.cs`), so a change to their constructors must be mirrored in all three places. Services in `AddBitcoinInfrastructure` may depend on them (e.g. `CommitmentKeyDerivationService` takes `ILightningSigner`).
5. Add tests in `test/NLightning.Infrastructure.Bitcoin.Tests/<Folder>/`, plus BOLT 3 vectors in `test/NLightning.Integration.Tests/BOLT3/` if applicable.

## Conventions
- Use a file-scoped namespace. External usings (NBitcoin, Microsoft.*) go above it; NLightning usings go below it as relative names (`using Domain.Money;`).
- Domain value objects cross the boundary as bytes and are converted here (`new PubKey(compactPubKey)`, `new uint256(txId)`). Domain stays NBitcoin-free.
- Resolve the network with `Network.GetNetwork(nodeOptions.BitcoinNetwork)`. The builders, `LocalLightningSigner` and `SecureKeyManager` throw on an unknown network, but `BitcoinChainService`, `BitcoinWalletService` and `BlockchainMonitorService` fall back to `Network.Main`, which is inconsistent.
- Singletons that need the DB create a scope per operation: `CreateScope()` then `GetRequiredService<IUnitOfWork>()` (see `Wallet/BlockchainMonitorService.cs`).
- Guard logging with `_logger.IsEnabled(...)`. Name tests `Given_X_When_Y_Then_Z` (xUnit v3 + Moq).
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate: `_field`/`s_field` naming, no unused usings.

## Dependency rules
- Allowed: the ProjectReference to `NLightning.Infrastructure` (which brings in Domain), plus NBitcoin 9.0.5, NBitcoin.Secp256k1 3.2.0, NetMQ and MessagePack.
- MUST NOT reference Application, Daemon, Client, Serialization, Persistence/Repositories or Bolt11. Application references this project, not the reverse.

## Gotchas (verified bugs)
- `WatchedTransactionModel.TransactionIndex` is the position in the block (coinbase = 0), a `uint` capped at 24 bits (NL-102). Rows written before migration `WidenWatchedTransactionIndex` may hold the old watched-only index, and channels confirmed then carry a wrong persisted `ShortChannelId`; nothing repairs them.
- `BlockchainMonitorService` block failures (NL-097): a block whose `ProcessBlock` throws is retried `MaxBlockProcessingAttempts` (3) times with doubling backoff from `BlockRetryBaseDelay` (1s); then the round halts with a Critical log and `IsChainProcessingHalted` is set, leaving it and later blocks queued (never skipped). The next ZMQ block or a restart retries from it. The queue holds at most `MaxQueuedBlocks` (144); later blocks are refetched from bitcoind once it drains. Replays (the last processed block is re-queued on start, and failed blocks are retried) skip deposits whose UTXO is already in `IUtxoMemoryRepository`, but still re-raise `OnNewBlockDetected`. `ProcessNewBlock` still saves the uow after a halted round, so partial effects of the failed attempt persist. The halt only recovers if the failure is transient; nothing fails the node if it persists.
- `InteractiveTransactionService` validates messages **received from the peer**: its `isInitiator` ctor flag means the local node, and it passes `!isInitiator` to the `Tx*Validator`s as the sender role. Serial ids are unique across inputs and outputs together; removals are checked against the matching collection.
- `SecureKeyManager` writes v2 key files (random 16-byte salt, random 24-byte nonce, Argon2id 64 MiB/3 passes, all stored in the file). v1 files (fixed `s_legacySalt`, zero nonce, 64 KiB) are still read and are rewritten as v2 by `FromFilePath`, after copying the original to `<file>.v1.bak`. Writes are atomic (temp file + move) and keep the target's Unix mode (new files `0600`) and symlinks. Passwords are hashed as full UTF-8; a file that only opens with the old libsodium truncated encoding (first `password.Length` UTF-8 bytes) is also rewritten. The node key (`GetNodeKeyPair`) is the master key itself. `ComputeNodeSharedSecret` (node-key ECDH) copies it out of locked memory only for the operation and wipes the copy. `ISecureKeyManager` implementations: `SecureKeyManager`, the Docker `FakeSecureKeyManager`, and the test-only `EcdhOnlyKeyManager` (Moq cannot set up its span-parameter method).
- `LocalLightningSigner.SignChannelTransaction` hardcodes input 0 + SIGHASH_ALL (commitment and closing txs only); HTLC transactions go through the HTLC methods above.
- `LocalLightningSigner.SignWalletTransaction` throws NotImplementedException, and channel signing info is memory-only (re-register via `RegisterChannel`).
- `BitcoinChainService`'s constructor makes a blocking RPC call, so DI resolution fails if bitcoind is down.

## Onion-routing (BOLT 4) hooks
- `Ecdh.SecP256K1Dh` already computes the Sphinx per-hop shared secret, SHA256(compressed(k*P)).
- EC math for ephemeral-key blinding lives behind the Domain port `ISecp256K1Math` (`MultiplyPubKey`, `MultiplyPrivKey`, `AddPubKeys`, `AddPrivKeys`), implemented by `Crypto/Functions/Secp256K1Math.cs` (on `NLightningCryptoContext`, registered as a singleton in `AddBitcoinInfrastructure`). `KeyDerivationService` consumes it; do not reintroduce private EC helpers. Sphinx code that needs EC math should depend on `ISecp256K1Math`, except the per-hop key chain in `OnionBuilder.ComputeHopKeys`, which works on `ECPrivKey` directly (CreatePubKey/ECDH/TweakMul on one parsed key, ~35% faster and ~70% fewer managed allocations per hop than the `IEcdh` + `ISecp256K1Math` round trips).
- Peeling needs node-key ECDH: `ISphinxService.PeelAsLocalNode` does it through `ISecureKeyManager.ComputeNodeSharedSecret` (the node key never leaves the key manager; route blinding tweaks the ephemeral key, ECDH(k*t, E) = ECDH(k, t*E), instead of the node key); `Peel(..., PrivKey nodeKey, ...)` takes the key explicitly. `OnionPeeler` takes either through its `NodeEcdh` delegate. The two are named differently on purpose, because a `byte[]` converts implicitly to both `PrivKey` and `CompactPubKey` (the path key).
- Every packet-caused `Peel` failure is an `OnionException` (only caller bugs, such as a bad node key or a `default` packet, throw anything else): BADONION codes (`InvalidOnionVersion`/`Key`/`Hmac`/`Blinding`) carry sha256_of_onion as `FailureData`; framing errors (after the HMAC verified) are `InvalidOnionPayload` with data `00 0000` (type 0, offset 0) and a copy of the shared secret in `OnionException.SharedSecret` (needed to encrypt the non-BADONION failure). For `OnionPacketKind.Payment` with a path_key every failure is remapped to `InvalidOnionBlinding` (original as inner exception). `pathKey` is only the path_key received with the onion (update_add_htlc TLV 0 / onion_message), never the payload's current_path_key. `OnionPacketKind.OnionMessage` allows payloads of 0-1 bytes. `PeeledOnion.PathKeySharedSecret` is ECDH(path_key, node_key) for M5. `ConstructWithSharedSecrets` returns the per-hop secrets without a second ECDH pass. Semantic hop-payload validation is not done here.
- HTLC-success/timeout transactions are built, signed and vector-tested (NL-056, NL-057): `test/NLightning.Integration.Tests/BOLT3/Bolt3HtlcSignerVectorTests` checks our `local_htlc_signature`s (Appendix C/F) byte for byte, validates every `remote_htlc_signature` (Appendix F only as `SINGLE|ANYONECANPAY`), rejects tampered/high-S/reordered/missing sigs, and, signing as node B, reproduces the `remote_htlc_signature` list in output order. The offered/received HTLC scripts and commitment building with HTLCs are complete and vector-tested.
