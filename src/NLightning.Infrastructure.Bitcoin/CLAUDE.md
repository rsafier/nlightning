# NLightning.Infrastructure.Bitcoin

This project is the NBitcoin-backed implementation of the Domain's Bitcoin and crypto ports. It builds BOLT 3 funding and commitment transactions from Domain models and generates the output scripts. It also handles BOLT 3 key derivation, the local signer, HD key storage, the wallet, fee polling, and chain monitoring over bitcoind RPC plus ZMQ `rawblock` (and `rawtx` for the mempool, O8). It also holds the BOLT 4 Sphinx core (`Onion/`); the interactive-tx rules live in Domain (`Protocol/InteractiveTx/InteractiveTxRules`, wave IT), and the old `InteractiveTransactionService` is gone. `ITlvConverterFactory` is registered by `AddInfrastructureServices`/`AddSerializationInfrastructureServices`, not here. Target is net10.0 (via src/Directory.Build.props), csproj version 1.0.0.

## Layout
- `Builders/`: `CommitmentTransactionBuilder`, `FundingTransactionBuilder` and `FundingOutputBuilder`. They take a Domain `*Model`/`*OutputInfo` and return an UNSIGNED tx as Domain `SignedTransaction(txid, rawBytes)`. `FundingTransactionBuilder` returns `FundingTransactionBuildResult` (tx + funding output index; inputs and outputs are both BIP 69 ordered, so a rebuild from the same UTXOs gives the same txid) and never mutates the model; the caller sets `FundingOutputInfo.TransactionId/Index`. Change/dust/fee decisions are made in Domain `FundingTransactionModelFactory` (typed `InsufficientFundsException`, dust change folded into the fee). `CommitmentTransactionBuilder.BuildWithOutputMap` returns `CommitmentTransactionBuildResult` (unsigned tx + `HtlcOutputsInTxOrder`: each untrimmed `HtlcOutputInfo` with its `Vout`, in transaction order, which is the order of HTLC transactions and `htlc_signatures`); `Build` is a wrapper returning only the tx. Outputs are sorted with a stable `OrderBy` over `TransactionOutputComparer`, so identical outputs keep the model order. `HtlcTransactionBuilder` (`IHtlcTransactionBuilder`, singleton in `AddBitcoinInfrastructure`) builds HTLC-timeout/HTLC-success txs from a Domain `HtlcTransactionModel` (made by the static Domain `HtlcTransactionModelFactory` from the commitment model + its output map): `Build` returns `HtlcTransactionBuildResult` (unsigned tx, spent witness script, spent amount: the BIP 143 sighash inputs) and `AddWitness` assembles `0 <remotesig> <localsig> <preimage|empty> <witnessScript>` (remote sighash `SINGLE|ANYONECANPAY` with anchors, else `ALL`; local always `ALL`). With anchors (O7-T3, B5-HTX-02) `AddFeeInputs(model, built, AnchorFeeInput[], changeScript, feeratePerKw)` combines the zero-fee transaction as built with wallet inputs: the HTLC input and output stay at index 0, fee inputs follow (sequence 0xFFFFFFFD), change is output 1 (into the fee when below the change script's dust); it returns a Domain `AnchorHtlcTransaction` (combined `HtlcTransactionBuildResult` to sign input 0 over with `SIGHASH_ALL`, fee, change, signed weight with 73-byte signatures) and refuses a non-anchor or already combined transaction, no/duplicate/weightless inputs or too little value; `EstimateAnchorBaseWeight(model, built, changeScriptLength)` is the weight before fee inputs. Tests: `Builders/AnchorHtlcTransactionBuilderTests` (every Appendix F HTLC tx byte-exact alone and script-valid combined with the spec's remote signature), `Builders/AnchorPenaltyTransactionBuilderTests` (Appendix F revoked penalties with the CSV-1 `to_remote`, second-level penalties at any vout). `ClosingTransactionBuilder` (`IClosingTransactionBuilder`, singleton in `AddBitcoinInfrastructure`, BOLT2 plan N10-T2) builds the BOLT 3 legacy closing tx from a Domain `ClosingTransactionModel` (version 2, locktime 0, the funding outpoint with sequence 0xFFFFFFFF, outputs ordered by amount then scriptpubkey as memcmp with the shorter first) and `AddWitness(unsigned, funding, localSig, remoteSig)` assembles `0 <sig for the lesser funding key> <sig for the greater> <2-of-2 script>`, both `SIGHASH_ALL`; sign it with `ILightningSigner.SignChannelTransaction` and check the peer's with `ValidateSignature`. BOLT 3 has no closing-tx vector: `Builders/ClosingTransactionBuilderTests` checks each field and verifies the signed tx with NBitcoin's interpreter. `SweepTransactionBuilder` (`ISweepTransactionBuilder`, BOLT 5 plan O3-T1) builds sweeps and claims from Domain `SweepInput`s: version 2, one output to the destination script, `nSequence` = the input's CSV or 0xFFFFFFFD, `nLockTime` = the `cltv_expiry` of the timeout claims; timeout claims are never batched with any other spend kind and all share one `cltv_expiry` (the caller groups them by expiry), and a preimage claim (whose `CltvExpiry` is its deadline) is refused when `nLockTime >= cltv_expiry`; `Build(inputs, destination, feeratePerKw, lockTime)` charges `SweepWeights.FeeSat` of the estimated weight (73-byte signatures), `BuildWithFee` an absolute fee (RBF); it validates each input for its spend kind (CSV, point, pubkey, cltv, 32-byte preimage, secret, a revocation pubkey whose HASH160 is in the script) and refuses an output below the destination's dust limit. `AddWitnesses(unsigned, sigs)` / `Sign(unsigned, signer, channelId)` assemble the BOLT 3 witnesses (internal static `CreateWitness`). `PenaltyTransactionBuilder` (`IPenaltyTransactionBuilder`, O5-T1) wraps it: `BuildBatched` (penalty inputs plus optionally our `to_remote`), `BuildSingle`, `BuildSplit` (one tx per input, B5-REV-08); nLockTime 0, every input replaceable. Both are singletons through `Onchain/OnchainServiceCollectionExtensions.AddOnchainBitcoinServices()` (the sweep builder needs `IOptions<NodeOptions>`). `AnchorChildTransactionBuilder` (`IAnchorChildTransactionBuilder`, BOLT 5 plan O7-T2; registered by the Application's `AddAnchorCpfpServices`) builds the transactions that spend BOLT 3 anchors: `GetAnchorWitnessScript`/`GetAnchorScriptPubKey`/`FindAnchorOutput` (the 330-sat P2WSH keyed to a funding pubkey), `BuildChild(anchor, walletInputs, changeScript, fee)` (the CPFP child: version 2, lock time 0, input 0 the anchor then the wallet inputs, all 0xFFFFFFFD, one change output; refuses no wallet input, a repeated outpoint, change below the script's dust limit), `EstimateChildWeight` (73-byte anchor signature, each `AnchorWalletInput.InputWeight`), `AddAnchorWitness` (`<sig> <anchor script>`, `SIGHASH_ALL`, other witnesses kept) and `BuildAnchorSweep` (anyone-can-spend after 16 blocks: `<> <anchor script>`, `nSequence` 16). Tests: `Builders/AnchorChildTransactionBuilderTests` (script-executed with the Appendix C funding keys). The interfaces are in `Builders/Interfaces/`, except `IFundingOutputBuilder`, which sits in `Builders/`.

`VerifyAndStore(secret, remoteCommitmentNumber, point, shachain)` inserts into the peer's shachain at `PerCommitmentIndex.From(n)` only after the point matched; the revoke_and_ack receive check), `FeeService` (register it with `Services/FeeServiceCollectionExtensions.AddFeeServices(primaryHandler?)`: one singleton for `FeeService` and `IFeeService` with its own long-lived `HttpClient` (30 s timeout), replacing any earlier `IFeeService`; - `Signers/LocalLightningSigner.cs`: implements `ILightningSigner`. Channel key m/6425'/0'/0'/0/i has hardened children 0'-5' (funding, revocation, payment, delayed, htlc, per-commitment seed). `GetPerCommitmentPoint`/`RevealPerCommitmentSecret` take a **commitment number** and derive the secret at index `PerCommitmentIndex.From(n) = 2^48-1-n` (NL-187). **Revocation guard (NL-189):** `RevealPerCommitmentSecret(channelId, n)` throws `SignerException` unless `n < LocalCommitmentNumber`; that number comes from `ChannelSigningInfo.LocalCommitmentNumber` at `RegisterChannel` (re-registering never lowers it) and moves only through `AdvanceLocalCommitment(channelId, n)` (monotonic; call it only after the new local commitment is persisted). There is no index-keyed or unguarded secret API any more; `CommitmentKeys` carries no secret (local keys are derived from the point). **HTLC signatures (NL-057):** `SignRemoteHtlcTransactions` (our sigs for the peer's commitment, key `htlc_basepoint_secret + SHA256(point || htlc_basepoint)` from the protected virtual `GetHtlcBasepointSecret`, `SINGLE|ANYONECANPAY` with anchors else `ALL`), `ValidateLocalHtlcSignatures` (count, compact parse, low-S, verify against `ChannelSigningInfo.RemoteHtlcBasepoint` tweaked by our point) and `SignLocalHtlcTransaction` (our own HTLC tx, always `ALL`). Each takes a Domain `HtlcSigningContext(HtlcTransactionBuildResult, PerCommitmentPoint, HasAnchors)`; signatures are RFC 6979 without low-R grinding, `MakeCanonical()`. **Broadcast signing and data loss (N9-T4):** `SignLocalCommitmentForBroadcast(channelId, number, unsignedCommitment, remoteSignature)` validates the peer's signature, signs with our funding key and returns the transaction with the BOLT 3 witness `0 <sig1> <sig2> <funding script>` in the script's key order (byte-exact against Appendix C commit tx 0, `test/NLightning.Infrastructure.Bitcoin.Tests/Signers/LocalLightningSignerBroadcastTests`); it refuses `number <` the current local commitment number (revoked, I4). `MarkDataLoss(channelId)` (also set by `RegisterChannel` when `ChannelSigningInfo.DataLossDetected`; sticky) makes it refuse `SignChannelTransaction`, `SignRemoteHtlcTransactions`, `SignLocalHtlcTransaction` and the broadcast signing with `SignerException` (I12). **Invariant S1 (BOLT 5 plan §3.5, O2-T1):** `SignLocalCommitmentForBroadcast` calls `MarkBroadcastSigned(channelId, n)` before it returns; `RegisterChannel` applies `ChannelSigningInfo.BroadcastSignedCommitmentNumber` with `MarkBroadcastSigned`, so the host restores the mark by filling that field from the persisted commitment broadcast row (O2-T2 wiring; not done yet, the mark is memory only until then). The I4/S1 checks, the broadcast signature and its mark hold a per-channel `System.Threading.Lock` shared with `AdvanceLocalCommitment`, `RevealPerCommitmentSecret`, `MarkBroadcastSigned` and `RegisterChannel`, so S1 holds without the caller's channel lock. Once marked (sticky, the lowest number wins, `TryGetBroadcastSignedCommitment` reads it) the signer refuses `RevealPerCommitmentSecret(m >= n)`, `AdvanceLocalCommitment(> n)`, `SignLocalCommitmentForBroadcast` of any other number (the same number may be signed again for a rebroadcast), `SignChannelTransaction` and `SignRemoteHtlcTransactions`; `SignLocalHtlcTransaction` (our HTLC-timeout/success for the on-chain resolution) stays allowed. The broadcast path signs the funding input through the private unguarded `SignFundingInput`. **Sweeps (BOLT 5 plan O3-T1):** `SignSweepInput(channelId, SweepSigningContext)` signs one input (`SIGHASH_ALL`, BIP 143, RFC 6979, low-S, 64-byte compact) with the key the context's `SweepKeyKind` names: `DelayedPayment` (delayed basepoint secret tweaked by our point), `Payment` (payment basepoint secret, static_remotekey; a null witness script means P2WPKH, script code P2PKH), `HtlcRemotePoint` (HTLC basepoint secret tweaked by the peer's point) or `Revocation` (`DeriveRevocationPrivKey(revocation basepoint secret, peer secret)`, and a given point must equal `secret * G`). The derived pubkey or its HASH160 must be pushed by the witness script, else `SignerException` (a wrong kind, point or secret never signs). Not blocked by data loss or S1. The basepoint secrets come from the protected virtual `GetRevocationBasepointSecret`/`GetPaymentBasepointSecret`/`GetDelayedPaymentBasepointSecret`/`GetHtlcBasepointSecret` (tests override them with the Appendix C secrets: `test/.../Signers/AppendixCSweepSigner`); derived keys are wiped after use. **Channel announcements (BOLT 7 plan G1-T2):** `SignChannelAnnouncement(channelId, unsignedAnnouncement, scid)` takes the payload bytes after the four signatures (`len`, `features`, `chain_hash`, `short_channel_id`, the two node ids, the two bitcoin keys, unknown trailing bytes) and returns `ChannelAnnouncementSignatures(node, bitcoin)` over their double-SHA256 (node key through `SignNodeMessage`, funding key through the same NBitcoin.Secp256k1 RFC 6979 low-S path, wiped after use). It parses the bytes and refuses (`SignerException`) another chain, a SCID other than the argument, the channel's funding output index or the channel's real SCID (re-read from the source when there is one, else the registered `ChannelSigningInfo.ShortChannelId`; unknown SCID refused), node ids not strictly ascending, neither being ours, the other not the registered `RemoteNodeId`, our slot's bitcoin key not our funding key, the other not the peer's, and anything after data loss. Tests: `Signers/LocalLightningSignerChannelAnnouncementTests.cs` (the assembled 256 verifies all four signatures, both node orders). **BOLT 7 node signatures (W0-E):** `SignNodeMessage(Hash)` signs the given 32-byte hash as is with the node key (from `ISecureKeyManager.GetNodeKeyPair()`, whose private-key copy is zeroed after parsing) through NBitcoin.Secp256k1 (`ECPrivKey.TrySignECDSA`: RFC 6979, low-S, 64-byte compact); `VerifyNodeMessage(hash, signature, nodeId)` returns false for an unparsable signature/pubkey and accepts high-S (normalized first; BOLT 7 relays may malleate s). The caller hashes: for channel_update `ChannelUpdatePayload.GetSignatureHash()` = SHA256d of the bytes after the signature. Tests: `Signers/LocalLightningSignerNodeMessageTests.cs` (an LND-captured channel_update verifies with LND's node id). The verification itself is `Gossip/GossipSignatureVerifier.VerifyCompact` (G0-T3), which `VerifyNodeMessage` delegates to.

- `Wallet/FeeInputSelector` (`IFeeInputSelector`, Domain `Bitcoin/Wallet/Interfaces/`, singleton in `AddBitcoinInfrastructure`; BOLT 5 plan O7-T1): picks mined wallet outputs with a known address (P2WPKH, P2TR), largest first, until they pay `targetFee + feeRatePerKw x (extraWeight + inputs (272 / 231 WU) [+ P2WPKH change 124 WU])`; change only when at least 294 sat is left after it, otherwise the excess is fee (`FeeInputReservation.Fee` = the wallet inputs' share, `ChangeAmount`, `ChangeScript` from `IBitcoinWalletService.GetUnusedAddressAsync(P2Wpkh, isChange: true)`; see `Domain/Bitcoin/Wallet/Constants/WalletWeights`). One call at a time (a `SemaphoreSlim`); outputs spent by a pending `BroadcastTransactions` row are never candidates (our unconfirmed funding after a restart, whose channel lock was memory only, or an earlier sweep/child); the outputs are reserved in memory atomically against channel fundings (`IUtxoMemoryRepository.TryReserveForFee`, re-selected up to 3 times when a funding took one meanwhile), then persisted (`IUnitOfWork.FeeInputReservationDbRepository`, own scope and save); a failed save releases them. `ReleaseAsync` deletes the rows first, then frees memory; `ConfirmAsync` returns false (nothing changed) while any input is still in the wallet, else deletes the rows only: wallet outputs are removed only by the chain monitor's block save (no second delete of the same `Utxos` rows racing it). `InsufficientFundsException` when the unreserved outputs cannot pay. The chain monitor restores the reserved outpoints with the UTXO set at start (`LoadUtxoSetAsync` -> `IUtxoMemoryRepository.LoadFeeReservations`) and deletes, in the startup save, every reservation none of whose inputs is still in the wallet (spent in a processed block but never confirmed or released). A reorg that unconfirms a confirmed child does not bring its reservation back (the caller reserves again), and concurrent reservations can get the same change address (NL-280).
- `Wallet/AnchorReserveService` (`IAnchorReserveService`, Domain `Bitcoin/Wallet/Interfaces/`, singleton in `AddBitcoinInfrastructure`; NL-379, NL-385): the on-chain reserve of `option_anchors` channels, LND style: `Node:Anchors:ReservePerChannel` (default 10,000 sat) per anchors channel not Closed/Stale in `IChannelMemoryRepository` plus the anchors opens a check admitted and not yet funded (counted while their temporary channel is stored, up to `Node:Anchors:PendingOpenTimeout` (10 min), or for `StoreGrace` (30 s) before it is stored; `ReleasePendingChannel` ends one; the checks run under one `SemaphoreSlim`, so two concurrent opens or accepts can not both pass against the reserve of one), capped at `Node:Anchors:MaxReserve` (100,000 sat; `AnchorReserveOptions`). The guarded balance is the outputs `UtxoModel.BacksAnchorReserve(height)` (what `FeeInputSelector` can spend: mined, known P2WPKH/P2TR address; plus the three-block confirmed rule), not locked, not fee-reserved, not spent by a pending broadcast (= `IUtxoMemoryRepository.GetAvailableConfirmedBalance`). `EnsureCanAcceptAnchorsChannelAsync(channel)` (fundee: available >= reserve with the new channel), `EnsureCanFundAsync(amount, channel)` (opener: available >= amount + the funding's worst-case fee (Domain `FundingFeeEstimator`, P2WPKH inputs and a P2TR change at the channel feerate) + reserve) and `LockFundingUtxosAsync(amount, channel)` (the funding lock through the repository overload that selects for amount + fee, keeps the reserve (backing outputs left + the funding's least change) and skips pending-broadcast outpoints, atomically under the repository's lock) throw `AnchorReserveException` (an `InsufficientFundsException`). `IFeeInputSelector` is not limited by it: the CPFP child and anchors HTLC fee inputs may spend the reserve. `GetStatusAsync` takes the same gate as the admission checks, so a spend that reserved its inputs and then checks the reserve (withdraw) never reads the status between an accept's check and its admission. `Wallet/PendingBroadcastOutpoints` is the shared helper that reads the outpoints our pending `BroadcastTransactions` rows spend (used by both). Tests: `Integration.Tests/Persistence/AnchorReservePersistenceTests` (SQLite).
- `Wallet/WalletSpendService` (`IWalletSpendService`, the on-chain `withdraw`; registered by `Wallet/WalletSpendServiceCollectionExtensions.AddWalletSpendServices()`, a TryAdd singleton, called from the Daemon's `AddWithdrawIpcServices`): refuses while chain processing is halted; parses the address on the node's network (`ParseAddress`: an address of mainnet/testnet/regtest/signet is `WrongNetwork`, anything else `InvalidAddress`); fee rate = the request's (253-250,000 sat/kw) or `IFeeService`'s (floored at 253), and not below bitcoind's `mempoolminfee` when `IBitcoinChainService` reports one (a requested rate below it is refused, an estimate raised to it); amount at least the destination's Bitcoin Core dust threshold (`GetDustThreshold`: P2WPKH 294, P2TR/P2WSH 330, P2SH 540, P2PKH 546). The inputs come from `IFeeInputSelector.ReserveAsync(amount as the target, rate, BaseWeight 42 + destination output weight, purpose `withdraw`)`, so its rules hold (mined P2WPKH/P2TR only, never channel-locked, fee-reserved or pending-broadcast outputs, largest first, P2WPKH change to a fresh change address when not dust, reservation persisted). "All" computes the amount from the same candidates: total - fee of spending them all - the anchors reserve (kept as change; at least 294 sat). After reserving, the reserve check (NL-379): `IAnchorReserveService.GetStatusAsync().AvailableBalance` (the reserved inputs no longer count) + this spend's change must cover `RequiredReserve`, else the reservation is released and `AnchorReserveException` thrown (the change counts, as for a funding, although it backs the reserve only three blocks after it confirms). The transaction (version 2, locktime 0, every input 0xFFFFFFFD, destination output then change) is signed with `SignWalletTransaction(tx, reservationId, [])`, every input re-verified with NBitcoin's interpreter, then stored and sent with `IChainBroadcaster.SaveAndPublishAsync` as a `BroadcastPurpose.WalletSend` row (a refused send stays pending and is resent after every block; `Published` false). A failure before the row exists releases the reservation; after, it is kept (the pending row keeps the outputs out anyway). Withdrawals run one at a time (a `SemaphoreSlim`), and each first ends the stale `withdraw` reservations, as does `ReleaseOrphanedReservationsAsync` (the host's startup call, after the chain monitor loaded the UTXO set): those none of whose inputs is still in the wallet are confirmed (`ConfirmAsync`), those none of whose inputs a pending `BroadcastTransactions` row spends are released (a crash or a failed, unverifiable save between the reservation and the row; nothing else would free them); when the pending rows cannot be read nothing is released. A `WalletSend` row is never bumped or abandoned (a refused one is resent forever, as NL-294's funding). Tests: `Wallet/WalletSpendServiceTests` (real selector and signer), Docker `WithdrawFlowTests`.

## Adding a new output or transaction type
1. Output script: subclass `BaseOutput` (or `BaseHtlcOutput`) in `Outputs/`, and pass the redeem script (from a static `Generate*Script(...)`) and the `ScriptType` to `base(amount, script, scriptType)`; `ScriptType` is a get-only base property, never a virtual override (the base ctor derives `ScriptPubKey` from it). Throw `InvalidScriptException` when `script.IsUnspendable || !script.IsValid`.
2. If the output goes on commitment txs, add the Domain `*OutputInfo` -> output conversion in `CommitmentTransactionBuilder.Build` and check how `TransactionOutputComparer` tie-breaks it.
3. For a new transaction type (e.g. HTLC-success/timeout): add a data-only Domain model/factory in `src/NLightning.Domain/Bitcoin/Transactions/`, then add an `IXBuilder` in `Builders/Interfaces/` and `XBuilder` in `Builders/`. Signing goes through `ILightningSigner` (add a method there and implement it in `LocalLightningSigner`).
4. Register singletons in `DependencyInjection.AddBitcoinInfrastructure` (only `IBitcoinWalletService` is scoped). `ILightningSigner` (`LocalLightningSigner`) is registered there too and takes the host's `ISecureKeyManager` from DI. `SecureKeyManager` and `FeeService` (`AddFeeServices`) are registered by the host (`NodeServiceExtensions.AddNltgNodeServices`, which the Docker tests also use). Services in `AddBitcoinInfrastructure` may depend on them (e.g. `CommitmentKeyDerivationService` takes `ILightningSigner`).
5. Add tests in `test/NLightning.Infrastructure.Bitcoin.Tests/<Folder>/`, plus BOLT 3 vectors in `test/NLightning.Integration.Tests/BOLT3/` if applicable.

## Conventions
- Use a file-scoped namespace. External usings (NBitcoin, Microsoft.*) go above it; NLightning usings go below it as relative names (`using Domain.Money;`).
- Domain value objects cross the boundary as bytes and are converted here (`new PubKey(compactPubKey)`, `new uint256(txId)`). Domain stays NBitcoin-free.
- Resolve the network with `nodeOptions.BitcoinNetwork.ToNBitcoinNetwork()` (`Networks/NBitcoinNetworkResolver`, W4-D): mainnet/testnet/regtest map to NBitcoin's, signet and every custom signet (Mutinynet) to `Bitcoin.Instance.Signet`, anything else throws. The `Wallet/` services (`BitcoinChainService`, `BitcoinWalletService`, `BlockchainMonitorService`) use it; the builders, `LocalLightningSigner` and `SecureKeyManager` still call `Network.GetNetwork(name)` (knows `signet`, throws otherwise). See `docs/agents/MUTINYNET.md`.
- Singletons that need the DB create a scope per operation: `CreateScope()` then `GetRequiredService<IUnitOfWork>()` (see `Wallet/BlockchainMonitorService.cs`).
- Guard logging with `_logger.IsEnabled(...)`. Name tests `Given_X_When_Y_Then_Z` (xUnit v3 + Moq).
- `dotnet format --verify-no-changes --exclude "**/BlazorTests/**"` is a CI gate: `_field`/`s_field` naming, no unused usings.

## Gotchas (verified bugs)
- `WatchedTransactionModel.TransactionIndex` is the position in the block (coinbase = 0), a `uint` capped at 24 bits (NL-102). Rows written before migration `WidenWatchedTransactionIndex` may hold the old watched-only index, and channels confirmed then carry a wrong persisted `ShortChannelId`; nothing repairs them.
- `BlockchainMonitorService.ProcessNewBlockAsync` (the ZMQ entry point, internal; tests call it directly) serializes its callers with `_newBlockSemaphore` and drops a block above bitcoind's tip (a ZMQ endpoint of another chain, NL-310). That guard is not full protection against a misconfigured endpoint: a foreign block at or below our tip is dropped as stale by the existing `DoesNotExtendProcessedChain`/`IsProcessedTipActiveAsync` path (no rewind, our tip is still active). The check costs one `getblockcount` RPC per ZMQ block; if it fails, the notification is dropped and logged, and the next block's catch-up recovers it. Tests that start a real monitor must not subscribe to a real ZMQ port: the Mutinynet container publishes `rawblock` on 127.0.0.1:28332 (the daemon's signet default), so use `Tests.Utils/Mocks/SilentZmqEndpoint` (loopback ports held by listeners that never speak ZMQ), as `ChainMonitorHarness` and `BlockchainMonitorServiceTests` do.
- `BlockchainMonitorService` tip poll: ZMQ delivers only what bitcoind publishes after the subscription reached it, and the start subscribes after its RPC catch-up (NetMQ connects in the background), so a block mined in between, or while ZMQ reconnects, was never processed until the next block. Every `Bitcoin:TipPollInterval` (default 30 s, 0 = off) the monitoring loop calls `PollTipAsync` (internal, tests call it directly): a poll that finds bitcoind's tip above our last processed block only notes it; the next one that finds it still there at the same processed height catches up over RPC under `_newBlockSemaphore` (tip read again inside), logs a Warning and counts `TipPollCatchUps`. Nothing is polled while processing is halted. `NLightningTestNode` sets 1 s on both test backends (found by the cluster harness, phase 2: a pod's ZMQ subscription is slower to set up than Docker's 127.0.0.1 port). Poll mode (`Bitcoin:Notifications=Poll`, NL-1094) opens no ZMQ socket and never calls `PollTipAsync`: the loop calls `PollChainAsync` every `GetPollInterval(network)`, which hands bitcoind's tip block to `ProcessNewBlockAsync` (the ZMQ path) unless it is the hash we processed at that height (while halted, only when the tip changed), then, when `IsMempoolWatched`, `PollMempoolAsync` (`IBitcoinChainService.GetMempoolSpendersAsync` = `gettxspendingprevout` over the watched outpoints and the outputs of spenders it reported, each new spender fed to `ProcessMempoolTransaction`). An `invalidateblock` with nothing mined after it waits for the next block, as with ZMQ.
- `BlockchainMonitorService` block failures (NL-097): a block whose `ProcessBlock` throws is retried `MaxBlockProcessingAttempts` (3) times with doubling backoff from `BlockRetryBaseDelay` (1s); then the round halts with a Critical log and `IsChainProcessingHalted` is set, leaving it and later blocks queued (never skipped). The next ZMQ block or a restart retries from it. The queue holds at most `MaxQueuedBlocks` (144); later blocks are refetched from bitcoind once it drains. Replays (the last processed block is re-queued on start, and failed blocks are retried) skip deposits whose UTXO is already in `IUtxoMemoryRepository`, but still re-raise `OnNewBlockDetected`. Each attempt is its own unit of work, so a failed attempt persists nothing (NL-214). The halt only recovers if the failure is transient; nothing fails the node if it persists (NL-216: the flag and its reason are on `IBlockchainMonitor`, shown by `chainstatus`, and new channel risk is refused while it is set).
- `SecureKeyManager` key files (`Infrastructure/Node/Models/KeyFileData`): v2 = random 16-byte salt, random 24-byte nonce, Argon2id 64 MiB/3 passes, all stored in the file; v1 files (fixed `s_legacySalt`, zero nonce, 64 KiB) are still read and are rewritten as v2 by `FromFilePath`, after copying the original to `<file>.v1.bak`. **Derivation (NL-159):** v1/v2 are `KeyDerivationScheme.LegacyGenesisChainCode` (the node key is the master private key, chain code = genesis hash); new nodes (`CreateNew`, used by `Program.cs`, and `FromMnemonic`) are `Bip32`, written as **v3** (v2 encryption + a standard BIP32 master + `nodeKeyPath` = `NodeKeyPathString` `m/1017'/0'/6'/0/0`, checked on load). The file version decides the node id, so never move a file between schemes (a v1 upgrade writes v2, never v3); the legacy constructor `new SecureKeyManager(privateKey, ...)` stays for tests and existing nodes. The master material and the node key sit in two locked buffers; the constructor zeroes its input arrays (as arrays: they are not pinned). Writes are atomic (temp file `0600` + move) and keep symlinks and the target's **owner** bits but never group/other bits (an old 0644 file becomes 0600 with a stderr warning; the `.v1.bak` too; SECURITY_REVIEW SR-02). Passwords are hashed as full UTF-8; for v1 files only, a password that opens with the old libsodium truncated encoding (first `password.Length` UTF-8 bytes) or, on Windows, the LPStr ANSI code page encoding (`GetSystemAnsiPasswordBytes`, NL-212; the internal `FromFilePath(..., legacyAnsiPasswordEncoder)` overload is the test seam) also opens and the file is rewritten. `GetNextChannelKey` writes the new index to the key file (atomic, flushed, never lowered, skipped while no key file exists) under the index lock **before** it returns the key, and throws when the write fails (the old fire-and-forget write could be lost or reordered, and a restart would reuse a channel key index; SR-04). `ComputeNodeSharedSecret` (node-key ECDH) copies the node key out of locked memory only for the operation and wipes the copy. `ISecureKeyManager` implementations: `SecureKeyManager`, the Docker `FakeSecureKeyManager`, and the test-only `EcdhOnlyKeyManager` (Moq cannot set up its span-parameter method). The output descriptors (`Output*Descriptor`) are computed from the key on every load (the file's `descriptor` is written but never read back): each names the xpub at its own origin (`wpkh([fp/84'/0'/0']<account xpub>/0/*)`, the channel one `wpkh([fp/6425'/0'/0'/0]<xpub>/*)`; SR-13, checked against the BIP84 vector). `FromFilePath` prints a stderr notice on every load while a `<file>.v1.bak` exists (`GetWeakBackupWarning`, SR-18): it is the same key under the weak v1 encryption. Threat model and residual risks: `docs/agents/SECURITY_REVIEW.md`.
- `LocalLightningSigner.SignChannelTransaction` hardcodes input 0 + SIGHASH_ALL (commitment and closing txs only); HTLC transactions go through the HTLC methods above. `SignLocalHtlcTransaction` accepts a combined anchors HTLC transaction (`HtlcSigningContext.HasAnchors`, input 0 the HTLC output, more inputs for the wallet's fee; wave O7 integration, O7-T3) and signs input 0 with `SIGHASH_ALL`; without anchors, and for `SignRemoteHtlcTransactions`/`ValidateLocalHtlcSignatures`, an HTLC transaction must have exactly one input. A simple taproot HTLC transaction takes fee inputs too (NL-904 item 4, taproot wave t03 lane T4L): `HtlcTransactionBuilder.AddFeeInputs` keeps the leaf and control block and sets `HtlcTransactionBuildResult.FeeInputSpentOutputs`, and our BIP 340 `SIGHASH_DEFAULT` signature (only ours: `TaprootSignatures.ComputeHtlcSigHash(..., allowFeeInputs)`) commits to every spent output, outpoints checked; the peer's 0x83 signature still covers input and output 0. Taproot anchors (NL-966): `SignTaprootAnchorInput(channelId, tx, inputIndex, ourPerCommitmentPoint, spentOutputs)` (`LocalLightningSigner.TaprootAnchors.cs`) signs our P2TR anchor by key path (our delayed key at the point, or the payment basepoint for our anchor on the peer's commitment, tweaked with the `OP_16 OP_CSV` root), refusing any spent output that is not exactly that 330-sat anchor; `AnchorChildTransactionBuilder` finds (`FindTaprootAnchorOutput`), witnesses (`AddTaprootAnchorWitness`) and sweeps (`BuildAnchorSweep` with `AnchorOutpoint.IsTaproot`: leaf + control block) taproot anchors.
- `LocalLightningSigner.SignAnchorInput(channelId, tx, inputIndex, amount)` (BOLT 5 plan O7-T2, region "Anchors" at the end of the class): our funding key, `SIGHASH_ALL`, BIP 143 over the anchor script the signer builds from the channel's `LocalFundingPubKey` (so the signature can only spend our own anchor, never the funding output), 330 sat only; not blocked by data loss or S1.
- `LocalLightningSigner.SignWalletTransaction(tx[, reservationId], otherSpentOutputs)` (BOLT 5 plan O7-T1, NL-067 second half; with a reservation id every wallet input must carry that reservation, else `SignerException` before anything is signed; the id-less overloads accept any reservation; the key derived from `AddressIndex`/`IsAddressChange` must give the scriptPubKey of the UTXO's recorded `WalletAddress`, so a UTXO without one, or with a mismatching index, is refused) signs, in place and with `SIGHASH_ALL`, every input of `tx` that spends a wallet UTXO (`IUtxoMemoryRepository.TryGetUtxo`): P2WPKH and P2TR key path (BIP 86 tweak, explicit `SIGHASH_ALL`, 65-byte signature), keys from `ISecureKeyManager.GetDeposit*KeyAtIndex(AddressIndex, IsAddressChange)`, the returned extended-key bytes zeroed and the `Key`s disposed after use. Every wallet input is checked first: one that is not fee-reserved (`TryGetFeeReservation`) or is locked to a channel funding (`SignFundingTransaction` signs those) throws `SignerException` and nothing is signed; a P2TR wallet input needs every other spent output (`Domain.Bitcoin.Wallet.Models.SpentOutput`, BIP 341), else it throws. Non-wallet inputs are left untouched. Each signature is checked with NBitcoin's interpreter (`TransactionValidator` when every spent output is known, else `IndexedTxIn.VerifyScript`) before the bytes are written. Returns false when no input is the wallet's. Channel signing info is no longer memory-only (NL-067): built with an `IChannelSigningInfoSource` (the DI registration passes `sp.GetService<IChannelSigningInfoSource>()`, which `AddRepositoriesInfrastructureServices` registers), the signer loads and registers a channel it does not know from the database on first use (`TryGetSigningInfo`: every channel-id API, including `TryGetBroadcastSignedCommitment`), with the persisted local commitment number (revocation guard), data-loss flag and broadcast mark (S1). Without a source (unit tests, harnesses) registration stays manual. `RegisterChannel` again refreshes the SCID, the peer's node id and htlc basepoint of an already registered channel, but never its key index, funding keys or outpoint (a mismatch throws `SignerException` before any guard or mark is touched; the first registration is kept). `SignChannelAnnouncement` refuses a private channel (`ChannelSigningInfo.AnnounceChannel` false, BOLT 7). A lookup of an unknown channel is a synchronous database read on every call (no negative cache); `SignLocalCommitmentForBroadcast` does it before taking the commitment lock. Closed and Stale channels are not loaded.
- `BitcoinChainService`'s constructor makes a blocking RPC call, so DI resolution fails if bitcoind is down.

## Onion-routing (BOLT 4) hooks
- `Ecdh.SecP256K1Dh` already computes the Sphinx per-hop shared secret, SHA256(compressed(k*P)).
- EC math for ephemeral-key blinding lives behind the Domain port `ISecp256K1Math` (`MultiplyPubKey`, `MultiplyPrivKey`, `AddPubKeys`, `AddPrivKeys`), implemented by `Crypto/Functions/Secp256K1Math.cs` (on `NLightningCryptoContext`, registered as a singleton in `AddBitcoinInfrastructure`). `KeyDerivationService` consumes it; do not reintroduce private EC helpers. Sphinx code that needs EC math should depend on `ISecp256K1Math`, except the per-hop key chain in `OnionBuilder.ComputeHopKeys`, which works on `ECPrivKey` directly (CreatePubKey/ECDH/TweakMul on one parsed key, ~35% faster and ~70% fewer managed allocations per hop than the `IEcdh` + `ISecp256K1Math` round trips).
- Peeling needs node-key ECDH: `ISphinxService.PeelAsLocalNode` does it through `ISecureKeyManager.ComputeNodeSharedSecret` (the node key never leaves the key manager; route blinding tweaks the ephemeral key, ECDH(k*t, E) = ECDH(k, t*E), instead of the node key); `Peel(..., PrivKey nodeKey, ...)` takes the key explicitly. `OnionPeeler` takes either through its `NodeEcdh` delegate. The two are named differently on purpose, because a `byte[]` converts implicitly to both `PrivKey` and `CompactPubKey` (the path key).
- Every packet-caused `Peel` failure is an `OnionException` (only caller bugs, such as a bad node key or a `default` packet, throw anything else): BADONION codes (`InvalidOnionVersion`/`Key`/`Hmac`/`Blinding`) carry sha256_of_onion as `FailureData`; framing errors (after the HMAC verified) are `InvalidOnionPayload` with data `00 0000` (type 0, offset 0) and a copy of the shared secret in `OnionException.SharedSecret` (needed to encrypt the non-BADONION failure). For `OnionPacketKind.Payment` with a path_key every failure is remapped to `InvalidOnionBlinding` (original as inner exception). `pathKey` is only the path_key received with the onion (update_add_htlc TLV 0 / onion_message), never the payload's current_path_key. `OnionPacketKind.OnionMessage` allows payloads of 0-1 bytes. `PeeledOnion.PathKeySharedSecret` is ECDH(path_key, node_key) for M5. `ConstructWithSharedSecrets` returns the per-hop secrets without a second ECDH pass. Semantic hop-payload validation is not done here.
- Error onions (M3): `Onion/FailureOnionService` (internal, Domain `IFailureOnionService`, singleton in `AddBitcoinInfrastructure`). It needs `IFailureMessageSerializer`, which only `AddSerializationInfrastructureServices` registers (this project cannot reference Serialization), so resolve it where both layers are added (the Daemon and the Docker DI do). `CreateErrorPacket(ss, message, minFailurePadLength = 256)` = ammag XOR (HMAC(um, body) || body); the internal static `CreateErrorPacket(ss, framedBody)` takes pre-framed bytes. `CreateErrorPacketFromMalformed(incomingSs, code, sha256OfOnion)` converts an `update_fail_malformed_htlc` (via `FailureMessage.FromMalformed`, then `CreateErrorPacket`; this node is the erring node). `WrapErrorPacket` truncates to 32768 then XORs the ammag stream (self-inverse). `DecryptErrorPacket(hopSecrets, packet)` runs max(27, hops) iterations, using a constant all-zero dummy secret past the route end, constant-time HMAC compare, and never attributes a dummy iteration; returns `null` when no hop matches (or the packet is < 32 bytes), else `DecryptedFailure` (message null if the framing/failuremsg is unparsable). Vectors: `test/NLightning.Integration.Tests/BOLT4/FailureOnionVectorTests.cs` (onion-error-test.json and the inline spec trace, every hop, both directions).
- Replay-set pruning (NL-327): `Onion/OnionReplayBlockPruner` subscribes to `IBlockchainMonitor.OnNewBlockDetected` (`Start()`/`StopAsync()`, the host's job, after the monitor starts and before it stops) and calls `IOnionReplayStore.PruneAsync(height)` on its own task: one prune at a time, coalesced to the highest height seen, lower/repeated heights ignored, a failed prune logged and retried at once when a higher block arrived during it, else by the next block (the requested height is kept); `WhenIdleAsync()` for tests. **Not wired yet**: nothing registers it or calls `Start()`/`StopAsync()` in the daemon's hosted service or the Docker `NLightningTestNode`, so a running node still prunes only lazily in `TryAddAsync`. The SQLite proof awaits `WhenIdleAsync()` after every block, because `SqliteTestDatabase` shares one connection and a prune overlapping the next block's save transaction fails. Registered by `Onion/OnionReplayPruningServiceCollectionExtensions.AddOnionReplayBlockPruner()` (TryAdd singleton; needs `IBlockchainMonitor` and `IOnionReplayStore`). Tests: `test/NLightning.Infrastructure.Bitcoin.Tests/Onion/OnionReplayBlockPrunerTests`, SQLite proof in `Integration.Tests/Persistence/ChainMonitorPersistenceTests`.
- Attributable failures (M3b): `Onion/AttributionDataService` (internal, Domain `IAttributionDataService`, singleton through `Onion/AttributionServiceCollectionExtensions.AddOnionAttributionServices()`, needs `IFailureOnionService`). Layout: hold times (20 × u32 BE, this node's first) then 210 truncated HMACs; node `x`'s block starts at `x*20 - x(x-1)/2` and holds positions 19-x..0, `hmac_0_y` at index `19 - y`; `hmac_0_y` = first 4 bytes of HMAC(um, message || hold_times[0..y] || hmac_j_(y-j) for j = 1..y at `start(j) + 19 - y`). Update = shift right (prune the left-most HMAC of each block, drop the last hold time and node 19's block), put hold time and 20 HMACs in front, XOR the `ammagext` stream; a missing or wrong-length downstream block counts as all zero. The message is the return packet before the node's own `ammag` (for the erring node the created packet XORed once more, the stream being self-inverse), the downstream `fulfillment_payload` for an intermediate fulfill, nothing for the final node's fulfill.
