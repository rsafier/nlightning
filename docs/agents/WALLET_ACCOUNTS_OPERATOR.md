# WalletKit named and watch-only accounts

`XCreateAccount` creates an owned BIP84 P2WPKH or BIP86 P2TR account. Its name is unique across scopes; `default` and `imported` are reserved. The request must set `i_know_what_i_am_doing`. Nested and hybrid P2SH scopes are refused. Existing default-account paths stay unchanged, including coin type 0 on the node's test networks.

Back up the node's wallet database together with its seed backup. Record each named account's `ListAccounts` public key, master fingerprint, derivation path, address type, and external/internal key counts. A seed-only restore does not recreate named-account discovery metadata. Do not assume an arbitrary account index or an address gap beyond the saved discovery window will be recovered automatically.

`NextAddr` requires the named account's address type. `FundPsbt(account=...)` selects that account's spendable coins and uses its own change scope; leave `change_type` unset. A PSBT retains the actual account/branch/child BIP32 origin. Address storage indexes are internal database identifiers and are not BIP32 child indexes.

Owned accounts keep a 20-address discovery window on both branches. Confirmed receipts extend the window in the same database commit as the block cursor, including receipts spent again in that block. Address handouts and block discovery share one allocator lock through their saves. Unused gaps of 20 or more addresses require explicit address derivation before funding them.

`ImportAccount` accepts account-level hardened public keys for BIP84 or BIP86, with an explicit address type and an optional four-byte master fingerprint. Network-appropriate xpub/tpub and BIP84 zpub/vpub versions are supported. Other versions, scopes and private keys are refused. `dry_run` derives the first 20 external and internal addresses without modifying the database.

Imported accounts remain watch-only: their scripts and historical transactions are stored separately from spendable UTXOs and custody accounting. They cannot fund or sign wallet transactions. Historical recovery starts at genesis because the upstream RPC provides no birthday. The imported-history tracker extends the 20-address gap using all historical receipts, including already-spent outputs, and replays until discovery stabilizes. Recovery requires the historical blocks; pruned or changing chains fail the request rather than return incomplete history. The existing imported-script bound is 1000 scripts and the historical scan bound is one million blocks. Discovery reaching those limits fails explicitly.

`coin_select` PSBT funding preserves supplied inputs, output order and PSBT maps. Inputless templates are accepted, including Bitcoin Core’s `createpsbt` v0 output; funded responses use PSBT v0. Existing wallet inputs must already be leased; foreign inputs must provide accurate `witness_utxo`. Only newly selected wallet inputs are leased by this RPC. Designate an existing change output (a zero-value placeholder is accepted and must finish above dust), or request a new account change output. Adding inputs or changing outputs can invalidate a foreign `SIGHASH_ALL` signature: collect that signature after funding, or use a signature mode appropriate to the final transaction. Finalization verifies every input.

`FundPsbt` requires at least 253 sat/kw. With the integer `sat_per_vbyte` field, use at least 2 sat/vB; 1 sat/vB converts to 250 sat/kw and is refused. Core relay policy may require a higher fee.

Transaction labels are durable records independent of confirmation state and raw-history rows. A known deposit, imported transaction or wallet broadcast may be labelled; unknown transactions are refused. Existing labels require `overwrite=true` to replace them.

Unconfirmed funds are available only when explicitly requested with `min_confs=0` and `spend_unconfirmed=true`. Core must still prove that the parent is in its mempool, the wallet owns the output and the output is unspent. These coins do not appear in confirmed balances or ordinary confirmed coin selection. Discovery is bounded; an incomplete discovery result cannot authorize signing. Account filters apply to both confirmed and unconfirmed inputs.

Output leases remain durable when a parent leaves the mempool, confirms, or is reorganized. A lease with `release_on_confirmations` stays held until the actual spending transaction reaches the requested depth; an elapsed time alone does not release that lease. A time-based lease with a zero confirmation requirement retains its usual expiry behavior.

`BumpFee` can create a wallet CPFP child for a wallet-owned unconfirmed output and replace that child at a higher requested fee. The fee target covers the entire ancestor package, subject to Core relay policy, the requested budget and dust limits. Repeated bumps retain the parent outpoint, account change script and durable replacement lineage. A saved broadcast intent keeps its lease even if the broadcast result is ambiguous; inspect the transaction status before retrying. Automatic deadline-based fee escalation is not provided by this wallet path.
