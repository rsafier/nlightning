## 0. Cross-cutting facts to know first

1. **Channel dispatch handles opening and normal operation.** `src/NLightning.Application/Channels/Managers/ChannelManager.cs` has cases for OpenChannel, AcceptChannel, FundingCreated, ChannelReady, FundingSigned and, since ABCD wave 1 (N6, a604dff), update_add/fulfill/fail/fail_malformed_htlc, commitment_signed, revoke_and_ack and update_fee (Open channels only; `NodeOptions.EnableHtlcs` gates them; not Open → warning + close; Failed → the stored error again). Since ABCD wave 2 `channel_reestablish` is handled (N7, 4ec83d3) and locked-in HTLCs go to `HtlcSwitch` (forward, final hop, fail back; ca87313). Each peer's channel messages run one at a time in arrival order under a per-channel lock, and every send goes through one ordered `PeerOutbox` per peer (NL-033, NL-193). Since ABCD wave 3 `shutdown`/`closing_signed` are handled too (N10, b38ce86), so no BOLT 2 channel message of a v1 channel falls to `default` any more (since wave qit `stfu` (2) and the interactive-tx messages 66-74 have cases too, handled by `StfuMessageHandler` and the `Tx*MessageHandler`s; only `open_channel2`/`accept_channel2` still get the channel-scoped "not supported yet" `warning`, the peer stays connected; a peer `update_*` after its own `stfu` gets warning + close, Q-S-04). A message for a channel we don't know gets an `error` for that channel_id. Channel failures always carry their channel id, never the all-zero id (NL-203).
2. **Peer-level messages.** `src/NLightning.Infrastructure/Node/Services/PeerService.cs` handles `IChannelMessage`, `error`, `warning`, gossip (since gossip wave G-B 256/257/258 go to the graph ingress when the graph is enabled, 258 also to `ChannelUpdateService`, 259 is a channel message handled by `AnnouncementSignaturesMessageHandler`; since gossip wave G-C 261-265 go to `IGossipSyncService` (`Application/Gossip/Sync/GossipSyncManager`: queries answered from the graph by `QueryResponder`, replies to our own queries checked, the peer's `gossip_timestamp_filter` kept for the relay; without a sync service, in-process tests only, queries get empty replies) (`stfu` is a channel message since wave qit, NL-019). Since wave M6, onion_message (513) goes to `IOnionMessageService.HandleIncoming` (queued, never processed on the read loop; dropped when the service is off), and a malformed 513 still gets the NL-207 warning and close (NL-444).
3. **Unknown even message types throw on receive**, as BOLT 1 requires (`src/NLightning.Infrastructure.Serialization/Messages/MessageSerializer.cs`). The BOLT 7 types 256-265 are all registered now (NL-100), so gossip no longer kills peers. Malformed messages (unknown even TLV, wrong wire type) get a connection `warning` and the connection is closed (NL-207).
4. **All tests run in CI.** `dotnet test --filter 'FullyQualifiedName!~Docker'` runs 9236 tests per framework at `a6c633f9` (no skips; net10.0, plus net11.0 when built with SDK 11) including Application.Tests (2361) and Daemon.Tests (603); `scripts/check-sln-configs.py` keeps it that way (NL-167). Docker (local only, OrbStack): green at `a6c633f9` on net10.0 (LND suite 66 incl. `KeysendFlowTests` 2 and `BackupRestoreFlowTests` 3, CLN 42 + 1 Explicit, `MultiNodeHarnessTests` 5 facts, Docker.Utils 2, gossip 28, on-chain legacy + anchors 42 + 2 Explicit, ABCD 3 x 10; SQL Server skipped); green at `a3445f3f` on net10.0 (CLN 39 + 3 Explicit incl. the BOLT 12 offer proofs, LND suite 62, `MultiNodeHarnessTests` 5 facts, gossip 28, on-chain legacy + anchors 40 + 2 Explicit, ABCD 3 x 10; SQL Server skipped); earlier: green at `48a8951` on net10.0 through the container runner scripts (gossip 3 x 24, on-chain 24 incl. both Explicit O5 variants, ABCD 3 x 10, LND suite 58 without SqlServer and the multi-node server-database theory, CLN 22); after gossip wave G-C the gossip suite has 24 tests and the CLN suite 22 (`Docker/Gossip/PublicPaymentFlowTests`, `GossipSyncFlowTests`, `Interop/Cln/ClnGossipTests`; green at `4dc0f77` on net10.0: gossip 24, CLN 22, ABCD 3 x 10, on-chain 22 + 2 Explicit, LND suite 55/56 with the one failure a port collision from a parallel run, NL-359); 139 tests after gossip wave G-B (adds `Docker/Gossip/` 16 and `Onchain/OnchainWatchCatchUpTests`; green at `5bbfbb5` on net10.0 with SQL Server and the multi-node server-database theory skipped: LND suite 57, CLN 15, ABCD 3 x 10, on-chain 22 + 2 Explicit, gossip 16), 120 after gossip wave G-A (green at `164289a` on net10.0 with SQL Server skipped; the 4 `Explicit` BOLT 7 capture tests pass when run on purpose; the list below is the wave 6 breakdown, see root `CLAUDE.md` for the current one), 106 after wave 6, all green at `3ce3cad` on net10.0 and net11.0 when run from an SDK container with `--network host` (the host process cannot reach the container IPs, NL-276), except 2 `Explicit` ones: the BOLT2 Proofs N0/N1/N6-N10 against LND (incl. `ChannelSafetyFlowTests`, `FeeUpdateFlowTests`, `CooperativeCloseFlowTests`), the channel_update exchange, the multi-node harness, the Postgres/SQL Server round trips, `MppFlowTests`, `PaymentRetryFlowTests` and the simple-close proofs (LND suite 57), `Docker/Utils` (2), the CLN interop and close suites (17), the ABCD suite (10;
