# Security review: key material and local attack surface

Wave rf1, lane r3-security-review (2026-09-26), on `wip/fafo` at `8b974626`. Scope: the node key file and
`SecureKeyManager`, the daemon's IPC pipe and cookie, password handling, secret files written by the daemon, and
secrets in logs. The peer-to-peer protocol (BOLT 1-11), channel code, payments and persistence migrations are out of
scope; seams into them are listed under "What remains".

Finding IDs are `SR-##` (this document). Ledger IDs (`NL-###`) are given where the issue already had one; the
integrator assigns ledger IDs to the new ones.

## Threat model

| Actor | Can | Wants | Main defences |
| --- | --- | --- | --- |
| Other local user (multi-user host, shared CI box) | Read world/group-readable files, connect to world-accessible sockets, list processes (`ps`) | Node key, wallet, RPC password, preimages, control of the node over IPC | Owner-only config dir (0700), files (0600) and socket, cookie auth, no secrets on the command line |
| Offline attacker with a copy of the config dir (stolen disk, backup, support bundle) | Unlimited offline guessing against the key file | The master key | Argon2id (64 MiB, 3 passes), random per-file salt and nonce, XChaCha20-Poly1305 |
| Log reader (log shipping, bug reports) | Read logs | Keys, preimages, cookie, passwords | Nothing secret is logged (see SR-16) |
| Same-user malware / root | Everything the node can do | - | Out of scope: it can read process memory and the unlocked key |
| Remote peer | Send Lightning messages | - | Out of scope for this lane |

Assets: the master key (BIP32 root: every wallet and channel key), the node key (identity, BOLT 8, onion ECDH, gossip
and invoice signatures), channel key indexes (reuse = two channels share keys), the key-file password, the IPC cookie
(full node control), the bitcoind RPC password, the database (preimages, channel state, per-commitment secrets).

## Accounting (NL-602: A2 operational books, A3 financial profile)

Lane A3-T7 (2026-10-02), on `wip/acct-a3` at `77f455b0` (A3-T0..T6 merged). Scope: what the built-in accounting adds
to the local attack surface and to the node's privacy: the price source, the classification rules' regular
expressions, the files it reads (prices CSV, lot import, price import) and writes (exports), and the period-close
signature. Plan: `docs/agents/ACCOUNTING_PLAN.md` §6-§8, §11 ("Security and privacy"). Nothing here is reachable by a
remote peer except where stated: every accounting command is IPC 41-45 behind the cookie (SR-05, SR-15), and no
accounting value reaches the Lightning wire.

| SR-27 | Info | **Period-close signature (A3-T5, D-A13).** The close digest is SHA-256 over a preimage that starts with the length-prefixed tag `nltg/accounting/period-close/v1` and covers the period, its last ledger sequence, the feed's chain hash there, the previous close's digest, the node id, the forced flag, the period's financial entries and reliefs, the open lots at its end and the closing state. The node key signs the 32-byte digest through `ILightningSigner.SignNodeMessage` (the signer wipes its copy of the key; no key leaves it). The same key signs BOLT 7 messages, whose signed hash is the double SHA-256 of the message: a close digest is a single SHA-256 of a tagged preimage far longer than 32 bytes, so it cannot equal the inner hash of a gossip message and a close signature cannot be replayed as one (or the reverse) without a SHA-256 preimage. It is not a BOLT `signmessage` (no `Lightning Signed Message:` prefix), so LND's or CLN's `verifymessage` does not check it | ok |

## Liquidity ads (NL-850)

Lane LA7 (2026-10-03), on `claude/youthful-hamilton-x4ngo7` at `10b8ba84`. Scope: what selling and buying inbound
liquidity (BOLT PR #1153 as Eclair 0.14.3 speaks it, `docs/agents/LIQUIDITY_ADS_PLAN.md`) adds to the remote attack
surface and to the node key's use. Unlike the accounting section, this one is reachable by remote peers: any peer can
send `request_funding` in `open_channel2`, `tx_init_rbf` or `splice_init`, and every seller answer we receive is
peer-supplied. Selling is off until `Node:LiquidityAds:FundingRates` lists a rate (D-L3; the config template writes the
section without rates), so SR-28 and SR-29 apply only to a node that sells.

| ID | Sev. | Finding | Status |
| --- | --- | --- | --- |
| SR-28 | Low | **UTXO griefing by buyers (D-L5).** A sale makes us contribute the requested amount from our wallet, so a buyer can lock our confirmed outputs in negotiations it never finishes, opens included (a peer without a channel can start one). Sale slots bound it: at most `MaxConcurrentSales` (4) sale negotiations node-wide and `MaxSalesPerPeer` (1) per node id hold our inputs at once (`LiquidityAdsService.TryStartSale`, in memory); a slot is held from the request until the negotiation completes (both `tx_signatures`, funding published) or aborts (the accepter's `OpenTimeout`, `tx_abort`, the disconnection). Requests from peers without a channel are **not** separately rate-limited beyond these caps (the plan's D-L5 rate limit was not built), node ids are free, so one attacker can fill the node-wide cap and deny sales to others (not funds); the wallet inputs of a signed attempt that never confirms stay reserved until an input is spent (IT-ABT-01), outside the slots | accepted (caps); a per-peer request rate limit is not built |
| SR-29 | Info | **The lease is not enforced.** #1153 asks the seller to keep the channel open for about a month; nothing on the wire binds it. We guard only our own cooperative close: `closechannel` of a channel with a seller purchase whose lease is in force (Pending, or Active before `LeaseStartHeight + LeaseBlocks`, 4,032 blocks) is refused unless `--force` (`ChannelCloseService`, `LiquidityLeases`); the peer's closes and `forceclosechannel` are never blocked (safety first). As buyer, our only recourse against a seller that closes early is the record: `LiquidityPurchases` keeps every purchase with the seller's signed `will_fund`, and a close inside the lease sets `ClosedEarly` (logged as a warning, listed by `liquidityads purchases`); there is no automatic blacklist | by design (D-L4) |
| SR-30 | Info | **Signature scope.** The node key signs `will_fund` through `ILightningSigner.SignNodeMessage`, which signs any 32 bytes as given (also used for BOLT 7 gossip and the period-close digest, SR-27). Our seller signs only `LiquidityAdsRules.SignedData` = SHA256(`"liquidity_ads_purchase"` \|\| funding_rate \|\| funding_script), with the rate one of our configured rates and the script the new funding output's, built by us. It cannot collide with a BOLT 7 signature hash, SHA256(SHA256(message)): equal digests need a SHA-256 collision or the single-hash preimage to be a 32-byte SHA-256 output, and ours starts with the 22-byte tag followed by the 20-byte rate (at least 42 bytes). A buyer cannot make us sign a chosen hash: it chooses only the requested amount and which of our rates, and the amount is not signed | ok |
| SR-31 | Low | **Fee limit.** The fee follows the seller's advertised rate (its `init` or `node_announcement`, both peer-supplied) and the attempt's feerate: the mining part grows with it (`funding_weight` x feerate / 1000), so an RBF to a high feerate makes a repeated purchase dearer, and a seller can advertise a large base or basis-point fee. The buyer checks the whole fee (mining + service) against the request's `--max-liquidity-fee`, else `Node:LiquidityAds:MaxFeeSat`, before anything is funded, and refuses above it (`LiquidityAdsRefusal.FeeTooHigh`: `error` before the interactive tx, `tx_abort` after); the answer must also be signed by the seller over our funding script, at the rate we asked, for at least the amount (`LiquidityAdsRules.ValidateWillFund`), and the fee must leave us our reserve (LA-RES-01, `DualFundLiquidity.GetBalanceViolation`). `MaxFeeSat` is unset by default (`null` in the daemon template), so a request without its own limit accepts any fee at a rate the seller advertised (the rate is chosen by us, the cheapest compatible one unless given) | open by default: set `Node:LiquidityAds:MaxFeeSat` or pass `--max-liquidity-fee` |

## Cashu payment processor (NL-992)

Cashu integration review (2026-10-03, branch `wip/cashu-int`). Scope: the CDK payment processor gRPC server
(`src/NLightning.Cashu.PaymentProcessor`, `Cashu:PaymentProcessor`, `docs/agents/CASHU_PLAN.md` §6), the daemon's only
network API besides the peer port. Whoever can call it can create invoices and offers, pay invoices and offers from the
node's channels and, with `OnchainEnabled`, withdraw from its wallet (`MakePayment`), up to the spend cap (SR-35). It is
off by default and then opens no port; mutual TLS is the default (SR-32).

| SR-33 | Medium | **Ambient endpoints.** `WebApplication.CreateSlimBuilder()` read `appsettings.json` from the working directory and the environment, so a `Kestrel` section there added endpoints beside the checked one (`0.0.0.0` included). Fixed (NL-998): no configuration sources; a start that does not listen on exactly the configured address stops and fails | fixed |

## Key derivation (NL-159)

| Key file version | Written by | Encryption | Master key | Node key |
| --- | --- | --- | --- | --- |
| 1 | builds before NL-158 | Argon2id 64 KiB, fixed salt, zero nonce | private key + genesis hash as chain code | the master private key |
| 2 | v1 upgrade; legacy `new SecureKeyManager(privateKey, ...)` | Argon2id 64 MiB, random salt and nonce | same as v1 | same as v1 |
| 3 | `SecureKeyManager.CreateNew` (daemon, new nodes), `FromMnemonic` | same as v2 | standard BIP32 master (from 32 random bytes of seed, or BIP39) | `m/1017'/0'/6'/0/0` (`NodeKeyPathString`, stored as `nodeKeyPath` and checked on load) |

The file version decides the node id, so a file never moves between derivations: a v1 file is upgraded to v2, never
to v3, and a v2 file is never rewritten as v3 (tests: `Given_Version1KeyFile_When_Upgraded_Then_KeepsTheNodeIdAndTheLegacyDerivation`,
`Given_Version3KeyFile_When_FromFilePath_Then_KeepsTheNodeIdAndTheWalletKeys`). The node key path follows LND's layout
(BIP43 purpose 1017, key family 6), but the seed is not an aezeed, so an LND wallet does not restore it. The wallet and
channel paths are unchanged (`m/84'/0'/0'`, `m/86'/0'/0'`, `m/6425'/0'/0'/0`), so `FromMnemonic` with the BIP84 test
mnemonic gives the BIP84 vector's first address (test `Given_TheBip84TestMnemonic_When_FromMnemonic_Then_DerivesTheStandardBip32Keys`).
Builds older than this one cannot read a v3 file. Moving an existing node to v3 would change its node id and every
wallet key: that needs a new node (close channels, sweep, start fresh), not a file migration.
