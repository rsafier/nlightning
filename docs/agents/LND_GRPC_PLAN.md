# LND_GRPC_PLAN — LND gRPC compatibility (NL-1160)

Loop follow-up: L0–L4 implemented from PR #14; see `LOOP_GRPC_PLAN.md` implementation record and NL-1190..NL-1197.

Status: wave 0 (this plan) and wave 1 done on `wip/lnd-grpc-compat` (from `wip/fafo` 7bf72c20), 2026-10-05;
see "Wave 1 record"; wave 2 done 2026-10-06, see "Wave 2 record". Wave 3 (NL-1168) on `wip/lnd-grpc-wave3`.

NLightning serves a subset of LND's gRPC API (`lnrpc.Lightning`, later `routerrpc.Router`,
`invoicesrpc.Invoices` and `walletrpc.WalletKit`) so existing LND clients can use the node as their
backend: our own in-tree LND client `test/NLightning.Testing.Lnd` first (the same client the cluster
`lnd` suite drives real LND 0.21.4 with), then BTCPay Server, Zeus/RTL-class wallets, Loop and the
Fedimint gateway. It is a sibling of the Bark/ASP backend (`src/NLightning.LnBackend`, NL-1148) and the
Cashu payment processor (`src/NLightning.Cashu.PaymentProcessor`, NL-992): its own Kestrel listener
inside the daemon, off by default, refused on mainnet unless allowed, no IPC involved (the services read
the node's repositories and services directly, as LnBackend does).

## 1. Shape

- Project `src/NLightning.LndGrpc` (Application + Domain + Bolt11 + Infrastructure.Bitcoin references,
  ASP.NET Core shared framework, `Grpc.AspNetCore.Server`), tests `test/NLightning.LndGrpc.Tests`
  (references `test/NLightning.Testing.Lnd`, the client side of the same protos).
- Protos: LND v0.21.4-beta (commit 390b2d2b), vendored byte for byte under `src/NLightning.LndGrpc/Protos/`
  with one change, the `csharp_namespace` line (`NLightning.LndGrpc.Lnrpc`, ...), exactly the rule
  `scripts/lnd-protos/update.sh` applies to the client copy. The proto `package` lines are untouched, so
  the wire service names (`/lnrpc.Lightning/GetInfo`) and every field number are LND's. LND's MIT
  `LICENSE` ships next to them (`Protos/LICENSE-LND.txt`) and `Protos/manifest.txt` records the source
  hashes. Wave 1 vendors `lightning.proto` only (server stubs); wave 2 adds `routerrpc/router.proto`
  and `invoicesrpc/invoices.proto`, wave 3 `walletrpc/walletkit.proto` (it imports `signrpc`).
- Every Lightning RPC we do not implement answers `UNIMPLEMENTED` (the generated base class), after the
  macaroon check (an unknown method of the permission table is refused like LND: `PERMISSION_DENIED`).
- Section `LndGrpc` (`LndGrpcOptions`): `Enabled` (false), `ListenAddress` (`127.0.0.1`), `Port`
  (10009, LND's), `DataDirectory` (`<configPath>/lnd-grpc`), `TlsExtraDomains`/`TlsExtraIps` (SANs of the
  generated certificate), `ClientCaPath` (optional mutual TLS), `AllowNoMacaroons` (false, loopback only),
  `AllowMainnet` (false), `MaxConnections` (16), `MaxDescribeGraphNodes`/`MaxDescribeGraphEdges`
  (bounds on `DescribeGraph`, 0 = LND's unbounded answer). Options are AOT-binder safe (no `required`,
  no init-only members).

## 2. Auth design

### TLS

Always TLS (LND has no plaintext gRPC). At the first start the host generates `tls.cert`/`tls.key` in the
data directory like LND does: ECDSA P-256, self-signed, valid 14 months, SANs `localhost`, `127.0.0.1`,
`::1`, the listen address and `TlsExtraDomains`/`TlsExtraIps`; the key file is written 0600 before use and
never replaced while it exists (delete both to regenerate). Clients pin the certificate (LND's model; our
`LndCertificatePinning` does exactly that). `ClientCaPath` additionally requires client certificates signed
by that CA (the NL-1089 mutual TLS rule), for operators who want both.

### Macaroons (real verification from wave 1)

LND's format, reimplemented in-tree (`NLightning.LndGrpc.Macaroons`): no maintained .NET library speaks
libmacaroons' v2 binary format (the old `Macaroons.Net` is v1-only and unmaintained), and the subset is
small. Verified byte-exact against the Go libraries LND itself links (`gopkg.in/macaroon.v2` v2.1.0,
`gopkg.in/macaroon-bakery.v2` v2.3.0): vectors generated by `scripts/lnd-grpc/macaroon-vectors/` and a
macaroon we bake accepted by the bakery checker (same program, `verify` mode).

- **Binary format:** v2 (`0x02`, packets of uvarint field type + uvarint length: location 1, identifier 2,
  verification id 4, EOS 0, signature 6 of 32 bytes). JSON and v1 macaroons are refused (LND refuses
  anything but v2 too).
- **Signature chain:** `sig0 = HMAC-SHA256(HMAC-SHA256("macaroons-key-generator", rootKey), id)`, then
  `sig = HMAC-SHA256(sig, caveatId)` per first-party caveat; compared in constant time.
- **Identifier (bakery v3):** `0x03 || protobuf MacaroonId { bytes nonce = 1 (16 random); bytes
  storageId = 2 ("0", LND's DefaultRootKeyID); repeated Op ops = 3 { string entity = 1; repeated string
  actions = 2 } }`, ops canonical (sorted by entity then action, grouped). Location `lnd`.
- **Root key:** 32 bytes from the CSPRNG in `<DataDirectory>/macaroons.key` (0600, created exclusively,
  never overwritten). Unlike LND it is not encrypted by a wallet password (our node key is protected by the
  key file password, but the gRPC must work unattended); the file has the protection of the key-file
  directory. Rotation = delete it: the next start makes a new key and re-bakes the three macaroons, which
  invalidates every macaroon baked before. Only storage id `0` exists (no `bakemacaroon`/
  `ListMacaroonIDs` yet).
- **Default macaroons** baked at the start when missing (all 0600; LND writes the read-only and invoice
  ones 0644, we do not): `admin.macaroon` = LND's `readPermissions + writePermissions`, `readonly.macaroon`
  = `readPermissions`, `invoice.macaroon` = `invoicePermissions` (invoices read/write, address read/write,
  onchain read). The op lists are copied from LND's `rpcserver.go` at v0.21.4.
- **Per-method permissions:** LND's `MainRPCServerPermissions()` table, copied (every `lnrpc.Lightning`
  method, implemented or not; later waves add the sub-servers' tables). A call is allowed when every op the
  method requires is in the macaroon's ops, or the macaroon holds `uri:<full method>` (LND's custom URI
  permission).
- **Caveats** (first party, checked like the bakery's `std` checkers): `time-before <RFC 3339>` (expired =
  refused), `ipaddr <ip>` (the caller's address must equal it), `iprange <cidr>`. Everything else is refused:
  `lnd-custom` (no custom caveat acceptors here), `declared`, `allow`, `deny`, `error`, unknown conditions
  and every third-party caveat (a verification id): the bakery would deny an unrecognized caveat too.
- **Transport:** exactly one `macaroon` metadata value, lower- or upper-case hex (LND reads one value and
  hex-decodes it). Missing/undecodable/forged/expired/foreign-root macaroon: `UNAUTHENTICATED`; valid
  macaroon without the method's permission: `PERMISSION_DENIED` (LND answers both as `Unknown` with the
  bakery's text; clients only look at the text, and these codes say more).
- **`AllowNoMacaroons`** (LND's `--no-macaroons`): no macaroon check at all; allowed on a loopback listener
  only and logged as INSECURE at every start.

### Listener rules (why off-loopback is acceptable)

NL-998/NL-1089 require mutual TLS off loopback for the Cashu processor and the LN backend because those
listeners have no other client authentication. Here every call carries a macaroon that is verified for real
(HMAC chain over a node-held root key, per-method permissions), so **server TLS + macaroon off loopback is
acceptable, matching LND**; mutual TLS is optional on top. The configurations refused at start: a
non-loopback listener with `AllowNoMacaroons`; an unparseable listen address; `ClientCaPath` naming a
missing file; any listener on mainnet without `AllowMainnet` (an LND-compatible admin macaroon moves real
funds).

## 3. Per-method mapping

`chan_id` everywhere is the uint64 SCID (`ShortChannelId` big-endian, BOLT 7 layout: block << 40 | tx << 16
| output), 0 while unconfirmed (LND too, apart from zero-conf aliases). `channel_point` is
`<funding txid hex>:<index>`. Amounts in sat are floored from our msat. Times: LND's seconds, `_ns`
fields in Unix nanoseconds.

→ ACCEPTED, Settled → SETTLED, Canceled → CANCELED; an expired Open invoice stays OPEN like LND until its
expiry sweep), `is_keysend`, `payment_addr`. **Difference:** LND's `add_index`/`settle_index` are dense
counters (1, 2, 3, ...); ours are unique and increasing but sparse (ticks). Clients that use them as opaque

dense counter needs a schema change (an auto-increment column on `Invoices`/`Payments`) and is NL-1165.
`htlcs` stays empty (our per-HTLC receive records are not exposed yet, NL-1167).

## 4. Proof strategy

1. **Unit:** macaroon codec and HMAC chain byte-exact against Go vectors; checker accept/refuse matrix
   (admin/readonly/invoice per method class, tampered signature, tampered caveat, expired `time-before`,
   foreign root key, wrong storage id, unknown caveat, third-party caveat, `uri:` permission, missing or
   duplicated metadata, `ipaddr`); SignMessage vectors byte-exact; options validation; mapping helpers.
2. **In-process:** the host starts on a loopback port with mocked node services, and
   `NLightning.Testing.Lnd.LndNodeConnection` (pinning our generated `tls.cert`, sending our baked
   `admin.macaroon`) calls every wave-1 RPC; the read-only macaroon is refused on `AddInvoice`/`SignMessage`.
3. **Cluster (lnd suite):** `Docker/LndGrpc/LndGrpcCompatFlowTests` runs an NLightning node with the
   LND gRPC on, connected to the fixture's LND alice with a channel; the test talks to our node only
   through `LndNodeConnection` like a real LND: GetInfo, ListChannels (chan_id, capacity and balances equal
   what alice reports for the same channel), AddInvoice through us, alice pays it, LookupInvoice/
   ListInvoices show it SETTLED with alice's amount, ChannelBalance moved, SignMessage verified by alice's
   VerifyMessage. Run through `scripts/run-cluster.sh -n 1 --suite lnd --class ...`, then the whole suite.
