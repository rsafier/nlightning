# test/ — agent guide

The xUnit v3 + Moq suite. There is one test project per src layer, plus cross-cutting spec-vector and Docker tests. Tests must never be referenced from src/.

## Layout
- `NLightning.Domain.Tests`: value objects, Money, FeatureSet (BOLT 9), TLV/BigSize models, payloads, CommitmentNumber, CommitmentTransactionModelFactory, BitReader/Writer, and the commitment state machine (`Channels/Commitments/`: exhaustive `HtlcStateTableTests`, per-rule tests named after the BOLT 2 plan matrix, and `CommitmentsTestKit.cs` with fake signer/verifier ports and the two-engine `CommitmentPair` that checks spec agreement and conservation after every signature; `CommitmentPair` also logs each side's domain events (`AliceEvents`/`BobEvents`, with the step name) and has `Disconnect()`; `CommitmentsEventsTests.cs` covers N4-T4 events (incl. `IncomingHtlcSettled`) and `ChannelDomainEvents.DerivePending`; `CommitmentPairSimulator.cs` + `CommitmentSimulatorTests.cs` are the seeded random two-engine invariant harness (it also checks the event invariants after every step: lock-in once and before any removal, fail only when final, every event re-derivable from the persisted transition): 500 seeds by default, the 10k-seed `[Trait("Category", "Long")]` test is `Explicit` and runs only with `-- xUnit.Explicit=only`).
- `NLightning.Application.Tests`: channel handlers (OpenChannel1, AcceptChannel1, FundingCreated, FundingSigned, ChannelReady, and the N6-T1 normal-operation handlers through `Channels/Handlers/NormalOperationTestContext`: pure engine + fake crypto ports, persistence mocks that record the call order; `Channels/Harness/TwoNodeHarness`: two real `ChannelManager`s with real signers joined by in-memory outboxes, sending through the production `ChannelOperationsService` + `CommitScheduler` (no debounce; `PumpAsync` waits for both schedulers) and optionally the real `LocalOnlyHtlcSwitch` with a hand-written `ISphinxService` fake (Moq can't mock its span parameters), the N6-T4 proof, extended for N7 with link drops, crash-at-save restarts and backup restores (`Channels/Reestablish/ReestablishHarnessTests`, see the Application CLAUDE.md); the N6-T2 send side in `Channels/Services/ChannelOperationsServiceTests`, `CommitSchedulerTests` and `Channels/Switch/LocalOnlyHtlcSwitchTests`), PeerManager (`PeerManagerConnectTests`: two real peer managers over loopback, NL-239/NL-240) and `Gossip/ChannelUpdateServiceTests` (real `LocalLightningSigner`s for both ends). Moq-heavy. `Channels/Services/RealSigningCommitmentPair.cs` is a two-engine harness with **real** crypto: each node is built from `AddBitcoinInfrastructure()` + `AddCommitmentEngineServices()` with a Moq `ISecureKeyManager` (deterministic seed) and a Moq `IChannelMemoryRepository`, so the engine ports sign and verify real BOLT 3 commitments; `Commit(from)` records the txid signed and the txid verified for every commitment. Each `RealSigningNode.Events` logs the engine's domain events with the step that raised them. `Payments/` (ABCD W1-B) tests the payment core with real Sphinx onions: `PaymentsTestNode` builds one node from `AddSerializationInfrastructureServices` + `AddBitcoinInfrastructure` + `AddPaymentsServices` with a hand-written `TestNodeKeyManager` (node-key ECDH through NBitcoin; Moq cannot set up span methods) and an `InMemoryInvoiceDbRepository`; `ThreeHopPaymentTests` peels a 3-hop onion at each hop. This is why Application.Tests references `NLightning.Infrastructure.Serialization`. `Channels/Harness/ThreeNodeHarness` (ABCD W2-B) runs Alice → Bob → Carol, each a production `ChannelManager` + `ChannelOperationsService` + `CommitScheduler` + `HtlcSwitch` with real signers, real Sphinx and error onions, the gossip service (signed `channel_update`) and its own SQLite file (real migrations, `UnitOfWork` and repositories, which is why Application.Tests also references `NLightning.Infrastructure.Repositories` and `NLightning.Infrastructure.Persistence.Sqlite`); per-direction FIFOs pumped round-robin; `SwitchNode.SwitchSuspended` records events without handling them (a crash right after the persist); `RestartAsync(node)` reloads the node from its database (startup replay with every link down) and `ReconnectAsync(node)` / `Disconnect(a, b)` + `ReconnectLinkAsync(a, b)` stand in for N7: they only call the production (decorated) `IPeerLivenessProbe.MarkLinkUp`, whose `LinkUpEventReplayer` replays `DerivePending` into the switch as in the daemon (`SwitchNode.ReplayPendingEventsAsync` is the manual replay for tests that un-suspend a switch); `Sent` logs every message with the sender's channel states; each node's `LockAudit` records any flow that takes a second channel lock (per async flow, as an immutable snapshot checked once the lock is taken, so sibling tasks forked from one context are separate flows; W6 integration); hooks: `SwitchNode.ConfigureServices` (last changes to the node's services on every start, set through `ThreeNodeHarness.CreateAsync(beforeStart)`, e.g. a manual `TimeProvider`), `SwitchNode.OnPublish` (every published message, right after its save), `AfterInvoiceRead`, `BeforeSetHtlcOrigin` and `BeforeSetOnionSharedSecret` (through `HookedUnitOfWork`, a wrapper of the production `UnitOfWork`). `Payments/Switch/ThreeNodeSwitchTests` is the W2-B proof (forward + immediate upstream fulfill, final-hop failure decoded at hop 1 after the irrevocable removal, malformed converted, fee_insufficient with Bob's signed update, restarts mid-forward with no lost or double fulfill, lock-in replay, pending circuit without an offer, two HTLCs for one invoice with the reads forced to interleave, the invoice settled in the fulfill's own save, a fulfill refused while the peer is away and sent once the link comes back (upstream and final hop, no restart), an offer that throws before or after its save, a crash between the onion HMAC's save and the shared secret's save that must not turn into a replay after the restart (NL-078); every archived row, incoming and outgoing, pruned).
- Trampoline proofs (NL-875 TR5): `Application.Tests/Payments/Trampoline/Harness/TrampolineHarness`, four `SwitchNode`s A → T → X → C on SQLite files with the production switch, payment service and (registered by the test) relay engine; its `README.md` lists the API, the options and what each phase proves. `TrampolineTargetE2ETests` drives the TR2 target with hand-built onions, `TrampolineRelayE2ETests` the relay engine, leg sender and payer together (restarts, MPP on both legs, NODE|26 retry, refusals, `Auto`, blinded recipients).

## Adding a test (the common case)
1. Put the test in the project that mirrors the src layer, using the same folder path (e.g. `src/NLightning.Infrastructure/Protocol/Tlv/Converters/X.cs` maps to `test/NLightning.Infrastructure.Tests/Protocol/Tlv/Converters/XTests.cs`).
2. Use a file-scoped namespace `NLightning.<Project>.Tests.<Folder>`. Relative `using Domain.X;` directives go after the namespace line.
3. Name tests `Given_X_When_Y_Then_Z`, with `// Arrange / // Act / // Assert` sections. Pass `TestContext.Current.CancellationToken` to async APIs.
4. For a new wire message, add `test/NLightning.Infrastructure.Serialization.Tests/Messages/<Name>MessageTests.cs`. Copy `UpdateAddHtlcMessageTests.cs` and build the serializer through `SerializerHelper`.
5. Spec vectors: shared C# vectors go in `NLightning.Tests.Utils/Vectors/Bolt<N>*Vectors.cs`. Spec tests go in `NLightning.Integration.Tests/BOLT<N>/`. Any text/JSON vector file needs a csproj item with `CopyToOutputDirectory="PreserveNewest"` (Serialization.Tests globs `<None Include="Vectors\*.*" .../>`; Integration.Tests uses `<Content Include="BOLT11/Vectors/ValidInvoices.txt" .../>`, so add `<Content Include="BOLT4/Vectors/*.json" .../>` there).
6. If you need internals, check that the src project's `AssemblyInfo.cs` InternalsVisibleTo lists the test assembly. Domain.Tests and Daemon.Tests are NOT listed (Application.Tests is) (`src/NLightning.Daemon/AssemblyInfo.cs` names a stale `NLightning.Bolts.Tests`). Internal vectors in Tests.Utils are visible only to the assemblies in `test/NLightning.Tests.Utils/AssemblyInfo.cs`.

## Mocking conventions
- Moq cannot mock `Span`/`ReadOnlySpan` parameters. Use the Fake* class + virtual `byte[]` `ITest*` interface pattern in `Tests.Utils/Mocks`.
- For HttpClient, mock `HttpMessageHandler` with `.Protected().Setup("SendAsync", ...)` (see Daemon.Tests/Services/FeeServiceTests.cs).
- `FakeSha256` computes a real SHA-256 over the appended data by default; override its virtual `GetHashAndReset()` via Moq to force a fixed digest. `FakeServiceProvider` returns null for unregistered types like the real provider (NL-249); `new FakeServiceProvider { Strict = true }` throws KeyNotFoundException instead.
- Tests that must run serially need `[CollectionDefinition(Name, DisableParallelization = true)]` plus `[Collection(Name)]`.

## Dependency rules
- Test projects may reference src projects and `NLightning.Tests.Utils`. Nothing in src/ may reference test projects.
- Tests.Utils references only Domain, Infrastructure and Infrastructure.Bitcoin (no Docker.DotNet since NL-866: Integration.Tests, its only user, references it directly). Serialization.Tests and Daemon.Tests do not reference it. No project references LNUnit since NL-820 (`LNUnit`, `LNUnit.LND`, `lnunit.lnd` and its SharpCompress 0.41.0 are gone, and with them the NL-170 audit suppression): `Fixtures/LnUnitAbsenceTests` fails when a project or shared MSBuild file references an LNUnit package, a source uses an LNUnit namespace, or the Integration.Tests deps file resolves an `lnunit*` library. The cluster is the only backend of the CLN, Eclair, LDK and Postgres fixtures since NL-866 (the LND network's since NL-820); only the Tor fixture (`Fixtures/Tor/`) and `SqlServerFixture` (not run) drive Docker, through `Fixtures/DockerContainerUtils` (pull only when missing), and `Fixtures/DockerAbsenceTests` fails when any other source uses the Docker API or the `docker` CLI (allowed besides: `Testing.Lnd.Tests`' Explicit `Docker/DockerCli`), when a project other than Integration.Tests references `Docker.DotNet` (Tests.Utils no longer does), or when a `Docker*Backend` type comes back.
- `src/Directory.Build.props` does NOT apply here. `test/Directory.Build.props` sets the target frameworks (net10.0, plus net11.0 when built with SDK 11, like src; the Blazor projects stay net10.0 only) and `LangVersion` 14, so test csprojs have no `TargetFramework`; each declares Nullable itself and sets `IsTestProject`. With SDK 11, `dotnet test` runs every project on both frameworks (results say `(net10.0)`/`(net11.0)`, so the counts double); `-f net10.0` runs one. Run Docker tests one framework at a time (`-f net10.0`): both would fight over the fixed container names. New test projects need `xunit.runner.visualstudio` (3.1.5) or `dotnet test` discovers nothing. `python3 scripts/check-sln-configs.py` (a CI step) fails when a `*.Tests` project lacks `IsTestProject` or the runner, or when a declared solution configuration has no mapping in `NLightning.sln`.

Only the Tor suite (`run-interop.sh tor`) is Docker only; SQL Server tests are not ported (every matrix suite leaves them out).

## Gotchas
- `!~Docker` is a substring filter, so keep Docker tests in `NLightning.Integration.Tests.Docker` and don't put "Docker" in other test names.
- A non-Docker test that deletes its SQLite file clears only that file's pool, `SqliteTestPools.Clear(path)` (`Application.Tests/TestUtils/`, `Integration.Tests/Persistence/`), never `SqliteConnection.ClearAllPools()`: test classes run in parallel, and clearing every pool disposes the idle connections of other tests' databases while they open them (`ObjectDisposedException` on the `sqlite3` handle, NL-747). The Docker restore tests still call `ClearAllPools` (their collection runs alone).
- Keep tests hermetic: no live DNS or internet outside the Docker namespace. `PeerAddressTests` HTTP cases resolve `localhost` for that reason.
- The only live-DNS test is `Infrastructure.Bitcoin.Tests/Bootstrap/DnsSeedLiveTests` (`[Fact(Explicit = true)]`, `Category=Live`: nodes.lightning.directory over 1.1.1.1 through the real `DnsClientRecordLookup` and `DnsSeedClient`). It never runs by default; run it by hand with `dotnet run --project test/NLightning.Infrastructure.Bitcoin.Tests -f net10.0 -- -explicit only -trait Category=Live -showLiveOutput`. New live tests follow the same pattern.
- The LND regtest network (`LightningRegtestNetworkFixture.NodeNames`: miner, alice, bob, carol, david) runs in a run namespace of its own per collection on the cluster, and one network is shared across the `regtest` collection, so state carries over between tests: assert deltas, never absolute state. `david` is an LND node with no channels (the ABCD payee). Always `PortPoolUtil.ReleasePort` in Dispose (a node made with `NLightningTestNode.CreateAsync` does it itself).

- Isolation rules (the cluster harness shares the machine with the Docker suites): it creates only `nltg-spike-*` namespaces labelled `nltg.run`/`nltg.spike=true` and never touches `default`, `kube-*` or another run's namespace; no cluster-scoped objects; at most 12 run namespaces at once (`RunAdmission.DefaultMaxRuns`, 6 until NL-844; `NLTG_MAX_CONCURRENT_RUNS` lowers it for the test processes; `-j` and `--max-namespaces` are capped at it through `nltg-cluster matrix cap`); pod requests at most 1 CPU / 1 GiB; new images only under `nltg-spike-*` (never rebuild or retag `custom_lnd`, `nltg-eclair*`, `nltg-ldk-server*` or the pulled images); it never runs the Docker suites or uses `docker` on `k8s_*` containers. It can run while a Docker suite runs: they share no names or ports.
